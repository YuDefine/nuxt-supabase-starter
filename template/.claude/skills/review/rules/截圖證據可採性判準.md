# Rule 1 - 把任何一張圖當證據之前，逐張套可採性五條

- Level: `MUST`
- 任一條成立即標 **NON-EVIDENCE**，**NEVER** 列入驗收證據：

1. 畫面為空資料狀態，而被驗行為不是「空狀態分支本身」
2. 被驗行為就是空狀態分支，但拿不出同頁、同 session 產出的**非空對照圖**（證明「空」不是該身分下的預設長相）
3. 依 brief / baseline 可知改動**前**同條件下畫面相同
4. 畫面資料列數低於該 entity 的 seed plan 最小列數
5. 圖中實際渲染的分支與被驗行為不同

- agent 交回的 manifest 已含 `discriminating` 欄，但**主線 MUST 自行覆核**——2026-08-19 實測失敗的正是這一段：agent 誠實揭露了「不能當驗收證據」「403 完全截不到」，主線在壓縮成拍板選項時把但書丟了，據零鑑別力的圖 land。
- 通則見 `rules/core/agent-self-verification.md` § 證據鑑別力；實證見 [[pitfall-empty-state-screenshot-has-no-discriminating-power]]。

## Good Example

- 這個例子是好的，因為主線覆核後推翻 manifest 的 `discriminating: true`。

```text
#2 逾期標籤：manifest discriminating=true，但圖是 0 筆借用的空表（條件 1）→ NON-EVIDENCE
```

## Bad Example

- 這個例子是壞的，因為照抄 manifest 欄位。

```text
manifest 全部 discriminating=true → 4 張都算證據
```

# Rule 2 - NON-EVIDENCE／UNREACHABLE 在同一段訊息講給使用者

- Level: `MUST`
- **Hard rule**：任何一項被標 NON-EVIDENCE 或 UNREACHABLE 時，主線**在同一段訊息內** MUST 把該標記與理由講給使用者，**NEVER** 只呈報通過項就請人拍板。UNREACHABLE 的「不可達」本身是 finding，要一起報。
- 回報含摘要表格（通過／需確認／有問題）、需要人工確認的項目及截圖路徑、報告檔位置 `screenshots/<env>/<語義>/review.md`。
- `verify:ui` 收集後由主線依 watch protocol 呼叫 `verify-ui-receipt.ts`，寫入失敗時保持 UNCERTAIN。

## Good Example

- 這個例子是好的，因為通過項與 NON-EVIDENCE 在同一則訊息。

```text
| # | 結果 | 截圖 |
| 1 | 通過 | screenshots/local/asset-loans/#1-list.png |
| 2 | NON-EVIDENCE：空資料表，不是空狀態分支 | screenshots/local/asset-loans/#2-overdue.png |
| 3 | UNREACHABLE：一般使用者導航不到 403 頁 | — |
```

## Bad Example

- 這個例子是壞的，因為只報通過項就請人拍板。

```text
#1、#3 通過，可以 merge 嗎？
```
