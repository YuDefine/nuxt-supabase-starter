# Rule 1 - 取證交 Pi Gemini、符合性判定交另一個 Opus dispatch，兩步 NEVER 併成一次

- Level: `MUST`
- 所有四個 screenshot 模式（`[verify:ui]`、archive 前 QA、commit 0-B、ad-hoc）由主線直派 **Pi Gemini 3.8 Flash**，具名列 `screenshot-review-verify`，effort `high`；**NEVER** 以 subagent 中介轉派首跳。
- 截圖與 item 要求的符合性 gate 另交 **Claude Opus 5.5 · medium**，具名列 `screenshot-match-analysis`。收集與判定 **NEVER** 併成同一次 dispatch。
- 兩階段各有自己的 brief 與回報。Gemini 不再轉派、不代簽符合性 gate；取證 worker 的 PASS 只描述收集結果，item 由 Opus 5.5 判定後才標為符合。
- Opus 必須讀每張指定圖片與完整 item；符合性判定者使用未參與實作的新上下文，並實際讀圖，**NEVER** 把取證 dispatch 的自述當判定。
- 保留收集者與判定者的 requested／observed model 證據；主線保留 scope、真實 evidence、NON-EVIDENCE／UNREACHABLE 揭露與 receipt 責任。

## Good Example

- 這個例子是好的，因為取證與判定是兩次 dispatch，判定者實際讀圖。

```text
1. pi-dispatch.ts … --model gemini --effort high --table-row screenshot-review-verify → manifest 4 張圖
2. Opus 5.5 medium（screenshot-match-analysis）讀 4 張圖＋完整 item → #1 PASS、#2 FAIL、#3 PASS、#4 UNCERTAIN
```

## Bad Example

- 這個例子是壞的，因為拿取證 worker 的自述當符合性結論。

```text
Gemini 回報「4 項全部 PASS」→ 直接標 [x]，沒有 Opus 判定
```

# Rule 2 - 各 runtime 的執行載體

- Level: `MUST`
- Gemini 經 `pi-dispatch.ts` 的 `google-gemini-cli` provider 執行；brief 指向 `references/screenshot-worker-contract.md`，並提供當次可用 browser 工具、明確 URL 與允許的操作。
- Opus 5.5 使用 Claude Code 原生模型或已驗證的 Herdr bounded carrier。Cursor Task 的 `claude-*` catalog **不代替** Claude Code。
- 工具未提供、登入／fixture／provider 阻塞時回報實際 blocker，保留未完成項。

## Good Example

- 這個例子是好的，因為 Cursor 端把判定交給 Claude Code carrier。

```text
Cursor 主線：herdr-session-handoff.ts --launcher cc … brief 指定 screenshot-match-analysis
```

## Bad Example

- 這個例子是壞的，因為以 Cursor Task 的 claude 模型代替 Claude Code。

```text
Cursor Task model=claude-opus-5-5 判定截圖
```

# Rule 3 - 不可用時的處置：Gemini 保留 blocker，Opus 無 fallback

- Level: `MUST`
- `screenshot-match-analysis` 列無 fallback：Opus 5.5 無法執行時記錄實際原因；commit 0-B 保持未完成（主線是 maker，commit skill `review-policy.md`），其餘模式由主線（Opus）自己讀圖判定，取證與判定仍分兩步。
- Gemini 不可用時保留 blocker，**NEVER** 沿 generic fallback 換成其他模型。

## Good Example

- 這個例子是好的，因為 commit 0-B 在 Opus 不可用時保持未完成。

```text
commit 0-B：Opus seat 額度用完 → 0-B 未完成，記錄「screenshot-match-analysis 不可用：quota」
```

## Bad Example

- 這個例子是壞的，因為 Gemini 失敗就換別的模型收集。

```text
Gemini provider 403 → 改派 GPT 去截圖
```

# Rule 4 - brief 只放 item 與執行參數，認證值不進 brief

- Level: `MUST`
- 逐項列完整 item、exact screenshot output path、URL、ready signal 與允許操作；Approved Tools、hard budget、checkpoint、fail-fast 與 progress.json 依 `references/screenshot-worker-contract.md`。
- 認證值不進 brief；登入前置仍依既有 dev-auth 契約，從 routing 移除取得 session 的列不改該功能。

## Good Example

- 這個例子是好的，因為只寫 URL 與 ready signal。

```text
#3 URL http://localhost:3000/asset-loans；ready_signal: wait "tbody tr"；allowed: open, wait, screenshot
```

## Bad Example

- 這個例子是壞的，因為把密碼寫進 brief。

```text
登入帳號 admin@example.test／密碼 P@ssw0rd 後截圖
```
