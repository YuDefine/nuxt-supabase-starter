# 訪談提問與收斂判準

觸發點：`SKILL.md` Phase 2 step 1（本次訪談第一次挑題前讀一次，之後沿用）。

標記「待讀程式碼」：使用者答不了的技術事實（出錯點有沒有 I/O、在哪個函式或 API）不問使用者，也 **NEVER** 自行填值；標「待讀程式碼」列成未決題，由 work-route 讀程式碼判。下文 gate 的例外都指這個標記。

# Rule 1 - 依訪談維度盤點缺口，每個子項標 Clear／Partial／Missing

- Level: `MUST`
- 每次挑題前，對照下表逐項標記；已知事實（使用者說過、Phase 1 從 artifact 讀到的）標 Clear，不再問。
- 分流事實維度不在本檔列子項：以 Phase 1 step 3 從 work-route 判準讀到的 predicate 逐項盤點（單一溯源，判準改了這裡自動跟上）。

| 維度 | 掃描子項 |
| --- | --- |
| 目標 | 想解決什麼問題；做完誰的什麼事變好；怎麼知道成功了 |
| 使用者與情境 | 誰在用（角色、權限）；在什麼時機、什麼畫面或流程用；頻率與量級 |
| 現況與痛點 | 現在怎麼做；哪裡卡、哪裡錯、哪裡慢；已試過什麼 |
| 範圍 | 這次一定要有的；可以下一次的；明確不做的 |
| 驗收例子 | 至少一個具體例子：給定什麼資料或狀態、做了什麼、應該看到什麼；邊界與錯誤情境各一 |
| 限制 | 期限、相依的外部系統或人、資料與權限邊界、不能動的既有行為 |
| 分流事實 | Phase 1 step 3 讀到的每一個 predicate |

## Good Example

- 這個例子是好的，因為已從 truth 讀到的事實標 Clear 不再問，缺口集中在使用者才知道的事。

```text
目標：Partial（知道要「匯出報表」，不知道給誰看）
驗收例子：Missing
分流事實／既有 scenario：Clear（specs/truth/features/api/報表.feature 已有「匯出月報」）
→ 下一題問：這份報表是給誰、拿去做什麼？
```

## Bad Example

- 這個例子是壞的，因為沒有盤點就照固定清單從頭問，問了 artifact 已回答的事。

```text
Q：請問這個功能目前有沒有測試？（specs/truth 已有對應 scenario）
```

# Rule 2 - 依影響排序挑題，一次只問一題

- Level: `MUST`
- 通則（先問影響大的缺口、上游先於下游）同 `../clarify/rules/盤點高影響需求缺口與提問排序判準.md` Rule 1；本 skill 的影響序：會改變分流列或 `work_kind` 的 > 會改變範圍與驗收的 > 會改變做法的 > 細節。gate 多項不過時照此序挑一項。
- 一次只問一題（與 clarify 每輪 1–3 題刻意不同）。開放題用使用者的語言問，不夾術語；問完就停，等回答。
- 使用者的回答同時答到其他子項時，一併標 Clear，不再問。

## Good Example

- 這個例子是好的，因為先問會決定分流的上游問題，而且一次一題。

```text
先確認一件事：現在匯出出來的數字是錯的，還是根本還沒有匯出這個功能？
```

## Bad Example

- 這個例子是壞的，因為一次丟出多題，還先問了要等分流確定後才有意義的細節。

```text
1. 要匯出 Excel 還是 CSV？ 2. 欄位有哪些？ 3. 這是 bug 嗎？ 4. 期限是？
```

# Rule 3 - 需要使用者拍板的取捨改用 QnX 格式

- Level: `MUST`
- 只在問題是「從幾個已知方案選一個」且答案會改變範圍、做法或分流時改用 QnX；格式照 QnX 協定（Charles 全域 CLAUDE.md § QnX 協定），下方範例僅示意。
- 還在探索、方案尚未成形時維持開放題，**NEVER** 為了好回答而捏造選項。
- 使用者回答後，把拍板結果記成已確認決策，摘要時列入；開放題裡使用者明確做出的決定（例如「四捨五入到整數」）同樣記成已確認決策。

## Good Example

- 這個例子是好的，因為取捨已成形，選項各附後果，推薦排第一。

```text
Q1：匯出的資料範圍？
- A. 只匯出目前篩選結果（推薦）：與畫面一致，量級可控
- B. 匯出全部歷史：要另做背景工作與下載通知
```

## Bad Example

- 這個例子是壞的，因為方案還沒成形就硬給選項，把使用者框在 AI 猜的答案裡。

```text
Q1：你的痛點是？ A. 太慢 B. 太貴 C. 其他
```

# Rule 4 - 過收斂 gate 才進摘要

- Level: `MUST`

評估：gate checklist，逐項檢查；任一不過 → 回 Phase 2 step 1 繼續問

| id | 檢查 | 不過時 |
| --- | --- | --- |
| G1 | 分流事實都已 Clear（標「待讀程式碼」者除外） | 問最上游那個分流事實 |
| G2 | 目標與範圍（含明確不做的）都是 Clear | 問缺的那一項 |
| G3 | 至少一個具體驗收例子（`work_kind` 候選為 behavior 或 bug-uncovered 時另含一個邊界或錯誤例子） | 請使用者舉一個例子 |
| G4 | 每個 Partial／Missing（標「待讀程式碼」者除外）已問到，或使用者說「先記著」並列成未決題 | 問它，或確認先記成未決題 |

- 使用者說「先這樣」「夠了」時，照目前狀態進摘要，未過 gate 的項目全列成未決題，**NEVER** 用推測補成已確認。
- 會改變分流、範圍或驗收的缺口只能列未決題，**NEVER** 寫進「我的推測」：使用者確認摘要時推測會一併升為已確認假設，放進推測等於用一聲「對」繞過 gate。推測只放不影響這三者的理解前提。

## Good Example

- 這個例子是好的，因為 G3 未過時先要例子，使用者喊停時把缺口列成未決題。

```text
G1 ✓ G2 ✓ G3 ✗ → 「可以舉一個你最常匯出的情況嗎？哪個月、哪幾家客戶、預期看到什麼數字？」
使用者：「先這樣，例子我明天問會計」→ 進摘要，未決題：驗收例子（會計提供）
```

## Bad Example

- 這個例子是壞的，因為沒有驗收例子就自己編一個，寫成已確認。

```text
驗收例子（已確認）：匯出 2026-09 月報，總額 123,456
```
