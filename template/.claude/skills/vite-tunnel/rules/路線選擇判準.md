# Rule 1 - 先判定要不要用 named tunnel，再依實際載入的整合選路線

- Level: `MUST`
- 由上往下比對，第一個符合的列就是結論：

| # | 情境或偵測信號 | 結論 |
| --- | --- | --- |
| R1 | 單機開發＋agent 並行驗證，或多 worktree 並行 dev server | 改道：`vendor/snippets/dev-auth/` cookbook 繞 OAuth（加 cookie namespace） |
| R2 | 臨時 webhook 測試、不需要預先註冊固定 URL | 改道：`cloudflared tunnel --url http://localhost:<實際-port>` 拿 quick tunnel |
| R3 | 給產品加**公開** hostname 到 remotely-managed tunnel（`cloudflared tunnel run --token`） | 改道：`vendor/snippets/cloudflare-tunnel-hostname/` cookbook（API／CLI；dashboard 404 不是停工理由） |
| R4 | lockfile 已安裝、且實際載入的 Vite config 已啟用支援 `tunnel` 的 `@cloudflare/vite-plugin` | 官方 Vite 路線（cookbook § A） |
| R5 | 一般 Vite 專案，本次採用第三方整合 | 第三方路線（cookbook § B） |
| R6 | Nuxt／Nitro 或其他已有 dev server，未使用上列整合 | 獨立 cloudflared 路線（cookbook § C） |

- `wrangler.*` 存在只表示有 Cloudflare 配置，不證明正在使用 Vite plugin；判 R4 前 MUST 查 lockfile 的安裝版本、實際載入的 config 與該版本 API，官方選項依 [Cloudflare local-dev tunnel 文件](https://developers.cloudflare.com/workers/local-development/local-dev-tunnels/) 核對。
- Nuxt 的 Vite 配置由 Nuxt 承接，NEVER 假定根 `vite.config.ts` 會被讀取。

## Good Example

- 這個例子是好的，因為看到 `wrangler.jsonc` 仍去查實際載入的整合，Nuxt 專案沒有 Vite plugin 整合就走 R6。

```text
Nuxt 4 專案、有 wrangler.jsonc、lockfile 無 @cloudflare/vite-plugin、要手機測 Google OAuth
→ R1–R3 不符；R4 不符（未安裝）；R5 不符（非一般 Vite）→ R6 獨立 cloudflared 路線
```

## Bad Example

- 這個例子是不好的，因為把 `wrangler.*` 當成官方 plugin 的證據，並在 Nuxt 專案新增不會被載入的根 `vite.config.ts`。

```text
有 wrangler.jsonc → 走官方 Vite 路線 → 新增 vite.config.ts 寫 cloudflare({ tunnel })
```
