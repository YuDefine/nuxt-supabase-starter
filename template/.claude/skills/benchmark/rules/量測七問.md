# Rule 1 - 說得出 limiter，才算知道量到了什麼（為什麼不是兩倍）

- Level: `MUST`
- 指名限制結果的資源或程式路徑（核心、鎖、磁碟、網路、load generator 自己），證據來自 profile 或執行期間的系統計數器（每行程 CPU、runtime profiler、I/O wait、syscall 計數），再對到原始碼。
- 看程式碼猜出來的不算 limiter。
- profiler 與 tracer 會拖慢工作：在不報告的那一次跑 profile，**NEVER** 把 profile 跑的數字當結果。
- 先確認 load generator 沒有先飽和；飽和就是你量到的是 load generator。
- 改動沒讓數字動時，limiter 就是解釋；找到它之前不要判定改動沒用。

## Good Example

- 這個例子是好的，因為 limiter 來自不報告的 profile 跑，且對到原始碼。

```md
Limiter：單核 JSON parse。另跑一次 `node --cpu-prof`（該次數字不報告），`parseRows` 佔 62% CPU，其他核心閒置。
```

## Bad Example

- 這個例子是壞的，因為 limiter 是讀程式碼猜的，沒有任何量測證據。

```md
Limiter：我看 export 函式裡有個迴圈，應該是這裡慢。
```

# Rule 2 - 每一側都要調到 production 設定

- Level: `MUST`
- 每一側都用 production 跑它的方式：release build、production 旗標與 env、批次與交易設定、連線池、與 production 同樣冷熱的快取，版本與資料一致。
- 有一側跑預設設定，比的是設定而不是實作。limiter 本身是一個設定（逐列 commit、debug build、缺 index）就代表那一側沒調好。
- 調好再量一次才能選贏家；調不了就不要從那次跑選贏家。
- 使用者是在挑要採用哪個選項時，把結論縮窄成「今天出貨的程式碼」不能解決這點，因為他們採用的是選項，不是今天的設定。

## Good Example

- 這個例子是好的，因為兩側都開 WAL 與批次交易，並把條件寫進報告。

```md
better-sqlite3 與 node:sqlite 都開 WAL、synchronous=NORMAL、每 1000 筆一個交易；寫入量 100k 筆。
```

## Bad Example

- 這個例子是壞的，因為一側逐列 commit、另一側批次，比的是交易設定。

```md
better-sqlite3（預設逐列 commit）8.1s；node:sqlite（批次交易）1.2s，所以 node:sqlite 快 7 倍。
```

# Rule 3 - 用算術檢查結果有沒有超過物理上限

- Level: `MUST`
- 把每秒位元組與磁碟、網路頻寬比；每秒操作數乘每次操作成本與核心數比；省下的時間與被改動那一段原本占的時間比。
- 移除占 10% 的片段，整體最多快約 11%。
- 超過上限的結果量到的是別的東西：快取、no-op 或 bug。

## Good Example

- 這個例子是好的，因為先用算術算出上限，再拿結果比對。

```md
被改的 `serialize` 原本占 12% 的執行時間，整體上限約快 13.6%；量到 −35% 超過上限，先查是不是快取命中。
```

## Bad Example

- 這個例子是壞的，因為沒算上限，直接接受不可能的結果。

```md
把 `serialize` 最佳化後整體快 35%，很棒。
```

# Rule 4 - 數失敗並驗輸出正確

- Level: `MUST`
- 數失敗次數與非成功回應，並檢查輸出是正確的，不只是有輸出。
- 拒絕通常很快，timeout 與重試很慢，這兩種都會扭曲數字。
- 腳本沒數錯誤就加上錯誤計數。

## Good Example

- 這個例子是好的，因為報告帶錯誤數並用輸出 checksum 確認內容正確。

```md
兩側各 0 個失敗；輸出 sha256 一致。
```

## Bad Example

- 這個例子是壞的，因為只看到有回應就當成功。

```md
回應 200，p50 33 ms。
```

# Rule 5 - 每側至少 5 次、交錯、報 median 與範圍

- Level: `MUST`
- 每側至少跑 5 次並交錯（A、B、A、B…），讓暖機、lazy initialization、快取與漂移不偏袒任一側。
- 報 median 與 range。差距小於 run-to-run 變異就是沒有可量測差異。
- 兩組數字交給 `scripts/summarize-runs.mjs` 判方向；差距很接近時才用 rank-sum 檢定或 harness 自帶統計。

## Good Example

- 這個例子是好的，因為交錯、跑數足夠並附範圍。

```md
7 次交錯：A median 41 ms（range 40–44）、B median 33 ms（range 32–35）。
```

## Bad Example

- 這個例子是壞的，因為各跑一次、先 A 全跑完再跑 B，且沒有範圍。

```md
A 41 ms，B 33 ms，B 快 20%。
```

# Rule 6 - 把微觀結果放在端到端的占比裡

- Level: `MUST`
- 微觀結果旁邊，量使用者等待的端到端路徑（真實資料量與併發），並把微觀結果寫成整體的占比。
- 只占請求 1% 的 helper，不論它多快，整個請求最多快 1%。

## Good Example

- 這個例子是好的，因為同時給微觀與端到端數字。

```md
`parseRows` 快 40%，但它只占請求 6%，端到端 p50 只快約 2.4%（7 次交錯量得）。
```

## Bad Example

- 這個例子是壞的，因為只報微觀數字，讀者會以為整個請求快 40%。

```md
`parseRows` 快 40%。
```

# Rule 7 - 確認工作真的在計時區間內發生

- Level: `MUST`
- 確認工作真的跑在計時區間內：請求到了 server、資料列寫入了、位元組被讀了、程式碼用到了結果。
- lazy 程式碼（沒人迭代的 generator、沒人 await 的 promise、JIT 可丟棄的結果）與 timeout 會替沒發生的工作產生數字。

## Good Example

- 這個例子是好的，因為用獨立計數證明工作發生了。

```md
計時結束後 `SELECT count(*)` 為 60,000，與輸入筆數一致。
```

## Bad Example

- 這個例子是壞的，因為 promise 沒被 await，量到的是排進事件迴圈的時間。

```md
`console.time('write'); db.writeAll(rows); console.timeEnd('write')` → 0.4 ms。
```
