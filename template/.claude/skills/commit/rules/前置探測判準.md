# Rule 1 - D0-Coord：三種活動線索命中先協調，全靜默也不免除所有權判定

- Level: `MUST`

跑三種活動線索（index.lock 年齡、publish sidecar、wt-helper stash），都是 warn-only 探測。任一命中時先完整讀 [gates.md](../gates.md) § 0-Coord，依實際身份與已授權的通道協調，未解決策再詢問使用者。線索全靜默不免除 Rule 4 的所有權判定。

## Good Example

- 這個例子是好的，因為命中線索後先讀對應 § 並找到具體持有者。

```md
`index.lock` 年齡 3 秒 → 讀 `gates.md` § 0-Coord → 查到是 publish session 在跑 → 等它結束再進 Rule 4。
```

## Bad Example

- 這個例子是壞的，因為把「線索全靜默」讀成「這些檔都是我的」。

```md
三條 signal 都沒命中 → 跳過歸屬判定，直接分組。
```

# Rule 2 - 所有 uncommitted 變更預設全數列入本次流程

- Level: `MUST`

批次模式的工作區是 helper 登記的 integration path，全包固定成員的完整 base→candidate diff；main 的既有 WIP 保留。已在本批正式 commit 的內容仍屬範圍，**NEVER** 因 `git status` 乾淨就省略批次的自驗。

所有 `git status` 顯示的 uncommitted 變更（含與本次工作無關、其他 session 並行的 WIP、不認得的檔案）**一律無條件**列入候選，照常進 D2 自驗、在 D3 依功能分組成獨立 commit。

## Good Example

- 這個例子是好的，因為不認得的檔也列入候選並分組。

```md
`git status` 有 3 個不是本 session 改的檔 → 列入候選 → D2 一起驗 → D3 自成一組 commit。
```

## Bad Example

- 這個例子是壞的，因為以 `git status` 乾淨為由省略批次已 commit 內容的自驗。

```md
integration 工作區 `git status` 乾淨 →「沒有變更，不用驗」→ 直接 seal。
```

# Rule 3 - D0-Transport：缺能力的檢查保持未完成，不換載體補位

- Level: `MUST`

D2 自驗用當前 runtime 的原生操作；隨 skill 交付的 CLI 位於 `$COMMIT_RESOURCE_DIR` 底下（解法見 [runtime-lifecycle.md](../runtime-lifecycle.md) § 執行依賴），gate 證據契約查 [runtime-gates.md](../runtime-gates.md)。缺能力就明示未完成並回報缺口，**NEVER** 悄悄換載體、略過或捏造 receipt。

# Rule 4 - D0-Scope：列候選、查歸屬、保留 WIP

- Level: `MUST`

先完整讀當前 runtime 已投影的 `commit.detail`「WIP 處置決策樹」與 `scope-discipline`「歸屬探測前置」。使用者在本任務或參數中指定的範圍持續有效；不同主題、來源陌生、想讓 commit 乾淨都不是自行排除或 stash 的理由。

每組提交前確認內容歸屬、授權與活躍寫入者的交接；HEAD 沒有該檔、路徑互不重疊都不能證明 ownership，歸屬未明的內容保留原狀。WIP 確實阻礙時，用 `commit.detail` 的三項 stash predicate，限定已授權路徑，建立後立即釘住 SHA 並寫進 HANDOFF（SHA、理由、範圍、恢復指引）才繼續。丟棄 WIP 須使用者對具體對象與動作的明確指示，**NEVER** 以「清理」「回到 baseline」代替授權。判定完成後直接進 D2，不再請使用者重複觸發 `/commit`。

## Good Example

- 這個例子是好的，因為 stash 前滿足 predicate、限定路徑、釘住 SHA 並登記 HANDOFF。

```md
別的 session 的 `foo.ts` WIP 擋住 typecheck、三項 predicate 成立且已授權
→ `git stash push -m <tag> -- foo.ts` → 記下 stash SHA → HANDOFF 寫 SHA、理由、範圍與恢復指引 → 才繼續。
```

## Bad Example

- 這個例子是壞的，因為以「讓 commit 乾淨」為由丟棄 WIP。

```md
「這幾個檔跟這次無關，先清理一下回到 baseline」→ `git checkout -- .`。
```

# Rule 5 - D0-MR：main／master 與 batch integration 的 Branch Gate，硬擋無 override

- Level: `MUST`
- 觸發：branch 是 `main` / `master` 或 helper 登記的 batch integration，且本次觸及進行中的 work item carrier（`tasks/<date>-<slug>.md`、`specs/plans/NNN-<slug>/tasks.md`、`docs/plans/<id>/tasks.md`）。其他 feature branch 才 skip。

觸發時 **MUST** 先完整讀 [gates.md](../gates.md) § 0-MR 的判定流程、auto-triage 路由表與禁止項。判定粒度是 **pathspec 交集**：BLOCK 的工作只 withheld 自己 carrier 的路徑，其餘 group 照常走 D3。批次 scope 含已正式 commit 的部分，不能因 branch 名稱或 status 乾淨跳過。

## Good Example

- 這個例子是好的，因為只 withheld 被擋工作自己的 carrier 路徑，其餘 group 照常提交。

```md
commit 觸及 `tasks/2026-10-01-auth.md`（人工檢查未完）→ 讀 `gates.md` § 0-MR → 該 carrier 路徑 withheld → 其他 group 走 D3。
```

## Bad Example

- 這個例子是壞的，因為以 branch 名稱與 status 乾淨跳過批次的 gate。

```md
在 `codex/batch-1a2b`、`git status` 乾淨 →「不是 main，也沒有變更」→ 跳過 D0-MR。
```
