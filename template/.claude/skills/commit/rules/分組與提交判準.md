# Rule 1 - 分組輸入用 `git status --porcelain`（Step 2）

- Level: `MUST`

```bash
git status --porcelain          # 分組輸入的權威來源（含 tracked modified + untracked）
git diff --stat                 # 僅輔助看 tracked 改動規模；NEVER 當分組輸入唯一來源
```

> **分組輸入 MUST 用 `git status --porcelain`，不是 `git diff --stat`**：`git diff --stat` **只列 tracked modified**，會漏掉 untracked 非 ignored 檔（`??` 開頭，如新建的 `tasks/todo.md` / `docs/<new>.md`）。只憑 `git diff --stat` 分組 → untracked 檔被 silently 丟掉、never commit。每次分組前自問：「`git status` 有沒有 `??` 開頭的行？沒被 `.gitignore` 覆蓋 = 必須納入分組。」

**分組輸入 = Step 2 的 `git status --porcelain` 完整輸出**（tracked modified + untracked 非 ignored），**NEVER** 只用 `git diff --stat`。

## Good Example

- 這個例子是好的，因為 `??` 的 untracked 檔進了分組。

```md
`git status --porcelain` 有 ` M src/a.ts` 與 `?? docs/new.md` → 兩個都列入分組輸入。
```

## Bad Example

- 這個例子是壞的，因為只看 `git diff --stat`，untracked 檔被靜默丟掉。

```md
`git diff --stat` 只列 `src/a.ts` → 只 commit 它 → `docs/new.md` 留在 working tree 沒人管。
```

# Rule 2 - `.gitignore` 有變更時的處置（Step 2）

- Level: `MUST`

若 `.gitignore` 有變更：

- **允許保留**：僅新增 Clade 管理的 installation artifact / runtime state ignore 條目（例如 `.claude/.commit.lock`、`codex/`）
- **其他變更** → 回到 Step 0-Scope 查明歸屬與本次授權；需要 stash 時先滿足同一套三項 predicate，限定 `.gitignore` 並釘住 SHA、登記 HANDOFF。**NEVER** 用 `git checkout .gitignore` 直接還原（會毀掉使用者的 WIP）。

## Good Example

- 這個例子是好的，因為非 Clade 管理的條目回到 0-Scope 查歸屬。

```md
`.gitignore` 多了 `dist-preview/`（不是 Clade artifact）→ 回 Step 0-Scope 查是誰加的、是否在本次授權內。
```

## Bad Example

- 這個例子是壞的，因為直接還原會毀掉使用者的 WIP。

```md
`.gitignore` 有不認得的變更 → `git checkout .gitignore`。
```

# Rule 3 - 依功能分組並輸出（Step 3）

- Level: `MUST`

依功能/目的分組並輸出：

```text
### Group 1: [功能描述]
類型: feat
檔案:
- path/to/file.ts
```

`類型` 取值與 Step 4 訊息開頭的 emoji（`commitlint.config.ts`）：

| Emoji | Type     | 用途     |
| ----- | -------- | -------- |
| ✨    | feat     | 新功能   |
| 🐛    | fix      | Bug 修復 |
| 🧹    | chore    | 維護     |
| 🔨    | refactor | 重構     |
| 🧪    | test     | 測試     |
| 🎨    | style    | 樣式     |
| 📝    | docs     | 文件     |
| 📦    | build    | 建置     |
| 👷    | ci       | CI/CD    |
| ⏪    | revert   | 還原     |
| 🚀    | deploy   | 部署     |
| 🎉    | init     | 初始化   |

- **Untracked 非 ignored 檔（`??`）一律納入分組**，通常自成獨立 `chore` group（除非語義明確屬於某 feat / fix group）
- 看到 `??` 開頭的檔想加 `.gitignore` 消掉時 **STOP**：先問「這本來就該 ignore（build artifact / runtime state），還是我在逃避 commit？」逃避 commit 而 gitignore = 把該入庫的東西藏掉，方向反了（詳見 [[wip-orphan-recovery]] § 反射性 gitignore 禁令）
- **0-MR withheld scope 內的路徑不進任何 group**（gates.md § 0-MR step 6 印出的 carrier 路徑）：它們留在 working tree，Step 5-A 登記進 HANDOFF。這是「全部變更都要入庫」的機械例外

分組顆粒是本 skill 的**內部決策**：**NEVER** 對別的 session 宣告「我要拆幾筆、哪筆先 land」或拿它協調——對方要等的只有「land 了沒有」這一個布林。

## Good Example

- 這個例子是好的，因為 untracked 檔自成 chore group，0-MR withheld 的路徑不進任何 group。

```md
### Group 1: 登入逾時修正
類型: fix
檔案:
- server/auth/session.ts

### Group 2: 新增工作筆記
類型: chore
檔案:
- tasks/2026-10-07-notes.md
（withheld：specs/plans/W-2026-10-01-auth/tasks.md，留在 working tree，Step 5-A 登記）
```

## Bad Example

- 這個例子是壞的，因為用 `.gitignore` 把該入庫的檔藏掉，還拿分組顆粒去跟別的 session 協調。

```md
`?? tasks/todo.md` → 加進 `.gitignore`；並通知另一個 session「我會拆 3 筆，第 2 筆先 land」。
```

# Rule 4 - 0-MR 有 withheld scope 時，每組 commit 前先跑 intersect（Step 4）

- Level: `MUST`

0-MR 有 withheld scope 時，**每個 group 的 `git commit --only` 之前 MUST** 先跑（gates.md § 0-MR step 6）：

```bash
node ~/offline/clade/vendor/scripts/commit-mr-gate.ts intersect --block <carrier X> [--block <carrier Y>] -- <files>
```

exit 1 → stdout 列的路徑落在 withheld scope，該 group **NEVER** commit；移出那些路徑後重跑，剩餘才 commit。

## Good Example

- 這個例子是好的，因為 exit 1 後移出命中的路徑再重跑。

```md
`commit-mr-gate.ts intersect --block tasks/x.md -- a.ts tasks/x.md` → exit 1、stdout `tasks/x.md`
→ 把它移出 group → 重跑 exit 0 → commit `a.ts`。
```

## Bad Example

- 這個例子是壞的，因為 exit 1 仍照原 pathspec commit。

```md
intersect exit 1 →「只是 carrier 檔，一起進沒關係」→ `git commit --only -- a.ts tasks/x.md`。
```

# Rule 5 - 每組用 `git commit --only -- <files>` 並驗 scope（Step 4）

- Level: `MUST`

對每個分組（用 `git commit --only -- <files>` 強制 limit scope，防別 session staged race — 詳見 `rules/core/commit.md` § Ad-hoc commit 必走 `git commit --only -- <paths>`）：

Co-author trailer 依本 repo 已核准的署名政策與實際參與者填寫；有可核對的名稱／email 才加入。沒有署名資料時省略 trailer，不把其他 runtime 的名稱或 email 當預設。下列一般與 deploy commit 範本共用此判準。

```bash
git commit --only -m "$(cat <<'EOF'
✨ feat: 功能描述

Via: /commit
EOF
)" -- <files>
git log -1 --oneline
git show --stat HEAD | tail -3   # MUST verify scope == expected files
```

Untracked file 例外：須先 `git add <untracked>` 再 `git commit --only -- <both-paths>` — scope 仍受 `--only` 過濾。

## Good Example

- 這個例子是好的，因為 commit 後核對了 changed files 數。

```md
`git commit --only -m "🐛 fix: 修正登入逾時…" -- server/auth/session.ts` → `git show --stat HEAD | tail -3` 顯示 1 file changed，符合預期。
```

## Bad Example

- 這個例子是壞的，因為裸 commit 會把 index 裡別 session 預 stage 的檔一起收進去，trailer 還套了別的 runtime 的署名。

```md
`git add src/a.ts && git commit -m "🐛 fix: 修正登入逾時"`（沒有 `--only`、沒有 pathspec），結尾加上手邊另一個 runtime 的 Co-Authored-By。
```

# Rule 6 - 受審基線 guard 與最後一組落地後的收尾（Step 4）

- Level: `MUST`

本次完整 0-A 無 Critical／Major 且 ledger 通過時，wrapper 才把有效 24 小時的 active
基線登記在本 worktree 的 git dir，綁定審查 session 與當次 commit lock；每次 verdict 都以 `STAGING_BASELINE:`
保留 immutable receipt。pre-commit hook 只驗真正 commit index 的 staged 子集，
及每個 staged entry 的內容與 mode 等於受審版本；不驗 worktree／HEAD 的逐路徑漂移，
未 staged 的 baseline 路徑再次改動不阻擋本組 commit。
post-commit 只移除該 session 已提交的受審路徑；其他 session 與無 session 的自動化 commit 不驗也不消耗此 guard。
審查 session 的身分來源同 gates.md § 0-A；全部來源缺席時不安裝 active guard，verdict 與 receipt 不受影響。
最後一組 commit 落地後，MUST 執行下列正常收尾，釋放未提交的外來 WIP 路徑；
commit lock 釋放或換代也會讓該次 guard 自動失效。缺 hook 或 helper 時先修接線，不以手動 subset 檢查代替。
取消、要提交修訂後的受審內容、到期或 post-commit 失敗時，依 gates.md § 0-A 的 `release --reason`
結束 active guard 並保留 closure receipt；原 approval 失效，修訂後須重審。

```bash
ACTIVE_REVIEW=$(git -C "$COMMIT_REPO" rev-parse --path-format=absolute --git-path clade-review-integrity.json)
if [ -e "$ACTIVE_REVIEW" ]; then
  COMMIT_RUNTIME="$COMMIT_RUNTIME" COMMIT_SESSION_ID="$COMMIT_SESSION_ID" \
    node "$CLADE_HOME/vendor/scripts/lib/review-integrity-scope.ts" complete \
      --repo "$COMMIT_REPO" --baseline "$ACTIVE_REVIEW" --reason 'all session commit groups landed'
fi
```

## Good Example

- 這個例子是好的，因為最後一組落地後跑了 `complete`，釋放未提交的外來 WIP 路徑。

```md
3 組 commit 都落地 → `$ACTIVE_REVIEW` 存在 → 跑 `review-integrity-scope.ts complete --reason 'all session commit groups landed'`。
```

## Bad Example

- 這個例子是壞的，因為缺 hook 時以手動比對代替，修訂後也沒重審。

```md
pre-commit hook 沒接上 →「我自己比一下 staged 子集就好」；審後又改了受審檔 → 直接 commit。
```
