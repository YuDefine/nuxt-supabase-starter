# Rule 1 - 分組輸入用 `git status --porcelain`（D3）

- Level: `MUST`

```bash
git status --porcelain          # 分組輸入的權威來源（含 tracked modified + untracked）
git diff --stat                 # 僅輔助看 tracked 改動規模；NEVER 當分組輸入唯一來源
```

`git diff --stat` **只列 tracked modified**，會漏掉 `??` 開頭的 untracked 非 ignored 檔。每次分組前自問：「`git status` 有沒有 `??` 開頭的行？沒被 `.gitignore` 覆蓋 = 必須納入分組。」

若 `.gitignore` 有變更：只新增 Clade 管理的 installation artifact／runtime state 條目可保留；其他變更回 D0-Scope 查歸屬與授權，**NEVER** 用 `git checkout .gitignore` 還原（會毀掉使用者的 WIP）。

## Good Example

- 這個例子是好的，因為 `??` 的 untracked 檔進了分組。

```md
`git status --porcelain` 有 ` M src/a.ts` 與 `?? docs/new.md` → 兩個都列入分組輸入。
```

## Bad Example

- 這個例子是壞的，因為只看 `git diff --stat`，untracked 檔被靜默丟掉。

```md
`git diff --stat` 只列 `src/a.ts` → 只 commit 它 → `docs/new.md` 留在 working tree 沒人管。
```

# Rule 2 - 依功能分組並輸出（D3）

- Level: `MUST`

依功能分組並輸出 `Group N: 描述／類型／檔案`；類型與開頭 emoji 見 `commitlint.config.ts`：

| Emoji | Type | Emoji | Type | Emoji | Type |
| --- | --- | --- | --- | --- | --- |
| ✨ | feat | 🐛 | fix | 🧹 | chore |
| 🔨 | refactor | 🧪 | test | 🎨 | style |
| 📝 | docs | 📦 | build | 👷 | ci |
| ⏪ | revert | 🚀 | deploy | 🎉 | init |

- **Untracked 非 ignored 檔（`??`）一律納入分組**，通常自成 `chore` group（語義明確屬於某 feat／fix group 除外）。
- 想把 `??` 檔加進 `.gitignore` 消掉時 **STOP**：先問是本來就該 ignore，還是在逃避 commit（見 [[wip-orphan-recovery]] § 反射性 gitignore 禁令）。
- D0-MR withheld scope 內的路徑不進任何 group，留在 working tree，並把這些路徑與原因列進 PR body 的「剩餘事項」（trunk-based 無 PR 則列進回報並交 `/handoff` 登記），**NEVER** 讓 withheld scope 無紀錄地消失。有 withheld scope 時，**每個 group 實際提交之前 MUST** 先跑 `node ~/offline/clade/vendor/scripts/commit-mr-gate.ts intersect --block <carrier> [--block <carrier>] -- <files>`；exit 1 → stdout 列的路徑落在 withheld scope，**NEVER** 提交，移出後重跑。
- 分組顆粒是內部決策：**NEVER** 對別的 session 宣告「我要拆幾筆、哪筆先 land」或拿它協調，對方要等的只有「land 了沒有」。

## Good Example

- 這個例子是好的，因為 untracked 檔自成 chore group，withheld 的路徑不進任何 group。

```md
### Group 1: 登入逾時修正
類型: fix
檔案: server/auth/session.ts

### Group 2: 新增工作筆記
類型: chore
檔案: tasks/2026-10-07-notes.md
（withheld：specs/plans/W-2026-10-01-auth/tasks.md，留在 working tree）
```

## Bad Example

- 這個例子是壞的，因為用 `.gitignore` 把該入庫的檔藏掉，還拿分組顆粒去跟別的 session 協調。

```md
`?? tasks/todo.md` → 加進 `.gitignore`；並通知另一個 session「我會拆 3 筆，第 2 筆先 land」。
```

# Rule 3 - 每組用 `git commit --only -- <files>` 並驗 scope（D3）

- Level: `MUST`

用 `git commit --only -- <files>` 強制 limit scope，防別 session staged race（見 `rules/core/commit.md` § Ad-hoc commit 必走 `git commit --only -- <paths>`）。**NEVER** `git add -A`、`git stash`、`git reset --hard`、`--force`、`--no-verify`。Co-author trailer 依本 repo 已核准的署名政策與實際參與者填寫，沒有署名資料就省略，不把其他 runtime 的名稱當預設。

```bash
git commit --only -m "$(cat <<'EOF'
✨ feat: 功能描述

Via: /commit
EOF
)" -- <files>
git log -1 --oneline
git show --stat HEAD | tail -3   # MUST verify scope == expected files
```

Untracked file 例外：須先 `git add <untracked>` 再 `git commit --only -- <both-paths>`。**NEVER** 把 `vendor/ledger/signals.jsonl` 的追加行帶進 commit。

## Good Example

- 這個例子是好的，因為 commit 後核對了 changed files 數。

```md
`git commit --only -m "🐛 fix: 修正登入逾時…" -- server/auth/session.ts` → `git show --stat HEAD | tail -3` 顯示 1 file changed，符合預期。
```

## Bad Example

- 這個例子是壞的，因為裸 commit 會把 index 裡別 session 預 stage 的檔一起收進去。

```md
`git add src/a.ts && git commit -m "🐛 fix: 修正登入逾時"`（沒有 `--only`、沒有 pathspec）。
```

# Rule 4 - D3：push、開非 draft PR、附意圖卡，然後停在 PR

- Level: `MUST`

最後一組 commit 落地後：

1. `git push -u origin <branch>`（**NEVER** `--force`；push 被拒回 D0 查原因）。
2. 開 PR（`gh pr create`）：body 開頭放 [品質檢查判準.md](品質檢查判準.md) Rule 2 的意圖卡，接著是變更摘要與剩餘事項。0-A 不接受 draft，所以 draft／ready 依誰在跑：
   - 一般使用者 session（`CLADE_DISPATCH_ID` 為空）：開 **非 draft** PR；已開成 draft 就 `gh pr ready`。
   - 被 coordinator 派出的 worker（`CLADE_DISPATCH_ID` 非空）：沿派工 brief，PR 維持既有 draft／ready 狀態，**NEVER** 自己 `gh pr ready`；ready 與 0-A 由主持者（`coordinator-ready.ts`）接手。
3. 回報 PR 號與 head SHA，**停在這裡**：CI-fast（D4）與 0-A（D5）平行跑，處置（D6）、CI-full（D7）、合入（D8）都不歸本 skill。**NEVER** 自己 merge、自己跑或派 0-A、自己宣告「CI 全綠」（test-lanes 在 0-A 通過前會 pending，那不是綠）。
4. HANDOFF 走 `/handoff`；Notion 與完成報告不在這裡。

trunk-based consumer 沒有 PR：D3 做到 commit 為止，要發版再走 SKILL.md 的 D9 條件步驟。無 PR 就沒有 D4 CI 與 D5 0-A 兜底，所以 **push main 前 MUST 先取得這些 commit 的 0-A `FINALIZE` verdict**（`claude-review-safe.sh`，規格見 [gates.md](../gates.md) § 0-A，交主持者或 attended 主線派審），Critical／Major 處置完才 push；沒有 verdict → push main 保持未完成，**NEVER** 憑「沒有 PR」略過。

commit 之後 working tree 對 HEAD 已沒有這段 diff，carrier 預設的 changeset（working tree 對 `HEAD`）會是空的或只剩無關 WIP——**MUST** 用快照把已 commit 的範圍呈現成 staged diff 再審（`--base` 是 push 前 `origin/main` 與 HEAD 的 merge-base；批次是 seal 的 `reviewed_base`）：

```bash
git -C "$COMMIT_REPO" fetch origin main
SNAP=$(node ~/offline/clade/vendor/scripts/review-snapshot.ts create --repo "$COMMIT_REPO" \
  --base "$(git -C "$COMMIT_REPO" merge-base HEAD origin/main)" --stage HEAD)
cd "$SNAP" && bash "$COMMIT_RESOURCE_DIR/scripts/claude-review-safe.sh" prepare xhigh
# 照 AGENT_CALL 派 commit-0a-reviewer → 跑 FINALIZE；之後不論結果 review-snapshot.ts remove "$SNAP"
```

**NEVER** 在 commit 後的工作區直接跑 `prepare`；changeset 為空時的 `No findings` 不是 verdict。D2 的 typecheck／affected 測試在這條路徑上也要完整跑完才 commit。

## Good Example

- 這個例子是好的，因為開非 draft PR、附意圖卡，回報後停手。

```md
`git push -u origin session/foo` → `gh pr create --title … --body-file body.md`（開頭是意圖卡）→ 回報「PR #123，head abc1234，CI 與 0-A 進行中」。
```

## Bad Example

- 這個例子是壞的，因為一般 session 開成 draft、自己宣告 CI 全綠還自己 merge。

```md
`gh pr create --draft` → test-lanes pending 時說「CI 全綠」→ `gh pr merge`。
```

# Rule 5 - 受審基線 guard 與最後一組落地後的收尾（D3）

- Level: `MUST`

0-A 無 Critical／Major 且 ledger 通過時，wrapper 才在 worktree 的 git dir 登記 24 小時有效的 active 基線；pre-commit hook 只驗 staged 子集的內容／mode 等於受審版本，post-commit 移除已提交的受審路徑。取消、要提交修訂後的內容、到期或 post-commit 失敗時，依 [gates.md](../gates.md) § 0-A 的 `release --reason` 結束 guard，修訂後須重審。

最後一組 commit 落地後，若有 active 基線 MUST 跑下列收尾；缺 hook 或 helper 時先修接線，**NEVER** 以手動 subset 檢查代替：

```bash
ACTIVE_REVIEW=$(git -C "$COMMIT_REPO" rev-parse --path-format=absolute --git-path clade-review-integrity.json)
if [ -e "$ACTIVE_REVIEW" ]; then
  COMMIT_RUNTIME="$COMMIT_RUNTIME" COMMIT_SESSION_ID="$COMMIT_SESSION_ID" \
    node "$CLADE_HOME/vendor/scripts/lib/review-integrity-scope.ts" complete \
      --repo "$COMMIT_REPO" --baseline "$ACTIVE_REVIEW" --reason 'all session commit groups landed'
fi
```

## Good Example

- 這個例子是好的，因為最後一組落地後跑了 `complete`，釋放未提交的外來 WIP 路徑。

```md
3 組 commit 都落地 → `$ACTIVE_REVIEW` 存在 → 跑 `review-integrity-scope.ts complete --reason 'all session commit groups landed'`。
```

## Bad Example

- 這個例子是壞的，因為缺 hook 時以手動比對代替，修訂後也沒重審。

```md
pre-commit hook 沒接上 →「我自己比一下 staged 子集就好」；審後又改了受審檔 → 直接 commit。
```
