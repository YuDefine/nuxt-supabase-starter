# Rule 1 - D2：作者自驗只跑本機 affected，其餘交給 PR 路徑一次

- Level: `MUST`

D2 只確認 PR 不是明顯紅的，不重跑整條品質鏈；能平行的就平行：

1. **typecheck ＋ lint**：repo 有 `ci-fast` 入口就跑它（D4 CI-fast 跑同一支，本機綠＝CI-fast 綠）；沒有就跑 `pnpm check`（clade：`node node_modules/tsrs/bin/tsrs -p tsconfig.clade.json --noEmit && node node_modules/tsrs/bin/tsrs -p tsconfig.vendor.json --noEmit`，加 `vp check`）。
2. **affected 測試**：`test:affected` 有則跑它；沒有就跑 diff 相關的測試檔，**NEVER** 本機跑不帶 lane 的整套（hook／gate 會擋），廣範圍回歸交 PR CI（D7）。repo 的 `scripts.verify` 指向 `gate-receipt-run-all` 時走 `pnpm verify`，沿用 24 小時內的本機收據；`CI=true` 時一律實跑。
3. **doctor**：repo 有 `scripts.doctor` 就本機 **MUST** 跑 `pnpm run doctor`（**MUST** 帶 `run`，裸 `pnpm doctor` 會 silent exit 0），100/100＋0 warnings 才進 D3，既有 warning 也要修（`commit.detail.md` rule-invariant）；CI 的 `doctor` job 是再兜一次，**NEVER** 拿它代替本機這一跑。
4. **simplify**（可選）：改完才算最終內容；之後再改，前面的證據都要重跑。

全綠才進 D3。紅燈先修再重跑受影響的項，**NEVER** 帶紅燈開 PR 指望 CI 擋。

## Good Example

- 這個例子是好的，因為只跑受影響的測試與型別檢查，全量回歸交給 PR CI。

```md
改 `vendor/scripts/foo.ts` → `ci-fast` 綠、`test:affected` 綠 → 進 D3；整套回歸看 PR CI。
```

## Bad Example

- 這個例子是壞的，因為在本機重跑整套，又帶紅燈開 PR。

```md
本機 `pnpm test` 整套跑 40 分鐘；typecheck 紅 →「CI 會擋」→ 照樣開 PR。
```

# Rule 2 - D2：在 PR body 填意圖卡，0-A 以它為審查輸入

- Level: `MUST`

PR body 開頭 **MUST** 有意圖卡，四欄各一到三行，貼不出內容就寫「無」並說明原因：

```md
## 意圖卡
- Intent：這張 PR 要解決什麼、為什麼現在做
- Risk：最可能壞的路徑與波及面（Tier 3 路徑、migration、對外契約要點名）
- Test evidence：D2 實跑的命令與輸出摘尾；本機沒跑的項目與原因
- Spec：對應的 plan／spec／TD 連結（沒有就寫「無」）
```

意圖卡是 0-A reviewer 的輸入；Test evidence 只寫實際跑過的，**NEVER** 沒跑卻寫通過。

trunk-based 沒有 PR body：意圖卡改寫進最後一組 commit 的 message body（`## 意圖卡` 段），push main 前的 0-A（[分組與提交判準.md](分組與提交判準.md) Rule 4）與 D9 發版回報都讀這一份，**NEVER** 因為沒有 PR 就省略。

## Good Example

- 這個例子是好的，因為每欄都有具體內容，沒跑的項目明說。

```md
- Intent：修 lane-plan 白算一次（TD-xxx）
- Risk：動到 `validate.yml` 選檔順序；波及所有 PR run
- Test evidence：`ci-fast` 綠；`test:affected` 3 檔綠；整套未跑，交 PR CI
- Spec：W-2026-11-05-commit-ci-flow-redesign
```

## Bad Example

- 這個例子是壞的，因為意圖空白，測試證據是沒跑過的宣稱。

```md
- Intent：修一些東西
- Test evidence：都過了
```

# Rule 3 - 0-A 在 PR 之後：reviewer 只有一席，本 skill 不跑也不補位（trunk-based 見分組與提交 Rule 4）

- Level: `NEVER`

語意審查（0-A）是 D5，PR 開出後由 coordinator 依 `claude-review-safe.sh` 派審。唯一合格 reviewer：fresh-context Claude Opus 5.5（effort: xhigh），`claude-review-safe.sh`；沒有備援席。Opus 不可用 → 該 gate 保持未完成，**NEVER** 以主線自審、其他模型或本機自己讀一遍代替；被派出的 worker **NEVER** 自跑或另派 0-A。verdict 只認 finalize。完整規格見 [review-policy.md](../review-policy.md)、[gates.md](../gates.md) § 0-A。

## Good Example

- 這個例子是好的，因為 PR 開出後就交給 0-A 流程，不自審。

```md
D3 開 PR 完成 → 回報 PR 號 → 0-A 由主持者派 → 不自己讀一輪頂著。
```

## Bad Example

- 這個例子是壞的，因為 Opus 不可用時改用別的 reviewer 補位。

```md
Opus 額度用完 →「先讓主線自己審一輪頂著」→ 記 0-A 通過。
```

# Rule 4 - 條件觸發的自驗：命中才讀 gates.md 對應 §

- Level: `MUST`

命中才讀對應 §，沒命中在意圖卡標「未觸發＋原因」：

- **Tier 3 路徑**（`rules/review-tiers.md`，路徑相對 `$COMMIT_RESOURCE_DIR`；attended 與 unattended 一視同仁）：讀 [gates.md](../gates.md) § 0-S，依序跑 0-S.1 確定性掃描與 0-S.2 `/security-review`；unattended 也不略過，0-S.2 無法執行時 gate 保持未完成。secret 掃描另由 D1 hook 與 D4 CI 負責。
- **UI 檔變更且 repo 已採用 impeccable**：讀 [gates.md](../gates.md) § 0-B.1 跑 detector，處置證據寫進意圖卡 Test evidence。
- **diff 觸及 docs／rules／snippets／audit／業務碼／pitfall**：讀 [gates.md](../gates.md) § 0-D 對齊文件。
- **diff 觸及 entry point**（`server/{api,routes,middleware,tasks}/`、pages）：CI 的 `evlog-map-gate` 兜底；本機要預檢時讀 [gates.md](../gates.md) § 0-E。

fast-path 已刪除，不自行判「太小免驗」；純測試／文件免審由 D4 判斷。

## Good Example

- 這個例子是好的，因為只讀命中的 §，其餘標未觸發。

```md
diff 只有 `server/utils/a.ts` → 不命中 Tier 3、無 UI → 意圖卡寫「0-S／0-B：未觸發（無敏感路徑、無 UI）」。
```

## Bad Example

- 這個例子是壞的，因為單行 `.ts` 變更也自行判免驗。

```md
只改 `utils/date.ts` 1 行 →「才一行」→ 跳過 D2。
```
