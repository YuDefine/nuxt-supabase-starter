# Rule 1 - D0-Lock：在多 session 共用樹提交，先取得 commit lock

- Level: `MUST`
- 觸發：要在 main checkout 或 batch integration 區（可能有他 session 寫入）提交。自己專屬的 worktree 不取鎖，直接進 D0-Scope。

以 `COMMIT_TARGET_ROOT` 保存工作區絕對路徑；acquire／release 用同一組 owner 與路徑。**MUST 先完整讀 [runtime-lifecycle.md](../runtime-lifecycle.md)**（work id、runtime／session、acquire、renew、背景工作收回、退出與中斷恢復），再 acquire 並保存 owner receipt。

取得失敗就停在本步並聯絡 receipt 的具名持有者，無通道則回報缺口。**NEVER** 自行 `rm` 鎖檔。Timeout、失聯與 PID 消失都不能授權接管。

## Good Example

- 這個例子是好的，因為取鎖失敗時停在本步並聯絡具名持有者。

```md
acquire 失敗，receipt 指出持有者是 session `ab12` → 問它還要多久 → 等它 release 後重新 acquire。
```

## Bad Example

- 這個例子是壞的，因為以 PID 消失為由自行刪鎖檔接管。

```md
acquire 失敗 →「持有者的 PID 已經不在了」→ `rm .claude/.commit.lock` → 繼續。
```

# Rule 2 - Final：最後一步收回工作並釋放 lock

- Level: `MUST`
- 觸發：本次有取鎖。

依 [runtime-lifecycle.md](../runtime-lifecycle.md)「背景工作與退出」收回本 ceremony 的工作，再用原 owner token release 並保留 receipt；完成、失敗、中止同一條路。仍有會改檔的工作未確認停止，或 owner 已變，保留鎖與證據並回報接手責任，**NEVER** 以 timeout 自動清鎖。

## Good Example

- 這個例子是好的，因為 gate 失敗也走同一條退出路徑，且留下 release receipt。

```md
自驗失敗決定中止 → 收回背景 handle → 用原 owner token release → 回報附 release receipt。
```

## Bad Example

- 這個例子是壞的，因為背景 writer 還沒確認停止就宣稱已釋放。

```md
背景 fix worker 還在跑 → 等 60 秒沒回應 →「逾時，視為結束」→ release 並回報「已安全退出」。
```
