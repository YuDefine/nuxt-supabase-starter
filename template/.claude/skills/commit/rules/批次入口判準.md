政策見已投影的 `commit` 與 `commit.detail` 規約；commit 類型 / emoji 表在 `分組與提交判準.md` Rule 2。

# Rule 1 - D0：每次進入 `/commit` 先跑 batch status，帶 `--workflow`

- Level: `MUST`

**每次**先跑 `wt-helper batch status --workflow <已解析 workflow_model>`（consumer：`scripts/wt-helper.ts`；clade：`vendor/scripts/wt-helper.ts`）。**NEVER** 省略 `--workflow` 讓 CLI 默認 PR 制。使用者主動要求的 trigger 是 `manual`，無最低件數；自動收割用 `auto`：`pr-merge-based` 1 個 distinct work id 即準備獨立 PR，`trunk-based` 要 4 個才啟動。Checkpoint 與 draft 不是 `/commit`，不得在其上啟動自驗或發版。

## Good Example

- 這個例子是好的，因為帶了已解析的 workflow model，trigger 也照來源選。

```md
使用者說「commit 一下」→ `node scripts/wt-helper.ts batch status --trigger manual --workflow pr-merge-based`
→ 無就緒成員、無 active batch → 走普通 `/commit`。
```

## Bad Example

- 這個例子是壞的，因為把 checkpoint 當成 `/commit` 啟動自驗與發版。

```md
`wt-helper batch status` → 看到一筆 checkpoint → 直接開始自驗並發版。
```

# Rule 2 - 依 batch status 的 `route` 欄分流，`cleanupPending` 另外疊加

- Level: `MUST`
- `route`（主分流）與 `cleanupPending`（只欠 cleanup 的批 id）由 `wt-batch.ts` 的 `batchEntryRoute` 算。worker 完成或 CI 通知喚醒同一個 coordinator 續跑本入口，**NEVER** 請 Charles 代觸發；worker 完成 ≠ landing，核對遠端 SHA 後才匯入並 `batch ready`。

評估：first-match；以上皆非 → B*

| id | `route` | 動作 |
| --- | --- | --- |
| B1 | `resume-active` | 讀 [batch.md](../batch.md)，接續在途批，在整合區跑 D2–D3 |
| B2 | `prepare` | 讀 [batch.md](../batch.md)，`batch prepare` 後在整合區跑 D2–D3 |
| B3 | `return-to-dev` | 未達自動門檻：返回開發，**不取得 commit lock** |
| B4 | `plain-commit` | 走普通 `/commit`，當前 WIP 照常全包 |
| B* | 其他值、欄位缺、指令非 0 | STOP，回報 `batch status` 原始輸出 |

評估：all-match（逐條檢查，命中就套用）

| id | 條件 | 約束 |
| --- | --- | --- |
| BC1 | `cleanupPending` 非空 | 逐批 `batch cleanup --batch <id>`，不重跑自驗 |
| BC2 | B1、B2 | D3 後 seal／land，正式落地才算完成。seal 的 `gates.review` 依 workflow 填：PR 制填 `not-applicable`，reason 寫「0-A 在 PR 上由 D5 跑，merge-queue 合入前驗 verdict」；trunk-based **MUST** 先照 [分組與提交判準.md](分組與提交判準.md) Rule 4 對整批已 commit 範圍跑 0-A，以 `FINALIZE` 產物填 `passed`，**NEVER** 填 `not-applicable`（trunk 沒有 PR 兜底，land 到 local main 前就要有受審證據） |
| BC3 | B1、B2 且 PR 制要合併 | 合併前跑 `deploy-trigger-check.ts`；`confirmed-push-main` 且 production 由 main 觸發 → 停止 unattended merge |

## Good Example

- 這個例子是好的，因為先接續隔離整合區，並在 merge 前判了部署觸發。

```md
`route=prepare`（1 個 ready 成員）→ 讀 `batch.md` → 在 integration path 跑 D2–D3 → merge 前跑 `deploy-trigger-check.ts`。
```

## Bad Example

- 這個例子是壞的，因為未達自動門檻仍取了 commit lock，已落地只欠 cleanup 的批次又重跑自驗。

```md
`route=return-to-dev`（trunk-based 只有 2 個 distinct work id）→ 照樣 acquire lock；`cleanupPending` 有一批 → 再跑一輪自驗才清理。
```
