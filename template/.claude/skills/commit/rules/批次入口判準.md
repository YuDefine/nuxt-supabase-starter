政策與禁止事項見當前 runtime 已投影的 `commit` 與 `commit.detail` 規約。本 skill 的 `SKILL.md` 定義執行順序，commit 類型 / emoji 對照表在 `分組與提交判準.md` Rule 3。

# Rule 1 - 每次進入 `/commit` 先跑 batch status，帶 `--workflow`

- Level: `MUST`
- 觸發：Step 0-Batch（取得 commit lock 前）。

**每次**進入 `/commit` 先跑 `wt-helper batch status --workflow <已解析 workflow_model>`（consumer：`scripts/wt-helper.ts`；clade：`vendor/scripts/wt-helper.ts`）。**NEVER** 省略 `--workflow` 讓 CLI 默認 PR 制。使用者主動要求的 trigger 是 `manual`，無最低件數；自動收割用 `auto`：`pr-merge-based` 1 個 distinct work id 即準備獨立 PR，`trunk-based` 仍要 4 個才啟動。dependency／drained／stop 可提前結批。Checkpoint 與 draft 都不是 `/commit`，不得在 checkpoint 或 draft 啟動完整品質鏈或發版。Draft 不是 ready。

## Good Example

- 這個例子是好的，因為它帶了已解析的 workflow model，trigger 也照來源選。

```md
使用者說「commit 一下」→ `node scripts/wt-helper.ts batch status --trigger manual --workflow pr-merge-based`
→ 無就緒成員、無 active batch → 走普通 `/commit`。
```

## Bad Example

- 這個例子是壞的，因為省略 `--workflow` 讓 CLI 默認 PR 制，又把 checkpoint 當成 `/commit` 啟動品質鏈。

```md
`wt-helper batch status` → 看到一筆 checkpoint → 直接開始跑 0-A 與發版。
```

# Rule 2 - worker 完成與 CI 通知喚醒同一個 coordinator，worker 完成不等於 landing

- Level: `MUST`

Cloud／worker completion 與該 PR 的 CI 通知 MUST 喚醒**同一 coordinator** 續跑本入口，不請 Charles 代觸發。integration 模式的切片沒有自己的 PR／CI：喚醒 coordinator 的是 worker 的 completion，coordinator 併入 `integration/<work-id>` 後，整件工作只對 `main` 跑一次本入口。Coordinator 核對遠端 SHA 後把 commits／證據匯入本機受管來源，再 `batch ready`。Worker 完成 ≠ landing。

## Good Example

- 這個例子是好的，因為 coordinator 核對遠端 SHA 後才把來源匯入並標 ready。

```md
收到 worker completion → 核對 PR head SHA 與遠端一致 → 匯入本機受管來源 → `batch ready` → 續跑本入口。
```

## Bad Example

- 這個例子是壞的，因為把 worker 完成當成已落地，還請使用者代為觸發。

```md
worker 回報完成 → 回覆「已落地，請你再下一次 /commit」。
```

# Rule 3 - 有就緒成員或待續批次先讀 batch.md，沒有才走普通 `/commit`

- Level: `MUST`

有就緒成員或待續跑／待清理批次時 **MUST 讀 [batch.md](../batch.md)**，先準備或接續隔離整合區，再在該區跑本 skill 的完整 Step 0–5；Step 5 後 seal／land，正式落地才進 Step 6。PR 制合併前 MUST 先跑 `deploy-trigger-check.ts`（與 Step 6-Gate 同一支），判定 main 更新會不會未授權部署 production。`confirmed-push-main` 且 production 由 main 觸發 → 停止 unattended merge。Unattended 預先核准 `release=manual` 時 Step 6 停在 6-B（已 land、未發版）。已落地只欠 cleanup 的批次直接清理，不重跑品質鏈。沒有就緒成員且沒有 active batch 時走普通 `/commit`，當前 WIP 照常全包。未達自動門檻時返回開發，**不取得 commit lock**。

## Good Example

- 這個例子是好的，因為它先接續隔離整合區，並在 merge 前判了部署觸發。

```md
status 顯示 1 個 ready 成員 → 讀 `batch.md` → 在 integration path 跑 Step 0–5 → merge 前跑 `deploy-trigger-check.ts`
→ `confirmed-push-main` 且 production 由 main 觸發 → 停止 unattended merge 並回報。
```

## Bad Example

- 這個例子是壞的，因為未達自動門檻仍取了 commit lock，已落地只欠 cleanup 的批次又重跑品質鏈。

```md
trunk-based 只有 2 個 distinct work id → 照樣 acquire lock 跑 Step 0；另一批已 landed → 再跑一輪 0-A 才清理。
```
