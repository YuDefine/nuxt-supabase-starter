# Rule 1 - Step 6 的第一步是判定發版觸發形狀

- Level: `MUST`

Step 6 會建立並推送 release tag。**對 production 由 tag 觸發的 repo，那一步等於 agent 自行決定部署 production**（含跑 production migration）。因此 **MUST** 先判定本 repo 的發版觸發形狀，**NEVER** 直接進 Step 6 的 bump / tag。Unattended coordinator 在 merge **前**就跑同一支 `deploy-trigger-check.ts`；本步驟只處理已 land 之後的發版分流。預先核准 `release=manual` 時停在 6-B，記「已 land、未發版」，不逐張追問 Charles 是否發版。

```bash
node scripts/deploy-trigger-check.ts
```

它讀 `.claude/consumer-meta.json` 的宣告，**同時**從 `.github/workflows/` 推導實際觸發條件，兩邊一致才給放行。判定看 `verdict=` 那一行：

| `verdict=` | 意義 | Step 6 走哪條 |
| --- | --- | --- |
| `confirmed-push-main` | 宣告 `push-main`，且 production deploy workflow 確實由 main push 觸發 —— 不建 tag 也照樣部署，攔 tag 沒有保護作用 | **走 6-A（現行完整流程）** |
| `needs-approval` | 其餘全部：`tag-v` / `manual`、宣告缺漏、宣告與 workflow 不符、workflow 推不出單一結論、腳本不存在 | **走 6-B（不建 tag；push main 本身另判授權）** |

**NEVER 因為「這個 repo 我記得是 push-main」就跳過這條查詢。**推錯的方向是不可逆的（tag 一推出去 production 就開始跑）。

## Good Example

- 這個例子是好的，因為依 `verdict=` 選分支。

```md
`node scripts/deploy-trigger-check.ts` → `verdict=needs-approval status=confirmed derived=tag-v` → 走 6-B。
```

## Bad Example

- 這個例子是壞的，因為憑記憶跳過查詢。

```md
「這個 repo 我記得是 push-main」→ 直接 `pnpm version minor` 並打 tag。
```

# Rule 2 - 放行條件是「宣告與 workflow 一致」；腳本不存在走 6-B

- Level: `MUST`

**放行條件是「宣告與 workflow 一致」，不是「宣告寫了 push-main」。** 這個 gate 曾經只讀宣告，而宣告是手寫的：某 consumer 宣告 `push-main`、實際 `push: tags: ['*']`，於是拿到 6-A —— 沒有任何一步會講出這件事，2026-08-22 靠人工 grep workflow 才發現。現在推導失敗、宣告與現實矛盾一律 fail-closed 到 6-B，**宣告錯誤換不到寬鬆分支**。

`scripts/deploy-trigger-check.ts` 不存在（consumer 尚未收到該次散播）時 **MUST 走 6-B**，**NEVER** 退回舊的「只讀宣告」查法——那正是這條 gate 要取代的東西。

## Good Example

- 這個例子是好的，因為腳本不存在時 fail-closed。

```md
`scripts/deploy-trigger-check.ts` 不存在 → 走 6-B，報告註明「consumer 尚未收到該次散播」。
```

## Bad Example

- 這個例子是壞的，因為退回只讀宣告的舊查法。

```md
腳本不存在 → 讀 `.claude/consumer-meta.json` 寫 `push-main` → 走 6-A。
```

# Rule 3 - `status=` 的 finding 列進完成報告，不在本次順手改

- Level: `NEVER`

> `status=` 那一行同時是 finding 來源：`undeclared`（缺 `deploy.deployTrigger`）、`mismatch`（宣告與 workflow 矛盾）、`unconfirmable`（`derived=ambiguous`：deploy workflow 掛了 ≥2 種觸發——分散在不同 workflow 時，宣告要填 **production** 的那個；同一個檔案裡 production job 分不出來時 detail 會寫 `changing the declaration will not help`，改宣告救不了，要拆檔或替 job 加 `environment:` ＋ ref 的 `if:`；或 `derived=none`：根本找不到 deploy workflow——後者不是宣告寫錯，是沒有東西可宣告）。**列進 Step 7 完成報告**，但 **NEVER** 在本次 `/commit` 順手改它——那是獨立的宣告修正，要單獨走。

## Good Example

- 這個例子是好的，因為 finding 進了報告，宣告修正另外走。

```md
`status=undeclared` → Step 7 報告列 finding「缺 deploy.deployTrigger」→ 本次不改宣告。
```

## Bad Example

- 這個例子是壞的，因為在本次 `/commit` 順手改宣告換取 6-A。

```md
`status=mismatch` → 把 `consumer-meta.json` 改成跟 workflow 一樣 → 重跑拿到 `confirmed-push-main`。
```
