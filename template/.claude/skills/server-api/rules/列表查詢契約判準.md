# 列表查詢契約判準

> 讀取時機：`server-api` SKILL.md Phase 2 step 2，要新增或修改列表、搜尋、聚合端點時。排序欄位 allowlist 與 id tie-breaker 在 `rules/API慣例判準.md` Rule 5，本檔不重述。

# Rule 1 - 列表 query 固定五個參數，pageSize 夾上限，回應帶完整分頁資訊

- Level: `MUST`
- 列表端點的 query schema 只用這五個參數名：`page`、`pageSize`、`sortBy`／`sortDir`（規則見 `API慣例判準.md` Rule 5）、`search`、`filters`（Rule 2）。不需要的可以不收，但**NEVER** 另取 `limit`／`offset`／`per_page` 等同義名。
- `page` 從 1 起算；`pageSize` 的預設值與上限以 Zod `.default()`／`.max()` 寫在 query schema，數字照 runtime 規約 `api-patterns`，它沒規定時用預設 50、上限 200。**NEVER** 只在前端限制、**NEVER** 讓沒帶 `pageSize` 等於不設上限。
- 回應的分頁資訊固定為 `page`、`pageSize`、`totalCount`、`totalPages` 四個欄位，放進 runtime 規約 `api-patterns` 宣告的 envelope 分頁位置（例如 `{ data, pagination }`）；envelope 外層形狀照 `api-patterns`，本規則只定這四個欄位。
- 資料查詢與 count 查詢用同一組篩選條件、並行執行（`Promise.all`），**NEVER** 先查資料再循序查 count。

## Good Example

- 這個例子是好的，因為參數名固定、pageSize 有上限，count 與資料共用條件並行查。

```ts
// shared/schemas/order.ts
export const listOrdersQuerySchema = z.object({
  page: z.coerce.number().int().min(1).default(1),
  pageSize: z.coerce.number().int().min(1).max(200).default(50),
  sortBy: z.enum(['id', 'created_at']).default('id'),
  sortDir: z.enum(['asc', 'desc']).default('asc'),
  search: z.string().trim().max(100).optional(),
  filters: z.string().max(4000).optional(),
}).strict()

// server/api/v1/orders/index.get.ts
const q = await getValidatedQuery(event, listOrdersQuerySchema.parse)
const where = buildOrderWhere(q)
const [rows, totalCount] = await Promise.all([findOrders(where, q), countOrders(where)])
return { data: rows, pagination: { page: q.page, pageSize: q.pageSize, totalCount, totalPages: Math.ceil(totalCount / q.pageSize) } }
```

## Bad Example

- 這個例子是壞的，因為 `limit` 沒有上限、回應沒有總數，client 只能猜還有沒有下一頁。

```ts
const { limit = 1000, offset = 0 } = getQuery(event)
return { data: await findOrders({ limit: Number(limit), offset: Number(offset) }) }
```

# Rule 2 - 可組合篩選是有限結構的樹，欄位與運算子都走 server allowlist，解析失敗回 400

- Level: `MUST`
- 篩選條件以單一 `filters` query 參數傳遞，內容是 URL-encoded JSON 樹：group 節點 `{ op: 'and' | 'or', children: [...] }`，condition 節點 `{ field, operator, value }`。
- `operator` 是 Zod `z.enum` 列舉；`field` 是 client 端的欄位鍵，server 以 allowlist 對照表映射成實際 column，**NEVER** 把 client 傳來的字串直接當 column 名或拼進 SQL。
- 樹的深度與節點數要設上限（例如深度 3、條件 20 個），超過就拒絕。
- fail-closed：JSON 解析失敗、結構不合 schema、未知 `field`、未知 `operator`、`value` 型別不符，一律回 400 並在錯誤碼指出是哪一類；**NEVER** 靜默丟掉該條件或當成「沒有篩選」回完整列表——UI 顯示已套用篩選、資料卻是全量，比報錯更危險。

## Good Example

- 這個例子是好的，因為欄位只經對照表映射，任何對不上的輸入都回 400。

```ts
const FILTER_FIELDS = { status: orders.status, createdAt: orders.createdAt } as const
const conditionSchema = z.object({
  field: z.enum(Object.keys(FILTER_FIELDS) as [keyof typeof FILTER_FIELDS]),
  operator: z.enum(['eq', 'neq', 'gt', 'lt', 'contains', 'in']),
  value: z.union([z.string(), z.number(), z.array(z.string())]),
})

function parseFilters(raw: string | undefined) {
  if (!raw) return undefined
  let tree: unknown
  try { tree = JSON.parse(raw) }
  catch { throw createError({ statusCode: 400, data: { code: 'FILTERS_INVALID_JSON' } }) }
  const parsed = filterTreeSchema.safeParse(tree)
  if (!parsed.success) throw createError({ statusCode: 400, data: { code: 'FILTERS_INVALID' } })
  return parsed.data
}
```

## Bad Example

- 這個例子是壞的，因為解析失敗時回傳 undefined，handler 就照「無篩選」回出全部資料；欄位名也直接進了查詢。

```ts
function parseFilters(raw?: string) {
  try { return JSON.parse(raw ?? '') } catch { return undefined }
}
const where = sql.raw(`${cond.field} = '${cond.value}'`)
```

# Rule 3 - LIKE／ILIKE 的使用者輸入先跳脫萬用字元

- Level: `MUST`
- 任何把使用者輸入放進 `LIKE`／`ILIKE` 樣式的查詢（Drizzle `like()`／`ilike()`、raw SQL、PostgREST `.ilike`），在加上前後 `%` 之前 **MUST** 先把 `\`、`%`、`_` 跳脫成 `\\`、`\%`、`\_`；SQLite／D1 要同時寫 `ESCAPE '\'`。
- 走 PostgREST `.or()`／`.ilike` 的 consumer 若已安裝 evlog 規約的 `sanitizePostgrestSearch()`，用它即可（它另外處理 `,` `.` `(` `)` 的 filter 注入），不另寫一份。
- 理由：沒跳脫時使用者打 `%` 會變成全表比對，`_` 會配對任意字元，搜尋結果與使用者輸入的字面不符，也會讓昂貴查詢可被輕易觸發。

## Good Example

- 這個例子是好的，因為使用者輸入的萬用字元先被跳脫，只保留外層的 `%`。

```ts
const escapeLike = (s: string) => s.replace(/[\\%_]/g, ch => `\\${ch}`)
const pattern = `%${escapeLike(q.search)}%`
const rows = await db.select().from(users).where(sql`${users.name} LIKE ${pattern} ESCAPE '\\'`)
```

## Bad Example

- 這個例子是壞的，因為使用者輸入 `%` 就等於沒有搜尋條件。

```ts
const rows = await db.select().from(users).where(like(users.name, `%${q.search}%`))
```

# Rule 4 - 聚合端點的運算、時間粒度與欄位都是列舉，錯誤不回原始訊息

- Level: `MUST`
- 聚合端點（count／sum／avg／min／max、時間分桶）的 `op` 與 `interval` 以 `z.enum` 限定；`field` 與 `groupBy` 只能是該資源已宣告可聚合的欄位（server 端對照表），**NEVER** 接受任意欄位名。
- 對數值欄位才允許 `sum`／`avg`；對不上型別就回 400。
- 查詢失敗時照 `api-patterns` 的錯誤處理回穩定錯誤碼，**NEVER** 把 DB 或 driver 的原始 `message` 傳回 client（會洩漏表名、欄位與查詢結構）。

## Good Example

- 這個例子是好的，因為三個維度都經列舉或對照表，錯誤回的是穩定錯誤碼。

```ts
const AGG_FIELDS = { amount: { column: orders.amount, numeric: true }, status: { column: orders.status, numeric: false } } as const
const aggQuerySchema = z.object({
  op: z.enum(['count', 'sum', 'avg']),
  field: z.enum(['amount', 'status']),
  groupBy: z.enum(['status']).optional(),
  interval: z.enum(['day', 'week', 'month']).optional(),
}).strict()
```

## Bad Example

- 這個例子是壞的，因為欄位名直接拼進 SQL，失敗時又把原始錯誤訊息回給 client。

```ts
try { return await db.run(sql.raw(`SELECT ${q.op}(${q.field}) FROM orders GROUP BY ${q.groupBy}`)) }
catch (e) { throw createError({ statusCode: 500, message: (e as Error).message }) }
```

# Rule 5 - 全域搜尋回分段結果，每段用 limit+1 判斷還有沒有更多

- Level: `MUST`
- 跨資源的全域搜尋（command palette、頂部搜尋框）回應固定為 `{ query, sections, totalCount, tookMs }`；每個 section 是 `{ key, label, href, icon, items, hasMore }`，`href` 指向該資源完整列表頁並帶同一個搜尋字串。
- `q` 長度 1–100 字（trim 後），每段 `limit` 上限 8；每段實際查 `limit + 1` 筆，多出的那筆只用來設 `hasMore: true`，回傳時截回 `limit` 筆，**NEVER** 為了 `hasMore` 另跑 count。
- 每個 section 套用使用者對該資源的讀取權限；沒有權限的資源整段不出現，**NEVER** 回空 section 暗示資源存在。
- 搜尋字串照 Rule 3 跳脫。

## Good Example

- 這個例子是好的，因為多查一筆就能判斷 hasMore，不必另外 count。

```ts
const rows = await searchOrders(pattern, limit + 1)
const section = { key: 'orders', label: '訂單', href: `/orders?search=${encodeURIComponent(q)}`, icon: 'i-lucide-receipt', items: rows.slice(0, limit), hasMore: rows.length > limit }
```

## Bad Example

- 這個例子是壞的，因為每段都多跑一次 count，且 q 沒有長度限制。

```ts
const [items, total] = await Promise.all([searchOrders(q, 8), countOrders(q)])
return { orders: items, ordersHasMore: total > 8 }
```
