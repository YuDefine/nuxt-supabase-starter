
# Rule 1 - 分組前 MUST 先查證每題前提，過時與重複的題另成「建議寫掉」組

- Level: `MUST`
- 佇列常混著前提已消失的題：問「要不要合入」的 PR 早已合入、同一件事被問了兩次、Charles 已在網頁或別的 session 答過、`flow pending` 帶 `⏳ 疑似過時` 子行的題。直接分組會讓 Charles 對過時的題重新做決定。
- 分組前逐題查證：PR 狀態（`gh pr view`）、同一 repo 同一件事的其他題、spine 上的舊答案（`flow answers --json`，**NEVER** 加 `--claim`）、`⏳` 子行給的證據。
- 查證屬實的題放進「建議寫掉」組，每題附一句證據；已有舊答案的題建議「照舊答案落檔」並引用舊答案原文。
- 寫掉 MUST 等 Charles 同意（回「寫掉」「照建議」或 `/sg` 都算），**NEVER** 先寫掉再告知；寫掉後重跑 `flow pending` 確認那題消失。

## Good Example

- 這個例子是好的，因為重複與過時的題都附了查證證據，另成一組，等 Charles 點頭才動。

```md
D. 建議寫掉（2 題）：這兩題問的事已經發生或已經答過
  - Q12 [repo-a] 要不要人工合入 #549：你剛在網頁答的「#549 由誰合入」是同一件事，那題已有答案
  - Q11 [repo-b] KPI 測試 commit 要不要放行：那筆 commit（e0e26ce06）已在 repo-b 的 main 上
  回「D 寫掉」我就寫掉並重跑佇列確認。
```

## Bad Example

- 這個例子是壞的，因為沒查證就把過時題當一般題列給 Charles 重新決定，或沒問就先寫掉。

```md
  - Q11 [repo-b] KPI 測試 commit 要不要放行？ A. 放行 B. 等 doctor 修好
（Q12 看起來重複，我已經先寫掉了。）
```

# Rule 2 - 分組依「怎麼最快消化」排，每組一句話說在決定什麼並給建議

- Level: `MUST`
- 分組軸（`flow pending` 每一桶的每一列都恰好進一組；軸 1–5 只收有 `Qn` 的題，命中多條時取排在前面的；軸 6、7 依 `flow pending` 的桶別直接歸組，不再套軸 1–5）：
  1. **擋住別人或有期限**：沒答會擋 PR 送 0-A、擋合入、main 在紅、有到期日——排最前面。
  2. **同一 repo 或同一件事的連動題**：答了一題會影響另一題的放一起（例：同一張 PR 的兩件事、同一個客戶專案的幾題）。
  3. **快速組**：都有推薦選項、不需要討論，看完按一下就結案。
  4. **要給值或給事實**：agent 猜不出來、要 Charles 給日期、數字、人名或現場資訊。
  5. **建議寫掉**：Rule 1 查證後的過時、重複、已答題。
  6. **動手組**：`要我動手` 的列，要 Charles 到場、動帳號或親自打指令；維持 bullet，**NEVER** 編 `Qn`（`rules/QnX渲染判準.md` Rule 3）。
  7. **狀態組**：`不在本 repo`、`loop 結構性推不動`、`未分類`、`卡住、等人動手` 四桶的列，排在最後；組內照 `flow pending` 的桶名分小標、維持 bullet 與 `→` 動作行，**NEVER** 編 `Qn`、**NEVER** 併進前面的組或省略。四桶都空時整組不出。
- 每組標題寫組名與題數，下一句說「這組在決定什麼」與建議答法；組內每題一行：`Qn`、`[repo]`、題目濃縮、推薦。
- 總覽結尾 MUST 說建議先談哪一組與理由，並給那組一次回完的範例（例：`Q12 A、Q13 A、Q14 A`）。
- 全部只成一組（題少又同主題）時，總覽與第一組討論合併成一則，直接進 Phase 3。
- **NEVER** 把整份佇列逐題攤開當總覽——總覽的目的就是讓 Charles 一眼挑組；題目細節留到該組討論時才展開。

## Good Example

- 這個例子是好的，因為擋人的題排最前、連動題放一起，每組一句話說在決定什麼，最後建議先談哪組。

```md
A. 擋住別人，建議先談（3 題）：決定 #2548 能不能送 0-A、blog-site #40 能不能合
  - Q12 [clade] #2548 第一件改歸 agent？ 建議 A
  - Q13 [clade] #2548 第二件改歸 agent？ 建議 A
  - Q14 [blog-site] #40 授權合入（會觸發一次正式機部署）？ 建議 A

B. 快速組（4 題）：都有推薦，看完按一下就結
  - Q3 [clade] 段落層，推薦加
  …

建議從 A 組開始：它擋住 #2548 的 0-A 和一張待合 PR。可以直接回「Q12 A、Q13 A、Q14 A」。
```

## Bad Example

- 這個例子是壞的，因為照佇列原序把 38 題逐題攤開，沒有分組也沒說先談哪個，Charles 只能自己從頭讀到尾。

```md
要我拍板（38）
Q1 …
  A. …（推薦）
  B. …
Q2 …
…
Q38 …
```

# Rule 3 - 一次只帶一組；出題前先查現況，每題附現況、選項後果與推薦理由

- Level: `MUST`
- 一則回應只展開 Charles 挑的那一組，**NEVER** 一次塞滿多組或用互動式選單一次問完。
- 出題前先實查這組每題的現況（PR、CI run、plan、evidence 目錄、spine 舊答案），把查到的寫進題目底下；佇列上的題面常是幾天前寫的，現況可能已經變了。
- 每題的結構：題目一句 → `現況：` 幾條查到的事實 → 選項，每條選項後面接「這樣做會怎樣」 → 推薦與理由（可寫成「我的看法：」）。題面與選項文字照 `flow pending`（`rules/QnX渲染判準.md` Rule 1），後果與理由加在底下。
- 查證發現推薦已不成立（例：查到前提跟題目假設的不同），照實寫出並調整「我的看法」，但 **NEVER** 改佇列上的選項本身。
- 沒選項的題：跑 `flow ask-options` 向出題者要選項，並把查到的現況寫在題目底下、說明「已請出題者補選項」；查證後題目已不成立就依 Rule 1 改列建議寫掉。**NEVER** 替題目編一組自己猜的選項，也 **NEVER** 把「沒有選項」改說成「這題要給值」——要給值的題是出題時就標明要填什麼的那種。
- 組尾給一次回完的範例（例：`Q11 寫掉、Q14 A、Q15 A、Q16 先不答`），並提醒可以逐題追問。

## Good Example

- 這個例子是好的，因為先查了現況，選項各自寫出後果，推薦附理由，結尾給一次回完的範例。

```md
第 2 組：Q8，InstaBox 接 test-lanes 後 main 連紅，要怎麼處理？

現況：
- 最近一次跑完的 main（15:19）紅在 test-lanes (6/6)，之後幾輪被取消或還在跑
- 修 umask 的 PR #2541 已開，但它自己的 CI 還有 3 個 failure

  A. 修環境（推薦）：保留 InstaBox 路由，#2541 修掉 umask 依賴、加大磁碟；main 在那之前會繼續紅
  B. 暫停接 main：main 立刻止血，InstaBox 要等修完才回來分攤
  C. 撤回授權：等於放棄這次擴容

我的看法：A 是終局；要 main 今天就止血可以答「B，然後 A」。
```

## Bad Example

- 這個例子是壞的，因為沒查現況、選項沒有後果，還替沒選項的題自己編了選項。

```md
Q8 InstaBox main 連紅怎麼辦？ A. 修環境 B. 暫停 C. 撤回
Q11 doctor 紅了要不要放行？ A. 放行（推薦） B. 不放行   ← 佇列上這題沒有選項
```

# Rule 4 - 每答就落檔並回報剩多少；插問先答再回到原組

- Level: `MUST`
- Charles 一則回覆裡答了幾題，同一個 turn 就照 Phase 3 逐題 `flow answer --apply` 落檔並實查，**NEVER** 攢到整組或整場結束才一次落（`rules/待拍板條目寫法.md` Rule 14）。
- 答案不在選項裡（自由文字、「照你建議」、「先不改，因為…」）時，`--answer` 帶他的原話；回「照建議」或 `/sg` 就照那題的推薦落，並在回報裡說落的是哪個選項。
- 落完重跑 `flow pending`，回報這組落了哪幾題、整份佇列還剩幾題，再接下一組。
- Charles 插問題外話（「我們不是有一個…嗎」「為何不是 X」）：先查證回答，答完回到原組，把這組還沒答的題連同推薦再列一次，**NEVER** 讓插問把這組晾著。
- Charles 質疑「這題我答過了／為何要問」：先去 spine 查舊答案；查到就照舊答案落檔並承認是重複提問，查不到就照實說明。

## Good Example

- 這個例子是好的，因為答案當下落檔、用了 Charles 的原話，回報剩幾題，插問答完回到原組。

```md
第 3 組都已經落地，重跑 flow pending 確認那幾題消失了，現在剩 9 題拍板。
- Q14 落成你的原話：「先不改，後續有全面調整計畫，到時改才有意義」
- Q16 照建議落成「現場暫時不處理」

接著是第 4 組 repo-c，我先查 P1-M2 的線索。
```

## Bad Example

- 這個例子是壞的，因為答案只記在對話裡，插問之後沒有回到原組。

```md
好的，Q14、Q15 記下了，最後一起落檔。
（回答完插問後直接結束，第 3 組剩下的 Q16、Q17 沒再提）
```

# Rule 5 - 答案帶出的後續工作記成清單，討論中 NEVER 離開去做

- Level: `MUST`
- 答案常帶出後續工作（派工、合入、送 0-A、補報告、轉給另一個 session）。討論中只記下來並在該組收尾時列出「後續交給誰」，**NEVER** 中途離開討論去實作——Charles 在線上的時間是用來拍板的。
- 被派出的討論 pane（`CLADE_DISPATCH_ID` 非空、brief 指派陪 Charles 消化佇列）：後續工作逐條交回主持者（同機用 `SendMessage`，收工時寫進 `--complete success` 的 summary），**NEVER** 自己派工、合入或送 0-A。
- 主線 session：討論結束後再照本 session 的派工與 commit 規約處置清單上的工作。

## Good Example

- 這個例子是好的，因為後續工作在組尾列出並交回主持者，討論繼續往下一組走。

```md
repo-c 這組已經全部落地，後續交給主持者：
- 補 P1-M2 的 soak 報告
- repo-c 開 work 把 NC 程式改存 Postgres
現在剩 7 題拍板，接下來是第 5 組。
```

## Bad Example

- 這個例子是壞的，因為討論到一半自己開始實作，Charles 被晾在原地。

```md
Q5 你選 B，我現在就去 repo-c 把 #261 改回 Postgres，改完再回來談下一組。
```

# Rule 6 - Charles 說結束或佇列清空時，MUST 列出已答與未答清單

- Level: `MUST`
- 收尾一則列出：已落檔的 `Qn`（附答案）、寫掉的 `Qn`、補過選項（`ask-options`）的 `Qn`、還沒答的 `Qn`，以及 Rule 5 的後續工作清單與各自交給誰。
- 被派出的討論 pane 把同一份清單寫進 `--complete success` 的 summary。
- **NEVER** 只說「今天先到這裡」：沒列未答清單，下一次 `/my` 分不出哪些是新冒出來、哪些是上次跳過的。

## Good Example

- 這個例子是好的，因為已答、寫掉、未答與後續工作都列齊。

```md
今天落了 14 題、寫掉 4 題，剩 2 題沒談：
- 未答：Q1 user-level skill 歸屬、Q2 meeting-assistant 驗收前提
- 補過選項：Q11（已請出題者補）
- 後續交給主持者：soak 報告、NC 程式改存 Postgres、重複提問根因
```

## Bad Example

- 這個例子是壞的，因為沒有任何清單，下一輪無從接續。

```md
好，今天先到這裡，剩下的下次再說。
```
