
# Rule 1 - Charles 的每一個回答 MUST 經 `flow answer` 關 span 並落 carrier，NEVER 只在對話裡回覆就算結案

- Level: `MUST`
- Charles 回 `Q1A`、`Q3通過`、`Q2 退回：<理由>`、給值，或對「要我動手」列回了 `可回：X／Y` 其中一個字之後，**MUST** 對那條 span 跑 `flow answer`（指令見 `flow指令.md` § answer）。
- `flow answer` 一次做完五件事（後兩件的回傳欄位與處置見 Rule 9、Rule 10）：
  1. 關 span（那題從佇列消失）
  2. 把決策紀錄寫進 carrier 的錨定區段（`## 決策紀錄` 節；`td:` carrier 則是該 TD entry 尾），block 形如 `### 決策紀錄 <日期> — <問句>`＋`**答案**：…`＋`來源：flow spine … span \`<span_id>\`…`
  3. 量測 tech-debt hygiene 的差集（會引入新的 `docs/tech-debt.md` hygiene finding 時回滾 carrier 寫入）
  4. 選中的選項標了「TD 結案」（或帶 `--close-td`）、答案是終局否定（結案／不做／封存類）且 carrier 是一條 TD 時，把那條 TD 的 `**Status**:` 改成 `closed`／`wontfix`（回傳 `td_status`）
  5. 把落檔的紀錄送進 origin：trunk-based 的 repo 直接 commit＋push，PR 制的開 PR（回傳 `published`）
- `--answer` 帶 Charles 給的答案：選了一個選項時寫成 `<字母>. <短標籤>`（例：`A. 包相容層`），驗收寫 `通過` 或 `退回：<他的理由>`，給值或自由回覆照他的原文。
- **NEVER** 只在對話裡回覆就算結案——那樣答案沒有持久載體，下一個 session 看到的還是那題還在等。

## Good Example

- 這個例子是好的，因為 Charles 一則訊息回了兩題，兩題都各自經 `flow answer` 落檔。

```bash
cd ~/offline/clade && node vendor/scripts/flow/flow.ts answer 9d2f…41 --answer 'A. 現在回收' --repo clade
cd ~/offline/clade && node vendor/scripts/flow/flow.ts answer 1b77…0c --answer '通過' --repo <consumer-id>
```

## Bad Example

- 這個例子是壞的，因為它只在對話裡確認收到，span 沒關、carrier 沒有決策紀錄。

```md
收到：Q1 選 A、Q3 通過，我記下了，接著處理。
```

# Rule 2 - `--repo` MUST 逐字照抄佇列上那題的 `repo` 欄位，NEVER 自己換算成目錄路徑

- Level: `MUST`
- **`--repo` 給的是佇列上那個名字**（`flow pending` 每題前面的 `[<repo>]`），逐字照抄。名字 → 根目錄由 `resolveRepoRootByName` 解析。
- **NEVER** 自己換算成目錄路徑：自己填路徑就是第二份實作，而它漂掉的後果不是「chat 端壞了」，是**答案寫進別的 repo 的 spine、改到別的 repo 的檔案**。
- roster＝`consumers.local` ∪ `registry/consumers.json` 上本機有 checkout 的 consumer（含 `pending_onboard`）。名字解析不出來時它印 `roster 上找不到 repo「<name>」——不寫入…` 並非 0 退出——**MUST** 先回頭核對 `flow pending` 上那題的 repo 欄位。
- 核對後那個 repo 確實不在 registry 上（題是 `--audience coordinator` 開在 fleet 之外的 repo）才改帶 `--repo-root <那個 checkout 的絕對路徑>`：span 必須在它自己的 spine 上，指錯會回 `no-such-decision`。**NEVER** 對 roster 上有名字的 repo 用 `--repo-root`，**NEVER** 用 `CLADE_HOME` 改指繞過。
- 佇列上沒有 `[<repo>]` 前綴的題屬於 clade 本身，`--repo` 可省略。

## Good Example

- 這個例子是好的，因為 `--repo` 照抄 `flow pending` 上的 `[<consumer-id>]`。

```bash
cd ~/offline/clade && node vendor/scripts/flow/flow.ts answer 1b77…0c --answer '通過' --repo <consumer-id>
```

## Bad Example

- 這個例子是壞的，因為它把 repo 名自己換算成路徑，又在被 roster 拒絕後改用 `CLADE_HOME` 繞過。

```bash
node vendor/scripts/flow/flow.ts answer 1b77…0c --answer '通過' --repo <home>/offline/<consumer-id>
CLADE_HOME=<home>/offline/<consumer-id> node vendor/scripts/flow/flow.ts answer 1b77…0c --answer '通過'
```

# Rule 3 - NEVER 手寫 inline import `answerDecision`

- Level: `MUST`
- **NEVER** 手寫 `node --input-type=module -e "import { answerDecision } ..."`：那條路徑不經 roster 檢查，`repoRoot` 由人目測填，正是 Rule 2 要防的第二份 repo 解析。
- 同理，改答案 **NEVER** inline import `reviseDecision`，補選項 **NEVER** inline import `amendDecision`；三者都只走 `flow answer`／`flow revise`／`flow amend-options`。

## Good Example

- 這個例子是好的，因為回答只走 CLI 門，repo 解析由 roster 負責。

```bash
cd ~/offline/clade && node vendor/scripts/flow/flow.ts answer 9d2f…41 --answer 'A. 現在回收' --repo clade
```

## Bad Example

- 這個例子是壞的，因為它繞過 CLI 直接 import，`repoRoot` 由人目測填。

```bash
node --input-type=module -e "import { answerDecision } from './vendor/scripts/flow/answer.ts'; answerDecision({ spanId: '9d2f…41', answer: 'A', repoRoot: '<home>/offline/<consumer-id>', answeredBy: 'me', via: 'chat' })"
```

# Rule 4 - `ok:false`（非 0 退出）MUST 依 `reason` 處置，NEVER 自己造一個新 carrier 檔繞過

- Level: `MUST`
- `ok:false` 是真的失敗，span 沒有被關。依回傳 JSON 的 `reason` 與 `detail` 處置：

  | `reason` | 意思 | 處置 |
  | --- | --- | --- |
  | `no-such-decision` | span 不在這個 repo 的 spine 上 | 換 `--repo`：回頭核對 `flow pending` 上那題的 repo 欄位 |
  | `already-resolved` | 已經答過了（別的 tab、Notion projector 或上一輪） | 先在該 repo 的 checkout 跑 `flow answers --json`（**NEVER** 加 `--claim`，那會鎖住答案）查原答案：與這次相同 → 不改，只做 Phase 3 第 4 步核對；不同 → 以 Charles 這次明說的為準，走 `flow revise <span_id> --answer '<text>' [--repo <name>]`（見 `flow指令.md` § revise），再依 Rule 5 處理鎖；回報時說明原答案與改後答案 |
  | `not-answered`（revise 才有） | 這題還沒有人回答過 | 改走 `flow answer`，不是 `flow revise` |
  | `picked-up`（revise 才有） | 答案已被鎖 | 見 Rule 5 |
  | `override-reason-required`（revise 才有） | 帶了 `--override-follow-up` 卻沒帶 `--reason` | 補 `--reason '<Charles 給的理由>'` |
  | `spine-override` | `CLADE_FLOW_EVENTS` 指向別的 spine，寫入會落錯地方 | 回報 `detail`，不寫入；NEVER 改指 spine 繞過 |
  | `accept-not-revisable`（revise 才有） | 驗收判決不是可改寫的答案 | 要翻案就再下一次 accept／drop 判決 |

- **NEVER** 自己造一個新 carrier 檔、改寫 spine，或用其他入口繞過上表任何一個拒絕。

## Good Example

- 這個例子是好的，因為 `already-resolved` 的題改走 `flow revise`，沿用同一個 span。

```bash
# answer 回 {"ok":false,"reason":"already-resolved",...}
cd ~/offline/clade && node vendor/scripts/flow/flow.ts revise 9d2f…41 --answer 'B. 留到下一輪' --repo clade
```

## Bad Example

- 這個例子是壞的，因為它看到 `already-resolved` 就新開一個 carrier 檔，把新答案寫進去。

```bash
echo '## 決策紀錄\n- 9d2f…41 改答 B' > docs/decisions-override.md
```

# Rule 5 - `flow revise` 回 `picked-up` 時 MUST 照 `locked.by` 說出是哪一種鎖

- Level: `MUST`
- `picked-up` 的回傳帶 `locked: { by, at, actor }`，`by` 只有兩種，處置不同：

  | `locked.by` | 意思 | 處置 |
  | --- | --- | --- |
  | `pickup` | 有 agent 用 `flow answers --claim` 宣告接手了這個答案 | **硬鎖**。告訴 Charles 是誰（`actor`）在何時（`at`）接手，**NEVER** 提供覆寫，也 NEVER 嘗試 `--override-follow-up`（對 `pickup` 永遠拒） |
  | `follow-up` | 答案之後同一件工作又開了新的 span，推測已有人在執行 | 渲染時 **MUST** 明說「推測已有人在執行」，並附上推翻指令 `flow revise <span_id> --answer '<text>' --override-follow-up --reason '<why>'` |

- 推翻指令**只在 Charles 明說要推翻時才跑**，`--reason` 寫他給的理由（理由會落在 `decision.revise` 的 payload，是事後唯一看得出「誰、為何推翻」的地方）。

## Good Example

- 這個例子是好的，因為它說出鎖的種類，`follow-up` 明說是推測並附推翻指令，等 Charles 明說才跑。

```md
Q1 改答失敗：推測已有人在執行（work W-2026-10-03-sync 在 10:42 又開了新 span）。
若要推翻，回「推翻 Q1：<理由>」，我會跑：
flow revise 9d2f…41 --answer 'B. 留到下一輪' --override-follow-up --reason '<你的理由>'
```

## Bad Example

- 這個例子是壞的，因為它沒說是哪一種鎖，對 `pickup` 硬鎖也直接加覆寫旗標，且 Charles 沒說要推翻就自己跑了。

```bash
node vendor/scripts/flow/flow.ts revise 9d2f…41 --answer 'B' --override-follow-up --reason '改一下'
```

# Rule 6 - `ok:true` 但 `landed:false` 不是失敗，NEVER 因此重跑

- Level: `MUST`
- `ok:true`＋`landed:false` 代表 span 已收、答案已在 spine 上，只有 carrier 那一步沒做到；`flow answer` 以 exit 0 結束。
- **NEVER** 因此重跑一次 `flow answer`——那個寫入已經生效了，重跑只會撞上 `already-resolved`。
- `reason` 會說是哪一種，照實回報給 Charles：

  | `reason` | carrier 那一步為什麼沒做到 |
  | --- | --- |
  | `no-carrier` | 題目沒指定落點，答案只存在 spine 上 |
  | `carrier-missing` | 指定了落點，但對應的檔案不存在 |
  | `carrier-outside-repo` | 落點解析到 repo 之外，拒絕跟過去 |
  | `td-hygiene-regression` | 寫入會新增 `docs/tech-debt.md` hygiene finding，已回滾 |
  | `carrier-lock-contention` | carrier 寫入鎖被別的 session 佔住超過上限 |
  | `landed-block-ambiguous` | carrier 上同一個 span id 出現不只一次，拒絕猜是哪一段 |

- 有指定 carrier 卻沒落地的題，超過寬限後會以 `answer-not-filed` 出現在 `flow status --stalled`，並自帶 `flow relend <span_id>` 指令；補落檔走 `relend`，不走重答（判準見 `rules/待拍板條目寫法.md` Rule 18）。

## Good Example

- 這個例子是好的，因為它認出答案已生效，只回報 carrier 沒落地的原因。

```md
Q2 已收（span 已關、答案在 spine 上），但 carrier 沒落地：carrier-lock-contention（另一個 session 正在寫 HANDOFF.md）。
稍後 status --stalled 會列 answer-not-filed，屆時用 flow relend 3e0a…9f 補回。
```

## Bad Example

- 這個例子是壞的，因為它把 `landed:false` 當成失敗，重跑 `flow answer`。

```bash
# 第一次回 {"ok":true,"landed":false,"reason":"carrier-lock-contention"}
node vendor/scripts/flow/flow.ts answer 3e0a…9f --answer 'A. 包相容層' --repo <consumer-id>   # 再跑一次
```

# Rule 7 - 落檔後 MUST 實查：只動 carrier 一個檔、block 真的在，NEVER 用 `tail` 查

- Level: `MUST`
- 跑完 `flow answer`（`ok:true`、`landed:true`）**MUST 實查**，在該題 repo 的根目錄，依回傳的 `published.state`：
  - `pushed`：`git status --porcelain -- <carrier>` 是空的，`git show origin/<預設 branch>:<carrier> | grep -n '<span_id>'` 看得到 block
  - `pr-opened`：主 checkout 的 carrier 已還原（`git status --porcelain -- <carrier>` 是空的），block 在 `published.pr_url` 那張 PR 的 `decision/<span_id>` branch 上
  - `unpublished`／沒有 `published` 欄：`git status --porcelain` 只動到 carrier 那一個檔，`grep -n '<span_id>' <carrier>` 看 block 真的在，再照 Rule 9 處置
- **NEVER** 用 `tail` 查——block 落在錨定區段（`## 決策紀錄` 或 TD entry 尾）裡，不在檔尾；`tail` 看不到不代表沒落地，看得到也可能是別的 block。

## Good Example

- 這個例子是好的，因為兩項實查都做，且用 grep 對 span id 定位。

```bash
# 回傳 "published":{"state":"pushed",…}
cd ~/offline/<consumer-id> && git status --porcelain -- HANDOFF.md
# （空）
git show origin/main:HANDOFF.md | grep -n '1b77…0c'
# 219:來源：flow spine `decision.request` span `1b77…0c`（Charles 在 chat 回答，由主線代填）。
```

## Bad Example

- 這個例子是壞的，因為它用 `tail` 看檔尾，沒看到就以為沒落地，也沒檢查有沒有動到其他檔。

```bash
tail -5 HANDOFF.md
```

# Rule 8 - 要先看會寫成什麼時用 `--dry-run`

- Level: `SHOULD`
- 不確定答案會寫成什麼、或要先給 Charles 看落檔內容時，先跑 `flow answer … --dry-run`：輸出裡的 `block` 逐字就是等一下會寫進去的那段，且不關 span、不改檔。
- 確認後再去掉 `--dry-run` 正式跑；**NEVER** 把 dry-run 的輸出當成已落檔。

## Good Example

- 這個例子是好的，因為先預覽 block，確認後才正式寫入。

```bash
cd ~/offline/clade && node vendor/scripts/flow/flow.ts answer 9d2f…41 --answer 'A. 現在回收' --repo clade --dry-run
# 看 "block" 欄位 → OK → 去掉 --dry-run 再跑
```

## Bad Example

- 這個例子是壞的，因為它跑完 dry-run 就回報已落檔。

```md
已落檔（dry-run 輸出 block 正確）。
```

# Rule 9 - `published.state` 是 `unpublished` 時 MUST 當下處置或回報，NEVER 當成已散播

- Level: `MUST`
- `flow answer` 落檔後會照該 repo 在 `registry/consumers.json` 的 `workflow_model`／`propagate_flow`／`push_hold` 把紀錄送進 origin。`published.state` 的值域與處置：

  | `state` | 意思 | 處置 |
  | --- | --- | --- |
  | `pushed` | 已 commit 並推上預設 branch | 無 |
  | `pr-opened` | 已推 `decision/<span_id>` branch 並開 PR，主 checkout 的 carrier 已還原 | 把 `pr_url` 回報給 Charles／主持者；**NEVER** 自己 merge |
  | `unpublished` | 紀錄只在這個 checkout 的工作區 | 依下表 `reason` |
  | `nothing-to-publish` | carrier 與 HEAD 沒有紀錄差異 | 無 |

  | `unpublished` 的 `reason` | 處置 |
  | --- | --- |
  | `carrier-has-other-edits` | carrier 上還有別人未提交的改動。**NEVER** 代為提交那些改動；回報是哪個檔，等它們被提交或移開後跑 `flow publish-answers --repo <name>` |
  | `branch-not-aligned`／`not-on-default-branch` | 主 checkout 與 origin 不一致。回報現況，對齊後跑 `flow publish-answers --repo <name>` |
  | `push_hold`／`no-workflow-model`／`not-registered`／`no-registry` | 這個 repo 的散播方式判不出。回報「已落檔、未散播」與 `reason`，由主持者決定；**NEVER** 自己 `git push` |
  | `commit-failed`／`push-failed`／`fetch-failed`／`pr-create-failed`／其餘 | 照 `detail` 回報；`pr-create-failed` 的 `detail` 自帶補開 PR 的指令 |

- 沒處置掉的 `unpublished` 超過 10 分鐘會以 `answer-not-published` 出現在 `flow status --stalled`，自帶 `flow publish-answers` 指令。
- **每一則**含 `unpublished` 的回報 **MUST** 逐字寫出「已落檔、未散播」與 `reason`。**NEVER** 只寫「已落檔」。

## Good Example

- 這個例子是好的，因為它把未散播與原因講明，並給出補送指令。

```md
Q2 已落檔、未散播（carrier-has-other-edits：<consumer-id> 的 docs/tech-debt.md 還有別的未提交改動）。
那些改動提交後跑：flow publish-answers --repo <consumer-id>
```

## Bad Example

- 這個例子是壞的，因為它把只在本機工作區的紀錄報成已完成，其他機器讀到的仍是「等回答」。

```md
Q2 已落檔。
```

# Rule 10 - 選項標了「TD 結案」（或帶 `--close-td`）的終局否定答案會關掉 carrier TD，回報 MUST 帶 `td_status`

- Level: `MUST`
- 判定寫在 `vendor/scripts/flow/answer.ts` 的 `tdStatusForAnswer`，兩道都過才關：
  1. **來源**：選中的選項說明（`標籤 :: 說明` 的後半；`flow ask` 問的題存在 `option_consequences`）標了「TD 結案／TD 關閉／TD 不做／wontfix」之類，**或** `flow answer` 帶 `--close-td`。兩者都沒有就**不動 Status**——答案文字再像終局也一樣（`B. 關閉` 可能是在回答「auto-sync 要不要關掉」）。
  2. **答案文字**（`terminalAnswerStatus`）：去掉選項字母後，答案**開頭**是「不做／不修／不處理／不採用／放棄／wontfix」→ `wontfix`，是「結案／關閉／封存／歸檔／close」→ `closed`；整段答案帶替代做法（「改做／改用／用／採用 B」，`不採用` 本身不算）、「但／除非／先不／暫時／之後再／等…再／或」或問號就判不出，**不動 Status**。
- 提問端要讓這題答了能關 TD，**MUST** 在那個選項的說明寫明「TD 結案」；回答端碰到選項沒標、但 Charles 明說要關的，帶 `--close-td`。
- 回傳帶 `td_status: { td, from, to, applied, reason }`：
  - `applied:true`：那條 TD 的 `**Status**:` 已改成 `to`，原值留在同一行。回報時說出「TD-NNN 已由 `<from>` 改成 `<to>`」。
  - `applied:false`：`reason` 是 `already-closed`／`no-entry`／`no-status-field`／`hygiene-regression`／`lock`。答案照樣已落檔；`hygiene-regression` 與 `no-status-field` **MUST** 回報「答案是終局否定，但 TD-NNN 的 Status 沒改（`<reason>`），需人工關閉」。
- `--answer` **MUST** 照 Charles 的原文寫。**NEVER** 為了觸發或避開關閉而改寫他的用詞。
- Charles 的答案是終局否定但沒有 `td_status`（carrier 不是 TD、選項沒標「TD 結案」也沒帶 `--close-td`、或答案帶了轉折詞）時，**MUST** 在回報裡說明那條 backlog 項目仍是 open，由誰關。

## Good Example

- 這個例子是好的，因為答案照原文落檔，並回報 TD 的 Status 變化。

```md
Q5 已落檔並推上 origin：「結案 近期沒打算提供沒打算做」。TD-047 已由 open 改成 closed，backlog 不會再派。
```

## Bad Example

- 這個例子是壞的，因為它把 Charles 的原文改寫成選項字母以外的字，Status 沒被關也沒回報。

```bash
node vendor/scripts/flow/flow.ts answer 5c1e…7a --answer '先不處理這條' --repo <consumer-id>   # 原文是「結案 近期沒打算提供沒打算做」
```
