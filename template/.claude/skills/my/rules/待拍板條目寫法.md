
# Rule 1 - 佇列只從 `flow pending` 讀，NEVER 自己 grep 四個檔案來源

- Level: `MUST`
- `flow pending` 已經收斂完**五個**來源：四個檔案來源（work-loop state／`HANDOFF.md`／`docs/tech-debt.md`／tasks）**加上 spine 本身**（agent 用 `flow ask` 直接問的題），並做完分桶、`Qn` 編號、以及結尾那行**當下實跑**的現況量測。
- Fleet 是預設：consumer repo 的問題照樣是同一個人要回的。exit 2 代表佇列空，不是壞掉。
- **NEVER** 改用 `rg`／`grep` 自己去翻那四個檔——它們與佇列會漂，而漂掉的那一份看起來一樣真。
- spine 更是 grep 不到的：`flow ask` 開的題不在任何檔案裡，只有 `flow pending` 看得見——所以用 `flow ask` 開的題一定會出現在 `\my`，自己 grep 的版本一定會漏掉它們。

## Good Example

- 這個例子是好的，因為佇列只有一個讀取入口，五個來源與量測都由同一支 CLI 給出。

```bash
node ~/offline/clade/vendor/scripts/flow/flow.ts pending
# exit 2 → 佇列空，照 QnX 渲染判準 Rule 7「佇列全空」處理
```

## Bad Example

- 這個例子是壞的，因為它自己掃檔案來源：漏掉 spine 上所有 `flow ask` 的題，且拿到的是可能已經與佇列漂開的那一份。

```bash
rg -n '🔴|🟡|Awaiting Charles' HANDOFF.md docs/tech-debt.md tasks/
```

# Rule 2 - 只存在本 session 對話裡的待決策點 MUST 逐條推進佇列

- Level: `MUST`
- 五個來源對下列三種待決策點**完全盲**，每一種都 MUST 掃出來：
  - agent 在對話裡列過選項、卻沒有定案的
  - agent 明講「這要你判斷」的
  - 工作停在等 Charles 回答的
- **每找到一條就推進佇列**（`flow ask`，參數見 `flow指令.md` § ask），推進去才有價值。**NEVER** 只在對話裡列出來就算——那正是「待拍板事項多數只存在於對話裡」這個缺口本身。
- 下列兩種**不是**待決策點，NEVER 推進佇列：
  - agent 自己做得掉的事——那是 `\nx` 的範圍，列進來是充數
  - 本 session 已由 agent 自行決定並執行的事——那是既成事實，該給的是回報不是選擇題
- 每一條推進去的題 MUST 帶推薦選項與理由。**NEVER** 因為某條「反正也做不了」就省略推薦——沒有推薦 = 這條沒被消化過，等於把決策工作原樣退回給 Charles。

## Good Example

- 這個例子是好的，因為對話裡一條「列過選項沒定案」的點被推進佇列，帶齊選項、推薦、理由與 carrier。

```bash
node ~/offline/clade/vendor/scripts/flow/flow.ts ask \
  --headline 'stale worktree 要現在收嗎？' \
  --question 'clade-wt/old-sync 已 14 天沒動、branch 已併回 main；要現在回收，還是留到下一輪批次？' \
  --option '現在回收 :: 跑 reclaim-stale，樹與 branch 一起清掉' \
  --option '留到下一輪 :: 不動，下一輪 batch 再判' \
  --recommended '現在回收' --why 'branch 已併回、樹內無未提交變更' \
  --carrier HANDOFF.md --actor 'w3:p2'
```

## Bad Example

- 這個例子是壞的，因為三種錯誤同時出現：只在對話裡列題、把 agent 自己做得掉的事列進來、且沒有推薦。

```md
目前還有幾件事待你決定：
1. stale worktree 要不要收？（A 收 / B 不收）
2. 我剛把 lint 錯修好了，要不要接受？
3. 要不要我跑一次 pnpm test？
```

# Rule 3 - 只有 Charles 做得了的工作：題目是「哪一台、哪個範圍」，執行寫成 `--step`

- Level: `MUST`
- 典型：consumer 端 `disable-model-invocation` 的 skill，例如 dep batch 的 `/version-upgrade`；派工 preflight 回 `skill_not_invocable` 的就是這種。
- 開成拍板題，題目問**哪一台、哪個範圍**；選項是範圍與「這輪不跑」；Charles 要親自執行的動作寫成 `--step`。
- **NEVER** 把「去跑它」本身開成帶字母的題——依 QnX 協定，要 Charles 執行的動作不編號。

## Good Example

- 這個例子是好的，因為題目是範圍選擇，動作以 `--step` 掛在卡上。

```bash
cd ~/offline/<consumer-id> && node ~/offline/clade/vendor/scripts/flow/flow.ts ask \
  --headline '<consumer-id> 跑 dep batch：範圍？' \
  --question '<consumer-id> 有 14 個 outdated 套件，/version-upgrade 只能你在 <consumer-id> 親自打；這輪要跑哪個範圍？' \
  --option '只跑 patch :: 只升 patch 版，風險最低' \
  --option 'patch＋minor :: 一併升 minor，需要看 changelog' \
  --option '這輪不跑 :: 留到下一輪 dep batch' \
  --recommended '只跑 patch' --why 'minor 裡有 nuxt 4.x，需要另排驗收' \
  --step 'Charles 在 <consumer-id> 親自打 /version-upgrade → Outdated mode' \
  --carrier HANDOFF.md --actor 'w3:p2'
```

## Bad Example

- 這個例子是壞的，因為它把「去跑」本身做成選擇題，Charles 回 A 之後沒有任何一個 span 能關。

```bash
node ~/offline/clade/vendor/scripts/flow/flow.ts ask \
  --question '請到 <consumer-id> 跑 /version-upgrade' \
  --option '好 :: 去跑' --option '不要 :: 不跑' \
  --recommended '好' --why '要跑'
```

# Rule 4 - 拍板題 bullet MUST 長成「問句＋2–4 條連續字母選項」的形狀

- Level: `MUST`
- 寫進 `HANDOFF.md`／`docs/tech-debt.md` 的待拍板 bullet，60 秒內會被 `vendor/scripts/flow/decision-sources.ts` 掃進 spine，出現在 `flow pending` 與 `\my`（掃描器與佇列契約在 clade 端 `decision-sources.ts`／`decision-sync.ts`）。**寫的人與答的人中間隔著一個解析器。**
- **Lifecycle repo（repo root 有 `specs/truth/work-lifecycle.md`）不寫這種 bullet**：`docs/tech-debt.md` 已停寫，`HANDOFF.md` 只留 W- 指標（[[handoff]] § Lifecycle repo）。拍板題直接 `flow ask`（Rule 11）；本 Rule 的題目形狀照樣適用於 `flow ask` 的題目。
- 一條要 Charles 拍板的 bullet **是**下列四個部件，照這個順序：

  | 部件 | 契約 |
  | --- | --- |
  | 問句 | 第一段 `**粗體**`。`source_id` 由它導出，所以**改寫它 = 換一題**（見 Rule 20） |
  | 選項 | 2–4 條，**MUST 從 A 起連續**，推薦的排第一並標「（推薦）」 |
  | 每條選項 | 一句「這樣做會怎樣」，不是名詞短語 |
  | 縮排 | 選項是問句的 sibling bullets，彼此相鄰、同縮排 |

- **沒有選項的拍板題 MUST 改寫成「這題要給值」並逐項列出要填什麼**；兩者都不成立就不要放進待拍板區段（否則手機上是一個答不了的空白輸入框）。
- 粗體只包字母、包整段、或包字母與標記（`**A（推薦）**：…`）三種都解析得到。
- 選項可換行，但續行 **MUST** 縮排比該 bullet 深、不是新的 list item，上限 3 行——被截斷時手機上沒有任何訊號。
- 下列每一種都解析不到，靜默退化成自由填答：

  | 寫法 | 為什麼收不到 |
  | --- | --- |
  | `或者可以 X，也可以 Y` | 散文。**NEVER** 從散文猜選項 |
  | `- **A 這樣做**` / `- **D 那樣做**` | 字母不連續，整組丟棄 |
  | `- **A 只有這條**` | 一條不是選擇題 |
  | A 在段落開頭、B 在六段之後 | 選項是相鄰的 sibling bullets，隔太遠的兩個粗體字母是散文 |
  | `- **A 方案已採用**` / `- **B 案已否決**` | 在敘述已經決定的事。待拍板區段裡 **NEVER** 放已拍板的紀錄 |

## Good Example

- 這個例子是好的，因為四個部件齊全：粗體問句帶一句理由、選項從 A 連續、推薦排第一、每條都是「這樣做會怎樣」。

```markdown
- 🔴 **一句話問句** —— 為什麼需要你拍板（一句）
  - **A（推薦）第一案** —— 這樣做會怎樣
  - **B 第二案** —— 這樣做會怎樣
  - **C 第三案** —— 這樣做會怎樣
```

## Bad Example

- 這個例子是壞的，因為選項寫成散文、字母又不連續，解析器整組丟棄，手機上只剩空白輸入框。

```markdown
- 🔴 **要不要換掉舊的 sync 腳本？** 或者可以直接刪，也可以先包一層相容。
  - **A 直接刪**
  - **C 包一層** 方案（之前討論過，見上面第六段）
```

# Rule 5 - 區段 heading MUST 用規定語義，分桶軸只有「這一列怎麼離開佇列」

- Level: `MUST`
- 掃描器用 heading 決定這條 bullet 落到 `\my` 的哪一桶。**MUST** 用下列語義，**NEVER** 自創同義詞：

  | heading 語義 | 桶 | 什麼進得去 |
  | --- | --- | --- |
  | `Awaiting Charles`（球在 Charles 手上） | `ruling` | 要拍板的選擇題，或要給值的題 |
  | `Ready for review`（做完了，等看一眼） | `review` | 已完成、等驗收的工作。**MUST 帶三欄**，見 Rule 6 |
  | `需要 Charles 執行` | `human-action` | 只有人做得到、而**終點不是一句回覆**的動作（實體硬體、線上帳號、密鑰輪替） |
  | loop 結構性推不動 | `loop-structural` | agent 反覆撞同一堵牆，要人改結構 |
  | **跨 repo** | **不進佇列** | 已移交的紀錄 |
  | **`Blocked`** | **不進佇列** | 敘述工作為什麼停住，寫不出 Charles 的動作 |

- **分桶的軸只有一條：這一列怎麼離開佇列**——一句短回覆 → `ruling`／`review`；別處的一個動作 → `human-action`；結構改動 → `loop-structural`。
- 分桶軸 **NEVER** 是重要性或可逆性；「可回答」（`ANSWERABLE`）是它的衍生屬性，**NEVER** 是第二條軸。
- 舊 span 的 `irreversible` 由 `bucketOf` 渲染時摺進 `human-action`，**NEVER** 改寫既有 span 的 `category`。
- **跨 repo 與 `Blocked` NEVER 進佇列**。**NEVER 把 `Blocked` 重新收進來，也 NEVER 改用區段內文的關鍵字啟發式**——真的要人動手就寫進 `Awaiting Charles`、`Ready for review`、tech-debt 的 `### 需要 Charles`、或 tasks 的 `deferred-user-only`。
- **改分桶語義時 MUST 同時改本 Rule 的分桶表與 `decision-sources.ts` 的 `categoryOfHeading()`**。

## Good Example

- 這個例子是好的，因為「要人插實體 USB key」終點不是一句回覆，所以放在 `需要 Charles 執行`，不是 `Awaiting Charles`。

```markdown
## 需要 Charles 執行

- 🔴 **NAS 的 USB 備份碟要換新的** —— 舊碟 SMART 已報 reallocated sectors
```

## Bad Example

- 這個例子是壞的，因為它自創 heading 同義詞，又把 `Blocked` 的敘述當成要人回答的題。

```markdown
## 要老闆決定的事（很重要）

- 🔴 **CI 卡住了** —— 等上游修

## Blocked

- 🔴 **要不要升 node 24？**
  - **A（推薦）升** —— …
```

# Rule 6 - `Ready for review` 的每一條 MUST 帶滿三欄

- Level: `MUST`
- **每一個** consumer 的 **每一條** `Ready for review` 條目，**MUST** 在它自己的 bullet 底下帶滿「改了什麼／證據／退回會怎樣」三行——不是「盡量」、不是「重要的那幾條」、不是「等有空補」。
- **Lifecycle repo（repo root 有 `specs/truth/work-lifecycle.md`）例外的是載體，不是三欄**：`HANDOFF.md` 不得有未勾的 `- [ ]`（[[handoff]] § Lifecycle repo，FR-028），所以本 Rule 與 Rule 7 的 `- [ ]` 條目 **NEVER** 寫進它的 `HANDOFF.md`。改用 `flow ask --category review --human-only <理由>`（三欄照寫進題目；agent 自己驗得了的不鑄題）或 `flow ask --category ruling` 直接進佇列；三欄與「一題一問」（Rule 12）的要求不變。
- **分不出 `review` 還是 `human-action` 時問：證據能不能壓成「30 秒可開的東西」**（preview URL／commit／一段輸出）。不能（要人手、實體裝置、只有 Charles 有的帳號，例如手機真機驗收）→ `human-action`；硬寫進 `Ready for review` 會永遠掛 `missing-evidence` 而進不了佇列。
- 三欄缺一就驗不了，**NEVER** 放寬成「三選一」。
- **證據 NEVER 寫「見 HANDOFF」、change 名字、或任何要對方再跳一次的指標。**
- 三欄沒寫齊的條目 ingest 端**拒鑄 span**，改在 `flow sources` 與 `handoff-scan` 印退件行（收件人是寫的人），補齊後下一趟掃描自己會開。

## Good Example

- 這個例子是好的，因為三欄齊全，證據是可點的 commit 與 preview URL，退回代價講清楚。

```markdown
- [ ] **打卡頁改成先選班別再打卡**
  - 改了什麼: 打卡前必須先選班別，未選時打卡鈕 disabled
  - 證據: https://preview-482.example.dev/my/clock ／ commit 3f9a1c2
  - 退回會怎樣: 回到舊流程，夜班仍會被記成日班
```

## Bad Example

- 這個例子是壞的，因為證據是要再跳一次的指標，且缺「退回會怎樣」，ingest 端會拒鑄 span。

```markdown
- [ ] **clock-shift-select**
  - 改了什麼: 見 tasks.md
  - 證據: 見 HANDOFF
```

# Rule 7 - 佇列的「通過」NEVER 代替人工驗收的「通過」

- Level: `MUST`
- 同一條 change 有兩個各自獨立的通過，它們的**終點不同**：

  | 哪一種 | 誰記錄 | 一句「通過」結掉的是什麼 |
  | --- | --- | --- |
  | 佇列的 `Ready for review` → `通過` | spine 上的 span，答完那條就離開 `\my`／`flow pending` | **方向 OK、可以進人工驗收** |
  | `tasks.md` 的 `[review:ui]` checkbox／plan 的 `@human` 場景 receipt | checkbox 自己，或 `flow receipt` 寫進 `evidence/receipts.jsonl`（`ui-judgement` 卡） | **人真的在瀏覽器把那一頁開起來看過了** |

- **答佇列 NEVER 等於驗收**——答完就離開佇列，未勾的 `[review:ui]` 沒有任何畫面再提醒。
- 所以**條目指向的 change 若還有沒勾的 `[review:ui]`，那條 NEVER 是佇列的題**：掃描端（`restatesManualReview()`，讀 `tasks/` 直下 live work 的未勾 checkbox，另以「`人工檢查` ＋ live work slug」文字 fallback）掛 `belongs-on-review`、**不**合成 通過／退回，但照樣留在佇列（**NEVER** 擋掉）。
- **NEVER 把未勾的 `[review:ui]` 各開一條進佇列**——一條 change 的驗收是一趟差事：plan 的 `@human` 場景家在 `ui-judgement` 卡，tasks.md 的 leaf 家在 checkbox 本身（evidence 齊了由 session owner 在 chat 一次交給 user，[[proactive-skills.manual-review-entry]] 第 4 步）。

  | REQUIRED 欄位 | 內容 |
  | --- | --- |
  | 觸發條件 | 條目指向的 live change 有 ≥1 項未勾 `[review:ui]` → `belongs-on-review` lint ＋ 不合成 通過／退回。**warn-only，不 block** |
  | 消費端 | 寫該條目的 agent（看到 lint 就把它移回人工驗收流程）＋ `flow pending` 上的 Charles（看到沒有通過鍵就知道要去逐條驗） |
  | 觸發點 | 本 Rule（`my/rules/待拍板條目寫法.md`：`my` Phase 1 第 3 步讀取；編輯 `HANDOFF.md`／`docs/tech-debt.md` 時由 hook 提示讀取） |

## Good Example

- 這個例子是好的，因為還有未勾 `[review:ui]` 的 change 不進佇列，而是一次交給人工驗收流程。

```md
tasks/clock-shift-select/tasks.md 還有 2 項未勾 [review:ui]
→ 不寫 Ready for review 條目；evidence 齊了由 session owner 在 chat 一次交給 Charles 逐頁驗
```

## Bad Example

- 這個例子是壞的，因為它把每一個未勾 `[review:ui]` 各開一題，Charles 回「通過」後 checkbox 仍未勾、也沒有畫面再提醒。

```markdown
## Ready for review

- [ ] **/my/clock 開起來看** …
- [ ] **/my/salary 開起來看** …
```

# Rule 8 - 已經出版的 work NEVER 再問一次，且判定 fail-closed

- Level: `MUST`
- 已經隨版本 tag 出版、散播到全 fleet 且零失敗的 work 不再問人：`flow sources --apply` 對每件 `done` 的工作查三格證據，全中就寫 `work.accept`（`actor: system`、`reason: landed <tag>`、`payload.accepted_by: 'landing'`）：
  1. `commit:<sha>` 這個憑證在本 repo 存在
  2. 它已經 push（至少一個 remote-tracking ref 包含它）
  3. 它落在一個 `v<semver>` tag 裡，而**那一版的 propagate journal 有紀錄、且每一台 consumer 都真的收到了那一版**
- **代替人按的是證據，NEVER 是判斷。** **NEVER 對沒有 landing 證據的 work 自動 accept**（「pane 回 success 了」「commit 已經在 main 上了」都不算——進了 main 不等於出版）。
- 判定 fail-closed：三格缺一就照樣問人；journal **0 筆不是零失敗**。
- 第 3 格的 status 判定 **MUST 是 allow-list**，**NEVER 是 deny-list**（漏列的預設就是放行一個終態的 `work.accept`）。只有兩種算送達：
  - `bumped` —— commit 建了、push 了、remote 確認過
  - `skipped` **且那台 consumer 的 upstream remote-tracking ref 上的 manifest 版本已到達該 tag**（`skipped` 分不出來源，所以問那台自己停在哪一版；讀 `landing.ts` 固定的 upstream commit 上的 `.clade/manifest.json`，舊版 manifest 路徑的遷移期 alias 由 `landing.ts` 處理）。**NEVER** 讀磁碟（propagate 先寫 manifest 才同步）、**也 NEVER** 讀 HEAD（journal 整檔覆寫會把 `push-withheld` 蓋成 `skipped`），也 **NEVER** 改成「HEAD 到版 ＋ HEAD 已 push」（consumer main 領先 origin 是常態，會永遠 false）。讀不到 → 無證據
- 其餘全部不算，包含 `push-unconfirmed`、`bumped-local`、`push-withheld`。**NEVER** 用「那一趟是 `--no-push`」放行 `push-withheld`——沒有證據是正確的量測。
- 沒有 landing 證據、且歸 Charles 的驗收列（帶 `--human-review` 或 `notion:` origin；其餘歸 agent 補可重驗證據，不進這張卡，見 `flow-work-tracking.md`）**同一個 repo 合併成一張卡**（全收／逐條／還沒）；卡片逐條列出是哪幾件，**NEVER** 讀成一次收掉一批沒看過的東西。

  | REQUIRED 欄位 | 內容 |
  | --- | --- |
  | 觸發條件 | 三格證據全中 → `flow sources --apply` 寫 `work.accept`，佇列不再排那一列。**不 block**，只少問 |
  | 消費端 | `flow pending`（同一支 `buildDecisionQueue`）；`flow accept` 保留給人 |
  | 觸發點 | 本 Rule（`my/rules/待拍板條目寫法.md`：`my` Phase 1 第 3 步讀取；編輯 `HANDOFF.md`／`docs/tech-debt.md` 時由 hook 提示讀取）；判定器 `vendor/scripts/flow/landing.ts` |

## Good Example

- 這個例子是好的，因為三格證據都由量測給出，缺一格就照樣問人。

```md
work W-2026-09-30-x：commit 3f9a1c2 存在 ✓、origin/main 含它 ✓、v3.41.0 journal 12/12 台 bumped ✓
→ 系統寫 work.accept（reason: landed v3.41.0），不再問 Charles
```

## Bad Example

- 這個例子是壞的，因為它用判斷代替證據，把「進了 main」與 `push-withheld` 當成出版。

```md
pane 回 success、commit 已在 main，journal 有 2 台 push-withheld（那趟是 --no-push）
→ 視為已出版，自動 accept
```

# Rule 9 - 答完的條目 MUST 自己標成完結

- Level: `MUST`
- `- 🔴`／`- 🟡` 是「還沒解決」；`- ✅` 與 `- [x]` 是已完結，掃描器跳過。
- 答案落檔是 append、不刪來源 bullet，所以**答完之後 MUST 自己把那條標成完結**；不標的話那條會繼續被掃描器讀成未決。

## Good Example

- 這個例子是好的，因為答案落檔後，來源 bullet 的標記同步改成完結。

```markdown
- ✅ **stale worktree 要現在收嗎？** —— 已答 A（2026-10-03），見 § 決策紀錄
```

## Bad Example

- 這個例子是壞的，因為決策紀錄已落檔，但來源 bullet 仍是 🔴，下一輪掃描會把它當成還沒答。

```markdown
- 🔴 **stale worktree 要現在收嗎？**
  - **A（推薦）現在回收** —— …
```

# Rule 10 - 自述結案的條目 MUST 搬離待拍板段

- Level: `MUST`
- 條目本文自己說了「已拍板 A」「已完結」「已隨 relay-4 落地」，掃描端判 `self-closed`、**不鑄 span**。
- **NEVER 把 `self-closed` 讀成「所以不用管它」**：`flow sources` 每輪會印計數，**MUST 搬到參考段或刪掉**。
- 判準只讀**標題 ＋ 第一段**，且要求**沒有**未勾 checkbox、**沒有**未答選項——一條寫著「已拍板 A，接下來要決定 B／C」的條目仍然是題目。
- 題目訊號只算結案語之後、同一行內的疑問詞（明說「接下來要決定／待你拍板」的跨行照樣算）。被誤判的代價是一題永遠不會被問。**NEVER 加關鍵字啟發式擴充這張表**。
- agent 代收走 `flow dismiss <span_id> --reason '<為什麼不再需要人>' [--repo <name>]`（寫 `decision.dismiss` 並在條目行首加 `✅ dismissed: `）。**NEVER** 手動改 carrier 那一行而不寫事件。

  | REQUIRED 欄位 | 內容 |
  | --- | --- |
  | 觸發條件 | 標題＋第一段命中結案語 ＋ 無未勾 checkbox ＋ 無未答選項 → 標 `self-closed`、不鑄 span、`flow sources` 印一行計數。**warn-only，不 block** |
  | 消費端 | 寫／編那份 carrier 的 agent（看到那一行就搬段或刪）；`flow pending`（少一條問不到人的題） |
  | 觸發點 | 本 Rule（`my/rules/待拍板條目寫法.md`：`my` Phase 1 第 3 步讀取；編輯 `HANDOFF.md`／`docs/tech-debt.md` 時由 hook 提示讀取）；判定器 `vendor/scripts/flow/decision-sources.ts` 的 `isSelfClosed`，對帳在 `decision-sync.ts` |

## Good Example

- 這個例子是好的，因為不再需要人的題經 `flow dismiss` 寫事件，而不是手改那一行。

```bash
node vendor/scripts/flow/flow.ts dismiss 7c1e…a2 --reason '已隨 relay-4 落地，不再需要拍板' --repo <consumer-id>
```

## Bad Example

- 這個例子是壞的，因為它把已結案的條目留在待拍板段，又手動在行首加 ✅ 而沒有寫事件。

```markdown
## Awaiting Charles

- ✅ **要不要換 sync 腳本？** 已拍板 A，已隨 relay-4 落地
```

# Rule 11 - 新問題優先走 `flow ask`，並依題目形狀帶齊必填

- Level: `MUST`
- 要問的題**現在**就成形時，直接開 span，不必等 60 秒掃描。檔案來源與 `flow ask` 寫進的是同一個佇列。
- 問句走 `--question`（**不是** positional），選項走可重複的 `--option`（一條一個旗標）。字母前綴與「（推薦）」由寫入端剝掉，卡片依索引自己編號——選項文字**只寫選項**，寫進字母或「（推薦）」會疊成 `A. A. 改（推薦）（推薦）`。
- **`flow ask` 依形狀檢查必填，缺了就 exit 1 並印出可照抄的改法**（`vendor/scripts/flow/ask-admission.ts`，與 `--complete blocked --decision-for charles` 共用）：

  | 這題要人做什麼 | 必帶 |
  | --- | --- |
  | 選一個（`ruling`／`review`） | 2–4 條 `--option '<短標籤> :: <後果>'`（短標籤 ≤16 字）＋ `--recommended` ＋ `--why` |
  | 給一個值 | `--needs-value` ＋ 每個要填的值一條 `--field '<欄位名>'` |
  | 到場做事（`--category human-action`） | 每個動作一條 `--step '<做什麼>'`；帶選項的到場題則照「選一個」那列給 `--option`＋`--recommended`＋`--why`，`--step` 只在沒有可用選項時必填 |
  | 問 Charles 的 `review`／`human-action` | 再加 `--human-only <理由>`，只收 `account`／`secret`／`external-commitment`／`irreversible`／`physical`／`taste`／`explicit-skill:<skill>`（清單 SoT：`ask-admission.ts` `HUMAN_ONLY_REASONS`；`explicit-skill` 寫入端核對投影與代打範圍；`taste` 要帶存在的 `--evidence <截圖或 URL>` 且該 work 沒有 plan 驗收 feature） |

- **agent 做得了的事不鑄給 Charles**（Charles 2026-10-06：「都不應該問我 都是應該自己做的」）：`--human-only` 一條都對不上就是 agent 自己的事——驗收自己驗（loopback 打同一個端點、跑同一支 CLI、`flow done --verify-cmd`），流程派 session 跑（specify 鏈由派工者代打，見 `rules/core/rule-authoring.md` § Invocation 成本模型）。**NEVER** 為了過 admission 挑一條不成立的理由。畫面／文案品味的正路是 work-route spec-by-example 寫成 plan package `features/acceptance/**` 的 `@human` scenario（Gherkin 的 PM 確認關卡 Charles 已看過），附上新鮮證據後由 `flow gates` 的 ui-judgement 自動出卡；`taste` 只給沒有 plan 驗收 feature 的工作（小修、clade 自家 UI），而且功能對不對（loopback 驗得了的）**NEVER** 算品味。

- 選填：`--deadline <ISO> --deadline-basis '<為什麼是這天>'`（72 小時內到期的卡排最前）、`--dedupe-key <key>`（同 key 的卡還開著時不另鑄，回原卡 span 並標 `deduped`；這次帶的不同卡面——典型是期限——補寫到原卡，期限取最早）。問 agent 的題加 `--audience coordinator`，不受上表限制。
- 手機上第一眼只看得到標題、推薦與理由、短標籤按鈕；長的背景寫進 `--question` 與 carrier。`--headline` 是卡片標題：一句人話的問句，不放 work id／SHA。
- 指令全貌見 `flow指令.md` § ask。

## Good Example

- 這個例子是好的，因為問句與選項各走自己的旗標，短標籤、推薦、理由齊全，標題是人話問句。

```bash
node vendor/scripts/flow/flow.ts ask \
  --headline '舊 sync 腳本要刪還是包相容層？' \
  --question 'scripts/old-sync.ts 已無呼叫端，但兩台 consumer 的 cron 還指著它；要直接刪，還是先包一層相容轉呼叫新腳本？' \
  --option '包相容層 :: 保留檔名轉呼叫新腳本，下一版再刪' \
  --option '直接刪 :: 兩台 cron 下次跑會失敗，需同步改 crontab' \
  --recommended '包相容層' \
  --why 'cron 在客戶機上，改 crontab 要等維護窗' \
  --carrier HANDOFF.md
```

## Bad Example

- 這個例子是壞的，因為問句當 positional、選項塞進一個逗號字串、標題放 work id，且缺推薦與理由——ask 會 exit 1。

```bash
node vendor/scripts/flow/flow.ts ask 'W-2026-10-01-sync: 刪還是包？' --options 'A. 刪（推薦）,B. 包'
```

# Rule 12 - dispatch 出去的 pane 走 `--complete blocked`，`--decision-for` 預設 coordinator

- Level: `MUST`
- pane 裡問的題不經 `flow ask`，走的是 completion handshake，選項一樣 MUST 走旗標：

  ```bash
  node vendor/scripts/herdr-session-handoff.ts --complete blocked \
    --summary '<目前狀態>' \
    --decision '<只問一個具體問題>' \
    --decision-option '<短標籤> :: <後果>' --decision-option '<短標籤> :: <後果>' \
    [--decision-recommended '<短標籤>' --decision-why '<一句為什麼>'] \
    [--decision-for coordinator|charles]
  ```

- `--decision-for charles` 的題過同一份 admission（Rule 11 的表）：選一個就 MUST 帶短標籤選項＋`--decision-recommended`＋`--decision-why`；要一個值就改帶 `--decision-field '<欄位名>'`。問 coordinator（預設）的題不受限。
- **你有 parent。** dispatch 出去的 pane 問的題，絕大多數 coordinator 當場裁決得了：

  | 值 | 這題會怎樣 |
  | --- | --- |
  | `coordinator`（預設） | 照樣鑄 `decision.request`（`payload.audience: 'coordinator'`）、照樣送控制訊息喚醒 parent pane，但**不在** `flow pending` 的預設佇列上（`--audience all` 才顯示） |
  | `charles` | 進人的佇列。parent pane 還活著時 helper 印一行 warn（不擋） |

- **MUST `--decision-for charles` 的判準是「這題只有 Charles 答得了」**（實機、線上帳號、對外承諾、密鑰、不可逆且他要負責的）。**NEVER** 因為「這題比較重要」就寫 `charles`。
- **coordinator 的題照樣是 span，這一點 NEVER 拿掉。** **parent 回答之後 MUST 跑 `flow answer <span_id> --answer '<答案>'`**——口頭裁決不落檔，那題會以 `answer-not-filed` 躺在停滯清單上。
- child 判出「只有 Charles 答得了」時仍走 `--decision-for charles`，**NEVER** 自己在對話裡問 principal。`CLADE_DISPATCH_ID` 非空時，final response 裡的提問不是授權通道（TD-901）。

  | REQUIRED 欄位 | 內容 |
  | --- | --- |
  | 觸發條件 | `--decision-for charles` 且 parent pane 的 wake 真的送達 → helper 收據帶 `warning`。**warn-only，不擋**：有些題就是要人，coordinator 在場不改變這件事 |
  | 消費端 | worker（填欄位）、coordinator（收控制訊息並 `flow answer`）、`flow pending`（預設只顯示 `audience: charles`） |
  | 觸發點 | 本 Rule（`my/rules/待拍板條目寫法.md`：`my` Phase 1 第 3 步讀取，`my` Phase 1 第 1 步的 worker 分支走這條）＋ `rules/core/session-tasks.operations.md` § Herdr session transport；helper 的 completion handshake 樣板每次 dispatch 逐字帶給 worker |

## Good Example

- 這個例子是好的，因為 worker 問的是 coordinator 裁決得了的題，走預設 audience，不在 final response 問 principal。

```bash
node vendor/scripts/herdr-session-handoff.ts --complete blocked \
  --summary 'migration 寫完，兩個 seed 檔衝突' \
  --decision '衝突的 seed 要保留哪一份？' \
  --decision-option '保留新版 :: 舊 fixture 測試要跟著改' \
  --decision-option '保留舊版 :: 新欄位改成 nullable'
```

## Bad Example

- 這個例子是壞的，因為 worker 在 final response 直接問 Charles，又因為「重要」就把一題 coordinator 答得了的題寫成 `charles`。

```md
（final response）Charles，seed 衝突要留哪份？A 新版 B 舊版——這題很重要所以直接問你。
--decision-for charles
```

# Rule 13 - 一個拍板題只問一個問題，底下的 bullet 是選項 NEVER 是項目

- Level: `MUST`
- 拍板題底下的 bullet MUST 是同一個問題的**替代方案**。兩件互不相干的事綁成一題時，那幾條 bullet 是**項目**不是替代方案（「或逐條指定即可」就是自白），解析不到、以空白輸入框上手機。
- 這種情況 **MUST 拆成兩題**，各自帶自己的 A／B。

## Good Example

- 這個例子是好的，因為兩條 TD 各自成題，各有自己的替代方案。

```markdown
- 🟡 **TD-309 的 Status 要不要改成 `done`？**
  - **A（推薦）改成 done** —— 驗收證據已齊，從 open 清單移除
  - **B 維持 open** —— 等下一版再驗
- 🟡 **TD-305 的 Status 要不要改成 `wontfix-until-signal`？**
  - **A（推薦）改** —— 停止追蹤，等外部訊號再開
  - **B 維持 open** —— 繼續占 open 清單
```

## Bad Example

- 這個例子是壞的，因為兩條互不相干的 TD 綁成一題，底下兩條是項目不是選項。

```markdown
- [ ] 🟡 **兩條 TD 的 Status 要不要照建議改？**（回「兩條都改」或逐條指定即可）
  - **TD-309 → `done`（推薦）**：…
  - **TD-305 → `wontfix-until-signal`（推薦）**：…
```

# Rule 14 - 在 chat 渲染過的 `Qn` 選項 MUST 同一個 turn 落 carrier

- Level: `MUST`
- 在對話裡渲染成 `Q1` ＋ A／B／C **不是登記**——`\my` 與 `flow pending` 讀 spine，spine 讀 carrier。
- **MUST 同一個 turn 兩邊都寫**：選項逐字寫進 carrier 的 bullet（或 `flow ask --option`）。
- **NEVER** 想著「等下再補進 HANDOFF」——沒選項的題 ingest 端會拒鑄 span，只剩一行給寫的人的退件。

## Good Example

- 這個例子是好的，因為對話裡出 Q1 的同一個 turn 就跑了 `flow ask`，選項逐字一致。

```md
（同一個 turn）
flow ask --headline '舊 sync 腳本要刪還是包相容層？' --option '包相容層 :: …' --option '直接刪 :: …' …
→ 對話：Q1 舊 sync 腳本要刪還是包相容層？ A. 包相容層（推薦） B. 直接刪 [本輪從對話撈出]
```

## Bad Example

- 這個例子是壞的，因為選項只存在對話裡，下一個 session 的佇列看不到這題。

```md
Q1 舊 sync 腳本要刪還是包？ A. 刪 B. 包（推薦）
（之後再補進 HANDOFF）
```

# Rule 15 - NEVER 把選項寫進問句本文

- Level: `MUST`
- `要留哪一個？(A) 留 X (B) 停 Y` 的 `options` 是空的，手機上退化成自由填答。
- `flow ask` 與 `--complete blocked` 兩個入口都會擋；擋不到的變體同樣禁止——**選項的載體是旗標，不是句子**。

## Good Example

- 這個例子是好的，因為問句只問問題，選項各走一個旗標。

```bash
flow ask --question '兩個 dev server 要留哪一個？' \
  --option '留 X :: 停掉 Y 的 3001 port' --option '停 Y :: 保留 X 的 3000 port' \
  --recommended '留 X' --why 'X 是本 session 啟的'
```

## Bad Example

- 這個例子是壞的，因為選項寫在問句裡，`options` 為空。

```bash
flow ask --question '要留哪一個？(A) 留 X (B) 停 Y'
```

# Rule 16 - NEVER 把該協調的事開成拍板題

- Level: `MUST`
- 「哪個 session／pane／worktree 該留下」「誰先 commit」這類題**球在 agent 手上**，不是裁決。
- MUST 先跑 [[session-tasks]] § 並行爭用 的 Step 0 判出持有者，再問它還要多久 land／要不要合併（對方是 Claude 用 `SendMessage`，非 Claude 才送 `herdr agent prompt`）。
- 談過之後仍談不攏的那一題才進佇列，且問句 MUST 寫明已探測、對方怎麼回。

## Good Example

- 這個例子是好的，因為先探測持有者並協調，談不攏才進佇列，問句寫明探測結果。

```md
Step 0 判出 w2:p1 持有 HANDOFF.md 的 dirty 變更 → SendMessage 問它多久 land
w2:p1 回：「要等 Charles 決定 schema 才能 land」
→ flow ask --question '已探測 w2:p1：它卡在 schema 選擇、無法先 land；schema 要用 A 還是 B？' …
```

## Bad Example

- 這個例子是壞的，因為它把 agent 之間的協調直接丟給 Charles。

```md
Q1 兩個 session 都改了 HANDOFF.md，要留哪一個？ A. 留 w2 B. 留 w3
```

# Rule 17 - NEVER 把 live change 的 `## 人工檢查` 寫成登記簿條目

- Level: `MUST`
- 逐條驗收是**人工驗收**（`ui-judgement` 卡 → `flow receipt`）的職責，所以 `HANDOFF.md`／`docs/tech-debt.md` 的條目 **NEVER** 承載「去把 `<change>` 的 `## 人工檢查` 逐條確認」：

  | `flow gates` 對那件 work 的輸出 | 這條 bullet 是什麼 | MUST |
  | --- | --- | --- |
  | 已有對應的 `ui-judgement` 卡（票已經在人的佇列上） | 重複——同一個判定由兩個畫面各要一次 | 刪掉這條 bullet |
  | 沒有卡（evidence 缺或過期——**agent 的球**，機械待辦 NEVER 成卡） | 繞道——卡出不來，於是改用登記簿叫人做 | 補齊缺的 evidence 讓卡出現，**再**刪掉這條 |

- **判之前 MUST 實跑**，NEVER 從「我記得它已經做完了」推斷（cwd = 該 repo，**NEVER** 帶 `CLADE_HOME`）：

  ```bash
  node ~/offline/clade/vendor/scripts/flow/flow.ts gates --repo-only --json
  ```

- **NEVER 代勾 `## 人工檢查` 的 checkbox 讓這條消失**（false-green，[[agent-self-verification]] MUST 8）。
- 已封存的 work item（`tasks/` 子目錄）不是佇列輸入，不在此列。

  | REQUIRED 欄位 | 內容 |
  | --- | --- |
  | 觸發條件 | 條目文字同時含 `人工檢查` 與某個 **live** change 的目錄名 → `belongs-on-review` lint ＋ 不合成 通過／退回。**warn-only，不 block，且 NEVER 拒鑄 span**（路由錯誤，擋掉會讓繞道變隱形） |
  | 消費端 | 寫該條目的 agent（看到 `✎` 評語照上表處置）＋ Charles。說明文字由 `LINT_NOTES['belongs-on-review']` 渲染，NEVER 由 agent 寫進人的佇列 |
  | 觸發點 | 本 Rule（`my/rules/待拍板條目寫法.md`：`my` Phase 1 第 3 步讀取；編輯 `HANDOFF.md`／`docs/tech-debt.md` 時由 hook 提示讀取——寫那條 bullet 正是在編輯這兩個檔） |

## Good Example

- 這個例子是好的，因為它先實跑 `flow gates`，依輸出決定刪 bullet 或先補 evidence。

```md
flow gates --repo-only --json → clock-shift-select 已有 ui-judgement 卡
→ 刪掉 HANDOFF 那條「去確認 clock-shift-select 的 ## 人工檢查」
```

## Bad Example

- 這個例子是壞的，因為它用登記簿繞道叫人逐條驗，又代勾 checkbox 讓 lint 消失。

```markdown
## Awaiting Charles

- 🔴 **去把 clock-shift-select 的 ## 人工檢查 逐條確認**
（同時把 tasks.md 的 [review:ui] 先勾掉）
```

# Rule 18 - 答案落檔失敗由 `answer-not-filed` 偵測，用 `flow relend` 補，NEVER 要人重答

- Level: `MUST`
- Carrier 是別的 session 也在寫的檔，答案附上去可能被整段覆寫。`flow status --stalled` 會列 `answer-not-filed` 並印出重新歸檔的指令：

  ```bash
  node vendor/scripts/flow/flow.ts relend <span_id>
  ```

- 每個 attended session 開頭 MUST 取得一次 `flow status --stalled` 的實際結果：已驗證的 session-start hook（`session-start-stalled.sh`）可自動提供，否則自己跑 `node scripts/flow/flow.ts status --stalled`（clade 用 `vendor/scripts/flow/flow.ts`）。設定檔或空白輸出不證明 hook 執行過；工具不可達就回報檢查未完成。
- `relend` 從 spine 重建區塊放回、重跑是 no-op。**NEVER 因為看到這一行就去要人重答一次。**
- **判準是「有沒有決策紀錄區塊」，NEVER 是「有沒有提到那個 span id」**；搬進 `docs/archives/` 算已落檔。

  | REQUIRED 欄位 | 內容 |
  | --- | --- |
  | 觸發條件 | 已答（非 retracted）× 有指定 carrier × repo 內找不到它的決策紀錄區塊 × 超過 10 分鐘寬限 → `flow status --stalled` 列一行、exit 3。**warn-only，不 block** |
  | 消費端 | 每個 attended session 的 agent，透過已驗證的 session-start hook 或上段顯式 CLI 取得結果；讀到就照 `relend` 指令處置 |
  | 觸發點 | 本 Rule；停滯輸出自帶 action 句，不需要先知道要去看 |

## Good Example

- 這個例子是好的，因為看到 `answer-not-filed` 就用 `relend` 從 spine 重建，不打擾 Charles。

```bash
node vendor/scripts/flow/flow.ts status --stalled
# answer-not-filed 7c1e…a2 → node vendor/scripts/flow/flow.ts relend 7c1e…a2
node vendor/scripts/flow/flow.ts relend 7c1e…a2
```

## Bad Example

- 這個例子是壞的，因為答案已在 spine 上，卻要人再答一次；又用「有沒有提到 span id」判斷是否落檔。

```md
grep 到 HANDOFF 有提到 7c1e…a2 → 算已落檔
另一題看不到 block → 在 \my 裡重新問 Charles 一次
```

# Rule 19 - 寫完 `HANDOFF.md`／`docs/tech-debt.md` MUST 當下檢查 ruling 沒帶選項

- Level: `MUST`
- 每次寫完 `HANDOFF.md`／`docs/tech-debt.md`，就地檢查「ruling 但沒有選項」：已接通的 `PostToolUse` hook 會跑共同 lint 並印 `OPTIONS_REQUEST_TEXT`；沒有 hook 觸發證據時寫完立即跑 `node scripts/flow/decision-lint.ts <repo-root> <edited-file>`（clade 用 `vendor/scripts/flow/decision-lint.ts`，參數用絕對路徑），讀 stderr 修正（exit 0 不代表條目完整）。
- 這是同一判準三個時刻裡唯一還能補救的那一個。
- **NEVER 在 hook 裡自己解析 markdown**——第二份 matcher 遲早與佇列不一致。

  | REQUIRED 欄位 | 內容 |
  | --- | --- |
  | 觸發條件 | 剛寫入的檔裡有 `no-options-under-ruling` 的條目 → 印到 stderr。**warn-only，一律 exit 0，NEVER 擋下 Edit**——`HANDOFF.md` 是高頻活文件，擋寫入買到的是繞過旗標不是更好的 bullet |
  | 消費端 | 剛寫下那條 bullet 的 agent（本 Rule）；判準與措辭走 `vendor/scripts/flow/decision-lint.ts` → `decision-sources.ts` 的 scanner ＋ `decisions.ts` 的 `OPTIONS_REQUEST_TEXT` |
  | 觸發點 | 本 Rule（編輯 `HANDOFF.md`／`docs/tech-debt.md` 時由 hook 提示讀取）；Hook 與顯式 CLI 共用 lint 輸出 |

## Good Example

- 這個例子是好的，因為沒有 hook 觸發證據時，寫完立即跑共同 lint 並讀 stderr。

```bash
node <clade-central-repo>/vendor/scripts/flow/decision-lint.ts \
  <home>/offline/<consumer-id> <home>/offline/<consumer-id>/HANDOFF.md
# stderr: no-options-under-ruling … → 補上 A/B 選項
```

## Bad Example

- 這個例子是壞的，因為它在 hook 裡自己寫 regex 判斷選項，形成第二份 matcher。

```bash
grep -A3 'Awaiting Charles' HANDOFF.md | grep -q '\*\*A' || echo '沒有選項'
```

# Rule 20 - 改寫問句 = 換一題；改說明或選項文字 = 同一題

- Level: `MUST`
- `source_id` 由 identity（檔案 ＋ 問句）導出，**不由內容**。因此：
  - **改寫說明、補一段 context、調整選項文字 → 同一題**，不會重問，佇列上那題的選項會在下一次掃描就地更新（`decision-sync.ts` 的 amend）
  - **改寫問句本身 → 換一題**：舊的撤回、新的重開。要重問就改問句
- **NEVER** 為了讓一題重新出現而刪掉再貼回——刪掉那一刻它會被記成 `retracted`（來源消失），不是被裁決。

## Good Example

- 這個例子是好的，因為只補 context 與調整選項文字，問句不動，佇列上就地更新。

```markdown
- 🔴 **舊 sync 腳本要刪還是包相容層？** —— 補充：<consumer-id> 的 cron 每天 03:00 跑
  - **A（推薦）包相容層** —— 保留檔名轉呼叫新腳本，下一版再刪
  - **B 直接刪** —— 需同步改兩台 crontab
```

## Bad Example

- 這個例子是壞的，因為它為了讓題目重新出現而刪掉再貼回，那一題被記成 `retracted`。

```md
（刪掉整條 bullet，存檔）
（再把同一條貼回去，存檔）
```

# Rule 21 - 編輯既有不合格條目時 MUST 順手轉正

- Level: `MUST`
- **每一次**編輯一條已經在待拍板區段、但不符本檔形狀的 bullet 時，都 MUST 一併把它改成合格形狀（`flow pending` 與 `\my` 的 `✎ 來源檔有幾行差一點就是選項` 就是給寫的人的提示）。

  | REQUIRED 欄位 | 內容 |
  | --- | --- |
  | 觸發條件 | item 落 ruling 桶且無選項（`no-options-under-ruling`）、body 含差一點就解析成功的行（`near-miss-option-line`），或 item 落 review 桶而三欄沒寫齊／證據不可點（`missing-evidence`）。**寫入路徑上三者都 warn-only、不 block**。**ingest 路徑上前者與後者拒鑄 span**（`decision-sync.ts` 的 `REJECTING_LINTS`），改成 `flow sources` 與 `handoff-scan` 的退件行並計入 exit code。`near-miss-option-line` 是**評語不是退件碼**，NEVER 拿它擋 ingest |
  | 消費端 | carrier 作者（退件收件人）＋ `flow pending` 上的 Charles |
  | 觸發點 | 本 Rule（`my` Phase 1 第 3 步讀取；編輯 `HANDOFF.md`／`docs/tech-debt.md`／work-loop state 時由 hook 提示讀取——也就是寫這種條目的當下） |

## Good Example

- 這個例子是好的，因為改一條舊 bullet 的說明時，順手把差一點就是選項的行轉成合格選項。

```markdown
改前：
- 🔴 **要不要換 sync 腳本？**
  - A. 直接刪 / B. 包相容層

改後：
- 🔴 **要不要換 sync 腳本？** —— cron 還指著舊檔
  - **A（推薦）包相容層** —— 保留檔名轉呼叫新腳本，下一版再刪
  - **B 直接刪** —— 需同步改兩台 crontab
```

## Bad Example

- 這個例子是壞的，因為只改了自己要改的那句，留下一條會繼續掛 `near-miss-option-line` 的不合格 bullet。

```markdown
- 🔴 **要不要換 sync 腳本？**（已補：cron 在客戶機上）
  - A. 直接刪 / B. 包相容層
```

# Rule 22 - 要 Charles 看 diff 才能判的條目 MUST 附 pulls.review 指令

- Level: `MUST`
- **每一條**要 Charles 讀程式碼變更才能判的條目（等人的 PR、Charles-only leftover、完成報告裡的落地內容），**MUST** 在條目裡附一行可以直接貼進 terminal 的指令：PR 用 `node scripts/pulls-review.ts <PR 編號>`，已落地的 commit 或範圍用 `node scripts/pulls-review.ts <sha 或 A...B>`（clade home 的路徑是 `vendor/scripts/pulls-review.ts`）。
- 指令開的是分組過的本機閱讀頁；AI 分組要 Charles 在頁面上按才會跑。**NEVER** 由 agent、hook、gate 或 batch 指令代跑這支 script 或替他觸發分析。頁面上的「Share result」會把分析貼成 PR 留言，同樣 **NEVER** 由 agent 代按。
- **NEVER** 改貼 `https://pulls.review/gh/…` 網址代替指令：私有 repo 在站上要另存 token，而且只有本機版能用本機 Claude Code 分析。
- 不需要讀 diff 就能判的條目（選方案、給值、到場動作）不附。

  | REQUIRED 欄位 | 內容 |
  | --- | --- |
  | 觸發條件 | informational — 不觸發任何東西（條目有沒有附指令沒有 detector） |
  | 消費端 | 寫等人條目的 agent（附指令）＋讀條目的 Charles（貼進 terminal 開閱讀頁） |
  | 觸發點 | skill SOP 的 READ step：`commit` 的 `gates.md` § 0-MR exit 3、`batch.md` 的 `batch yield-blocked` 回報、`SKILL.md` Step 7；`my` Phase 1 第 3 步讀取本檔 |

## Good Example

- 這個例子是好的，因為等人的 PR 帶著判斷題，也帶著一行可直接執行的閱讀指令。

```text
✅ 0-MR auto-triage 完成，等人 1 張
- #482 [ruling] 打卡頁要不要擋未選班別的打卡？
  閱讀：node scripts/pulls-review.ts 482
```

## Bad Example

- 這個例子是壞的，因為只給 PR 編號，Charles 要自己去 github.com 翻 Files changed；另一行替他把分析跑掉了。

```text
- #482 等你看一下 diff
（已先跑 pulls.review 分析好了）
```

# Rule 23 - `flow ask` 因「已有答案」或「repo 不在 roster」被拒時，照拒收句做，NEVER 換寫法硬問

- Level: `MUST`
- `flow ask` 在寫入前做兩道檢查，兩道都只對問 Charles 的題（`--audience charles`，預設值）：

  | 拒收句開頭 | 成因 | 處置 |
  | --- | --- | --- |
  | `這個 carrier（…）14 天內已經有 Charles 的答案，不再問一次` | 同一個 repo、同一個 carrier 已有答過的題。TD entry 與帶 `#anchor` 的 carrier：任何一題答過就算；整份檔的 carrier（`HANDOFF.md`、`plan.md`）：問句相同或 `--dedupe-key` 相同才算 | 拒收句逐條印出既有答案與日期：**照那個答案做**，不再問。現況確實變了才加 `--supersede <那一題的 span id>`，並在 `--question` 寫明什麼變了 |
  | `這個 repo（…）不在 flow roster 上` | cwd 的 repo 在 clade 旁邊、卻不在 `registry/consumers.json` 上，`flow pending` 讀不到它的 spine | 照拒收句三條改法擇一：登記進 registry、改到題目真正所屬的 checkout 問、或這題是問 agent 的就加 `--audience coordinator` |

- **NEVER** 為了通過檢查而拿掉 `--carrier`、換一個 carrier、改寫問句，或不讀既有答案就加 `--supersede`——那一題的答案 Charles 已經給過。
- `--supersede` 指到的 span 會記在新題的 `payload.supersedes`。

## Good Example

- 這個例子是好的，因為被拒之後照既有答案做，沒有再問。

```md
flow ask 被拒：TD-047 在 2026-10-05 已有答案「提供來源再補」（span 4175…5d）。
照既有答案處理：本輪不動 TD-047，等來源提供。
```

## Bad Example

- 這個例子是壞的，因為它拿掉 `--carrier` 讓同一題重新進佇列，Charles 會被問第二次。

```bash
node ~/offline/clade/vendor/scripts/flow/flow.ts ask --question 'TD-047 的教師資料來源要補嗎？' \
  --option '補 :: …' --option '不補 :: …' --recommended '補' --why '…'   # 原本帶 --carrier TD-047 被拒
```
