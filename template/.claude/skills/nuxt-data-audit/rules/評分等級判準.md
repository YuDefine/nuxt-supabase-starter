
# Rule 1 - 依安全 → 完整性 → HR／SR 的順序判 grade

- Level: `MUST`
- 由上往下第一個命中的列即 grade。N/A 排除分母；unknown **NEVER** 併入 pass，並列出缺少的證據。

| Grade | 條件 |
| --- | --- |
| F | 已確認 E11 跨 request 資料污染，或 E15 認證／快取隔離缺陷 |
| incomplete | 任一適用項目仍 unknown，或 reference rule／範圍尚未查清 |
| A | 所有適用 HR pass，且適用 SR 至少 80% pass |
| B | 所有適用 HR pass，SR 未達 A |
| C | 至少 3 個適用 HR pass，且有 HR fail／partial |
| D | 其餘有 HR fail／partial 的情形 |

- HR＝E1、E3、E4、E9、E10、E18、E19，對應 reference rule 的 HR-1～HR-7。E2 的 custom key 是額外檢查；E11、E15 的安全缺陷優先判 F。其他適用項目納入 SR；`E15-performance` 單列 SR。
- 沒有適用 SR 時，A 的 SR 條件記為 N/A；沒有任何適用項目時報 N/A，**NEVER** 給 A。

## Good Example

- 這個例子是好的，因為 HR 全過但 E18 仍有 unknown，先判 incomplete 而不是 A。

```text
HR: E1 pass, E3 pass, E4 pass, E9 N/A, E10 N/A, E18 unknown, E19 pass
→ Grade: incomplete（E18 缺 interceptor 是否保留 signal 的證據）
```

## Bad Example

- 這個例子是壞的，因為 E15 已確認跨使用者快取外洩，卻按 HR 通過率給 B。

```text
HR 全 pass，SR 70%，E15 fail（getKey 未含 user id）→ Grade: B
```

# Rule 2 - grade 只供讀者排查，不新增 gate

- Level: `MUST`
- grade 是 informational，不觸發任何東西，**NEVER** 據此新增 publish gate。F 的安全缺陷按既有授權修正或交付對應 consumer；incomplete 保留待查證據。報告輸出即 baseline，**NEVER** 另存到 HANDOFF 或其他登記簿。

## Good Example

- 這個例子是好的，因為 F 交給 consumer 修，報告本身留作下次比對。

```text
Grade F（E15）→ 對 consumer 開修正工作；本報告即本輪 baseline
```

## Bad Example

- 這個例子是壞的，因為把 grade 抄進 HANDOFF 的稽核 baseline 表。

```text
HANDOFF.md ## 稽核 baseline | nuxt-data-audit | <consumer-id> C |
```
