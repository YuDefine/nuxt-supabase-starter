
# 共通判定原則

- Level: `MUST`
- 候選命中（`--candidates` 輸出）只是線索；逐筆讀實際呼叫與資料路徑後才評分。零命中、檔案數或函式名稱數量 **NEVER** 等於行為已驗證。
- 沒有適用對象記 N/A 並寫已查範圍；尚未讀完呼叫鏈或缺執行證據記 unknown。這兩種狀態 **NEVER** 算 pass。
- non-Colada consumer（`stack.notApplicable` 含 E9、E10）：E9、E10 記 N/A，其餘全部適用。
- 每項對照 reference rule `nuxt-data-perf` 的對應 HR／SR 條文判斷。

# Rule 1 - E1 setup 無裸 $fetch（HR-1）

- Level: `MUST`
- 追查初始資料載入的實際呼叫路徑，包括 setup 呼叫的 helper 與 `$csrfFetch` 等 alias。函式包裝本身不提供 SSR payload 保護。
- pass：初始資料由 useFetch／useAsyncData／useQuery 等適用機制承接，其他 `$fetch` 只由事件等非初始載入入口觸發。
- fail：setup 初始載入直接或經 helper 呼叫裸 `$fetch`。

## Good Example

- 這個例子是好的，因為初始載入走 useFetch，`$fetch` 只在按鈕事件。

```vue
<script setup>
const { data } = await useFetch('/api/rows')
const save = () => $fetch('/api/rows', { method: 'POST', body: form })
</script>
```

## Bad Example

- 這個例子是壞的，因為 helper 把裸 `$fetch` 包起來仍在 setup 執行，SSR 與 client 各打一次。

```vue
<script setup>
const rows = await loadRows() // loadRows() 內部是 $fetch('/api/rows')
</script>
```

# Rule 2 - E2 custom composable 的 useFetch 有 key（HR-4 useFetch 部分）

- Level: `MUST`
- custom composable（`composables/*.ts`、`queries/*.ts`）內的 useFetch／useAsyncData 手動指定 key；page／component 內自動產生 key 通常 OK，不列入分母。
- pass：所有 custom composable 都明確給 key。fail：任一 custom composable 依賴自動 key。

## Good Example

- 這個例子是好的，因為 composable 被多處呼叫時 key 穩定。

```ts
export const useOrders = (status: Ref<string>) =>
  useFetch('/api/orders', { key: () => `orders:${status.value}`, query: { status } })
```

## Bad Example

- 這個例子是壞的，因為自動 key 依呼叫位置產生，composable 內的呼叫會撞 key 或無法共用快取。

```ts
export const useOrders = (status: Ref<string>) => useFetch('/api/orders', { query: { status } })
```

# Rule 3 - E3 重複請求處理正確（HR-2）

- Level: `MUST`
- **NEVER** 把「0 處 dedupe」直接判 fail——預設 `'cancel'` 對「只要最新結果」的場景本來就是正解。`defer` 只在「同一個 key 有 in-flight request」時生效，逐個 call site 對照 HR-2。

| 觀察到的情形 | 評分 |
| --- | --- |
| 搜尋框／篩選器被加了 `dedupe: 'defer'` | **fail**（引入 bug：回傳舊關鍵字的 promise） |
| key 隨輸入變動的 query 加了 `'defer'` | **fail**（無效程式碼：該分支永遠走不到） |
| 輸入框觸發 fetch 但無 debounce，且舊請求不 abort | **fail**（請求放大） |
| 同一 key 的冪等重複觸發（連點 refresh）未處理 | partial |
| 全部維持預設 `'cancel'`，且無請求放大 | **pass** |

## Good Example

- 這個例子是好的，因為搜尋框維持預設 `'cancel'` 並 debounce，舊請求被取消。

```ts
const q = refDebounced(input, 300)
const { data } = useFetch('/api/search', { query: { q } })
```

## Bad Example

- 這個例子是壞的，因為 `defer` 會回傳舊關鍵字那次的 promise。

```ts
const { data } = useFetch('/api/search', { query: { q: input }, dedupe: 'defer' })
```

# Rule 4 - E4 reference data 有 cache 策略（HR-3）

- Level: `MUST`
- 先列出 HR-3 所指的低變動 reference data，再追查每個呼叫的有效 cache 設定（含共用 defaults）：Colada 看 `staleTime`，non-Colada 看 `getCachedData`。一般即時 query 不放入此項分母。
- pass：全部適用呼叫符合 HR-3。fail：任一適用呼叫不符。

## Good Example

- 這個例子是好的，因為部門清單是低變動資料，設了 staleTime。

```ts
useQuery({ key: deptKeys.all, query: fetchDepartments, staleTime: 5 * 60_000 })
```

## Bad Example

- 這個例子是壞的，因為每次進頁都重抓不會變的下拉選項。

```ts
useFetch('/api/departments')
```

# Rule 5 - E5 大 payload 有 pick／transform（SR-1）

- Level: `MUST`
- 先對照大 payload 的實際回應與使用欄位。
- pass：已在 server 選欄位，或 client pick／transform 已縮到需求範圍。fail：確認傳輸／SSR payload 有不必要的大量資料。unknown：只有函式名稱，沒有 payload 或欄位證據。

## Good Example

- 這個例子是好的，因為列表只取顯示用的三欄。

```ts
useFetch('/api/orders', { pick: ['id', 'title', 'status'] })
```

## Bad Example

- 這個例子是壞的，因為整列（含大 JSON 欄位）進 SSR payload，頁面只顯示 title。

```ts
const { data } = useFetch('/api/orders') // 每列帶 attachments、history
```

# Rule 6 - E6 Lazy 元件用對地方且有 hydration strategy（SR-2）

- Level: `MUST`
- **NEVER** 用「Lazy 用得多＝好」評分——`<Lazy*>` 只做 code-split，不搭 strategy 完全不省 hydration。
- 依 SR-2 逐個判斷首屏原子元件、非首屏重元件與實際 hydration 路徑。確認有 Lazy 原子元件濫用（候選 `E6-atomic`），或適用的非首屏重元件缺策略／策略失效＝fail；所有適用元件符合規約＝pass。
- 沒有延遲載入需求記 N/A；strategy 數為零本身不構成 fail。SPA 的 code splitting 與 SSR hydration 分開評估（`ssr: false` 時 hydration strategy 不適用）。

## Good Example

- 這個例子是好的，因為非首屏重圖表延遲並在可見時才 hydrate。

```vue
<LazyOrderChart hydrate-on-visible :data="data" />
```

## Bad Example

- 這個例子是壞的，因為首屏輕量原子元件被 Lazy，多一次 chunk 請求而無收益。

```vue
<LazyUButton label="儲存" />
```

# Rule 7 - E7 routeRules 有 performance 設定（SR-3）

- Level: `MUST`
- 逐條檢查 public／landing routes 是否依內容更新需求採用 SR-3 策略，並核對部署支援。
- 只有私人／個人化 routes 時記 N/A；**NEVER** 為取得 pass 而對私人資料加共享快取。

## Good Example

- 這個例子是好的，因為公開 landing 用 prerender，私人後台不加快取。

```ts
routeRules: { '/': { prerender: true }, '/admin/**': { ssr: false } }
```

## Bad Example

- 這個例子是壞的，因為個人化 dashboard 被加上共享 swr 快取。

```ts
routeRules: { '/dashboard': { swr: 600 } }
```

# Rule 8 - E8 NuxtImg 最佳化（SR-5）

- Level: `MUST`
- pass：`@nuxt/image` 已安裝且 NuxtImg 有 format／loading（或 fetchpriority／preload）設定。partial：裝了但沒 optimize。N/A：沒裝（不強制）。

## Good Example

- 這個例子是好的，因為指定格式與延遲載入。

```vue
<NuxtImg src="/hero.jpg" format="webp" loading="lazy" sizes="sm:100vw md:50vw" />
```

## Bad Example

- 這個例子是壞的，因為裝了模組卻只當 `<img>` 用。

```vue
<NuxtImg src="/hero.jpg" />
```

# Rule 9 - E9 Colada key factory（HR-4，Colada only）

- Level: `MUST`
- 逐個追查 useQuery／useMutation 的實際 key 來源，包含封裝與共用 defaults。factory 定義數量 **NEVER** 代表呼叫端採用率。
- pass：全部適用 key 來自集中 factory。fail：任一散落 magic string key。

## Good Example

- 這個例子是好的，因為 key 來自集中 factory。

```ts
useQuery({ key: orderKeys.detail(id), query: () => fetchOrder(id) })
```

## Bad Example

- 這個例子是壞的，因為 magic string key 讓 invalidate 對不上。

```ts
useQuery({ key: ['order', id], query: () => fetchOrder(id) })
```

# Rule 10 - E10 useMutation 有 cache invalidation（HR-5，Colada only）

- Level: `MUST`
- 逐個 mutation 追查 onSuccess／onSettled（含共用封裝），確認 `invalidateQueries` 的 key 涵蓋受影響 query。同檔存在 `invalidateQueries` **NEVER** 代表該 mutation 已接上。
- pass：全部符合 HR-5。fail：任一缺失或 key 錯誤。

## Good Example

- 這個例子是好的，因為 mutation 完成後 invalidate 受影響的列表。

```ts
useMutation({ mutation: createOrder, onSettled: () => queryCache.invalidateQueries({ key: orderKeys.list() }) })
```

## Bad Example

- 這個例子是壞的，因為新增成功後列表仍是舊資料。

```ts
useMutation({ mutation: createOrder })
```

# Rule 11 - E11 無跨 request state 污染（安全項）

- Level: `MUST`
- 追查 server 可達的 module-scope 可變 state 與 request 隔離。
- fail：確認跨 request 共用使用者資料（Grade 直接 F，見 `rules/評分等級判準.md`）。pass：完成適用路徑查核且 state 隔離。SSR 不可達的 client-only state 不據此判污染；零搜尋命中但未完成查核＝unknown。

## Good Example

- 這個例子是好的，因為使用者 state 放進 Pinia／useState，每個 request 一份。

```ts
export const useCurrentUser = () => useState<User | null>('current-user', () => null)
```

## Bad Example

- 這個例子是壞的，因為 module-scope ref 在 SSR server 上被所有 request 共用。

```ts
export const currentUser = ref<User | null>(null)
```

# Rule 12 - E12 Error handling 完整

- Level: `SHOULD`
- 對 useFetch／useQuery 呼叫檢查 `error` 是否被 template 消費（`v-if="error"`、`{{ error }}`）或 watch。
- pass：> 50% 有 error 消費。partial：< 50%。fail：0。

## Good Example

- 這個例子是好的，因為錯誤有呈現給使用者。

```vue
<UAlert v-if="error" color="error" :title="error.message" />
```

## Bad Example

- 這個例子是壞的，因為請求失敗時畫面只是空白列表。

```vue
<script setup>const { data } = await useFetch('/api/rows')</script>
```

# Rule 13 - E13 平行 request 用 Promise.all

- Level: `MAY`
- advisory：有就加分，不扣分。

## Good Example

- 這個例子是好的，因為互不相依的請求平行送出。

```ts
const [a, b] = await Promise.all([$fetch('/api/a'), $fetch('/api/b')])
```

## Bad Example

- 這個例子是壞的，因為互不相依的請求被串成瀑布。

```ts
const a = await $fetch('/api/a')
const b = await $fetch('/api/b')
```

# Rule 14 - E14 watch／immediate 合理

- Level: `MUST`
- 逐個呼叫對照觸發需求，包含預設 watch／immediate、reactive key 與顯式 refresh。維持預設值本身不扣分。
- pass：行為符合需求。fail：確認漏載或多次觸發。

## Good Example

- 這個例子是好的，因為使用者按下查詢才抓，且只在送出時觸發。

```ts
const { data, execute } = useFetch('/api/report', { query, immediate: false, watch: false })
```

## Bad Example

- 這個例子是壞的，因為 `watch: false` 讓篩選條件改變後資料不更新（漏載）。

```ts
useFetch('/api/orders', { query: { status }, watch: false })
```

# Rule 15 - E15 Nitro 快取有過認證邊界（SR-6，安全項優先於效能）

- Level: `MUST`
- fail：有快取 handler 且該 endpoint 取用使用者身分，但 `getKey()` 未納入使用者識別 → **跨使用者資料外洩**（Grade 直接 F）。
- 效能缺口：適用 edge cache 沒有符合 SR-6 的持久化 driver；列為 `E15-performance` fail，與安全評分分開。
- pass：每個適用快取的身分／授權邊界與必要 headers 都已逐項驗過，且 key 隔離符合 SR-6。無快取 handler 記 N/A。只看到 `getKey` 函式名稱仍為 unknown。

## Good Example

- 這個例子是好的，因為快取 key 含使用者識別。

```ts
export default defineCachedEventHandler(handler, {
  maxAge: 60,
  getKey: (event) => `me:${event.context.user.id}`,
})
```

## Bad Example

- 這個例子是壞的，因為 endpoint 回使用者資料但所有人共用同一份快取。

```ts
export default defineCachedEventHandler((event) => getProfile(event.context.user.id), { maxAge: 60 })
```

# Rule 16 - E16 字型單一來源且明列 weight（SR-7）

- Level: `MUST`
- fail：有 `@fontsource/*` bare import **且** codebase 用了 400 以外字重 → 合成粗體（CJK faux bold 筆畫糊化）。
- fail：`fonts.families`（nuxt.config）與 CSS `@import` 宣告同一字型 → 雙重載入。
- pass：明列 weight subpath，或只用 `@fontsource-variable/*`（可變字型 bare import 涵蓋全 weight）。

## Good Example

- 這個例子是好的，因為用到的字重都明列。

```css
@import '@fontsource/noto-sans-tc/400.css';
@import '@fontsource/noto-sans-tc/700.css';
```

## Bad Example

- 這個例子是壞的，因為 bare import 只載 400，`font-bold` 變成合成粗體。

```css
@import '@fontsource/noto-sans-tc';
```

# Rule 17 - E17 routeRules 選對渲染模式（SR-8）

- Level: `MUST`
- public route 依內容性質選 `prerender`／`isr`／`swr`／`cache`。
- `experimental.payloadExtraction` **NEVER** 計入缺口：Nuxt 4 預設 `true`；`compatibilityVersion: 5` 時預設為 `"client"`；`ssr: false` 時強制 `false`。SPA consumer 此項一律 N/A。

## Good Example

- 這個例子是好的，因為更新頻率不同的公開頁各選合適模式。

```ts
routeRules: { '/docs/**': { prerender: true }, '/news/**': { isr: 600 } }
```

## Bad Example

- 這個例子是壞的，因為把 SPA consumer 沒設 payloadExtraction 當成缺口。

```text
E17 fail：未設定 experimental.payloadExtraction（consumer 為 ssr: false）
```

# Rule 18 - E18 取消訊號貫通 HTTP client（HR-6）

- Level: `MUST`
- 列出每個 query function／data-fetching handler，依 consumer 安裝版本查框架如何提供 `signal`，逐段追到實際 HTTP client。共用 interceptor 也在查核範圍：既有 signal 保留或合併，**NEVER** 被新 controller 取代。
- pass：每個適用呼叫均有來源到 HTTP client 的傳遞證據，interceptor 沒有覆寫。fail：任一適用呼叫遺漏 signal，或 interceptor 覆寫它。unknown：呼叫鏈或版本行為尚未查清，不算 pass。

## Good Example

- 這個例子是好的，因為 Colada 給的 signal 一路傳到 `$fetch`。

```ts
useQuery({ key: orderKeys.list(), query: ({ signal }) => $fetch('/api/orders', { signal }) })
```

## Bad Example

- 這個例子是壞的，因為 interceptor 新建 controller 蓋掉了上游 signal。

```ts
onRequest({ options }) { options.signal = new AbortController().signal }
```

# Rule 19 - E19 非冪等寫入有真正的防重機制（HR-7）

- Level: `MUST`
- 逐筆檢查 POST／PUT／PATCH／DELETE 與 mutation 的提交入口，依 HR-7 查 server idempotency key／dedup 或按鈕 loading-disabled。**cancel 不是防重**：取消前端等待不能證明 server 沒有寫入。
- pass：每個適用寫入都有防重證據，未把 abort／cancel 當防重。fail：只靠取消前一個請求，或沒有防重機制。N/A：查核範圍沒有適用寫入，附範圍證據。

## Good Example

- 這個例子是好的，因為送出期間按鈕 disabled，server 另以 idempotency key 去重。

```vue
<UButton :loading="isLoading" :disabled="isLoading" @click="submit" />
```

## Bad Example

- 這個例子是壞的，因為只 abort 前一次請求，server 可能已寫入兩筆。

```ts
controller?.abort(); controller = new AbortController()
await $fetch('/api/orders', { method: 'POST', body, signal: controller.signal })
```
