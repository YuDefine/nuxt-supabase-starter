# Rule 1 - 帳號資源的查詢與異動走 `cf-cli`，wrangler 只留部署與本機開發

- Level: `MUST`
- 依操作判歸屬：

評估：first-match；以上皆非 → W*

| id | 操作 | 歸屬 |
| --- | --- | --- |
| W1 | `wrangler deploy`、`wrangler dev`、`wrangler tail`、`wrangler types`、config 驗證 | wrangler（本 skill） |
| W2 | 查 dev server 的本機資料（`wrangler d1 execute <db> --local` 等） | wrangler（本 skill） |
| W3 | CI workflow 內的步驟（D1 migration、`pre-migration-bookmark.sh` 等） | wrangler，邊界見 `cloudflare-workers.md` § 8 |
| W4 | D1／KV／R2／Vectorize／Queues／DNS／Worker secret 等帳號資源的查詢、建立、異動、刪除 | 轉 `cf-cli` skill |
| W* | 以上皆非 | 先查 `cloudflare-workers.md` § 8 的邊界；仍判不出就回報，不自行挑工具 |

- **NEVER** 用 `wrangler d1|kv|r2|secret|...` 子指令改打遠端帳號資源。

## Good Example

- 這個例子是好的，因為建立 KV namespace 屬 W4 轉 cf-cli，只有 binding 寫進 config 與部署留在 wrangler。

```md
1. 經 `cf-cli` skill 建立 KV namespace，取得 id。
2. 把 binding 寫進 `wrangler.jsonc` 的 `kv_namespaces`，跑 `wrangler types` 與 `wrangler deploy --dry-run --env staging`。
```

## Bad Example

- 這個例子是壞的，因為用 wrangler 子指令直接改遠端帳號資源。

```bash
pnpm exec wrangler kv namespace create CACHE
pnpm exec wrangler secret put API_KEY
```
