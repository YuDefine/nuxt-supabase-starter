# Rule 1 - 監看 CI 一律用 `$GH_CI_WATCH` 機械輪詢，NEVER 交給 LLM watcher、事件流通知器或前景等待

- Level: `MUST`
- 監看 CI＝機械輪詢：target adapter 的 background command runner 跑 `$GH_CI_WATCH`，腳本自己 poll 到 terminal state 才 exit，主線只在完成時收到一次通知。等待期間零 LLM turn、零 token、行為確定。
- **NEVER** 用 LLM watcher（Agent subagent）監看：它會中途反覆回報、空等被 cancel 的 run、回報舊 run 結論。run 尚未建立、被 concurrency 取代、同 SHA 多條 run，script 都已機械處理。
- **NEVER** 用事件流型通知器（漏 terminal state 時沉默）、前景 `gh run watch`（3 秒刷新）／`gh pr checks --watch`（10 秒刷新），或主線 wakeup／`sleep` 輪詢（block 主線）。
- **NEVER** 手寫 ad-hoc `until ...; do sleep ...; done` 輪詢取代本 script。
- 輪詢間隔 **NEVER** <30s：script 已 clamp，手寫的一次性查詢 loop 也適用同紀律。

## Good Example

- 這個例子是好的，因為等待交給 script，主線繼續原工作。

```text
Bash(run_in_background=true): bash "$GH_CI_WATCH" workflow ci.yml --commit "$SLICE_SHA"
→ 主線繼續寫 plan evidence，等完成通知
```

## Bad Example

- 這個例子是壞的，因為 LLM 在等待期間反覆消耗 turn，且可能回報舊 run。

```text
Agent("每 2 分鐘查一次 CI，綠了告訴我")
```

# Rule 2 - 派 watcher 前 MUST 確認該 workflow 會被本次 diff 觸發，同一條 run NEVER 派第二個 watcher

- Level: `MUST`
- 先讀該 workflow 的 `on:`（`paths:`、`branches:`、`tags:`）確認本次 push 命中。沒命中就不會有 run，watcher 只會等滿 `WATCH_TIMEOUT`（例：沒動 `supabase/migrations/` 卻派 migration gate）。
- 一條 run 只掛一個 watcher；要改目標＝kill 舊的再派新的，**NEVER** 對跑一半的 watcher「下改派指令」——script 沒有也不需要互動管道。

## Good Example

- 這個例子是好的，因為派之前先核對觸發條件。

```text
diff 只動 docs/ → ci.yml on.pull_request.paths-ignore 含 docs/** → 本次不派 watcher，回報「本次 diff 不觸發 ci.yml」
```

## Bad Example

- 這個例子是壞的，因為 migration gate 不會有 run，watcher 會空等一小時。

```text
diff 只動 app/pages/ → bash "$GH_CI_WATCH" workflow migration-gate.yml --branch main
```

# Rule 3 - 沒收到通知 NEVER 解讀成任何結論，watcher 存活只用 adapter 的 owner-status 查

- Level: `MUST`
- 「還沒收到完成通知」不代表成功、失敗或卡住；要確認 watcher 還活著，用 target adapter 的 owner-status 查詢（Claude：保留 Bash 回傳的 owner，`TaskOutput(block=false)` 只看狀態）。
- **NEVER** 讀取未經 adapter 整理的 background output：那會把整段輸出送進 context，在 control-turn allowlist 之外。

## Good Example

- 這個例子是好的，因為只查 owner 狀態。

```text
TaskOutput(task_id=<owner>, block=false) → running
```

## Bad Example

- 這個例子是壞的，因為把未整理的背景輸出整段讀進來，並據此臆測結論。

```text
cat /tmp/…/bash-output.log → 還在 queued，應該是 runner 壞了
```

# Rule 4 - 只有完成後的處置需要多步 LLM 工作且使用者明確要求全自動時，才可包一層 Agent，等待本身仍 MUST 用 script

- Level: `MAY`
- 例：使用者明說「紅燈就自己修到綠」。該 Agent 內部仍 MUST 用本 script 等待，等待永遠不交給 LLM。
- 純監看＋回報（絕大多數場景）一律直接 background Bash。

## Good Example

- 這個例子是好的，因為 Agent 只負責紅燈後的修復，等待仍是 script。

```text
使用者：「紅燈就自己修到綠」→ Agent brief：用 bash "$GH_CI_WATCH" run <id> 等結果，failure 才進修復
```

## Bad Example

- 這個例子是壞的，因為只是要知道結果，卻包了 Agent。

```text
使用者：「CI 好了跟我說」→ Agent("盯 CI")
```
