# Rule 1 - 任何紅燈進 root-cause 之前 MUST 先跑 `RANGE`，逐條看它涵蓋的 commit

- Level: `MUST`
- 失敗報告在 failed logs 之前印兩行：`LAST_GREEN: <sha> <時間> <url>`（同 workflow 最後一條 success run；branch push 限同 branch，tag 觸發不限）與 `RANGE: git log --oneline <last-green>..<red>`。
- 依下表判定起點與第一嫌疑：

| 可觀察 predicate | 判定 |
| --- | --- |
| 紅燈的起點（`LAST_GREEN` 之後第一條紅 run）**早於**最近一次環境變更（換 runner／image／secret） | 根因與那次環境變更無關，往 range 內的 code／依賴變更查 |
| range 只含環境變更那一筆 | 才把環境列為第一嫌疑 |
| `LAST_GREEN: unknown` | 用 `gh run list -w <workflow> -s success -L 1` 自己補查；查不到就明說「起點不明」，**NEVER** 預設是最近那次變更 |
| PR 的紅燈測試在 base（`main`）同一條 workflow 的最新 run 上也紅 | 紅在 base 就有，不是這張 PR 造成的：`gh run list -w <workflow> -b main -L 1 --json headSha,conclusion,url` 確認後回報「base 同紅」並附 base run URL，**NEVER** 在這張 PR 上修別人的紅燈 |

- **NEVER** 用「剛剛才換了 runner，應該是它」當起點。

## Good Example

- 這個例子是好的，因為先看 range，發現紅燈早於換 runner。

```text
LAST_GREEN: a1b2c3d 2026-10-02T03:10Z；RANGE 含 5 個 commit，第一條紅 run 在 10-02 05:00，runner 10-03 才換
→ 往 range 內的依賴升級查
```

## Bad Example

- 這個例子是壞的，因為沒跑 range 就把最近的環境變更當根因。

```text
ci.yml failure → 昨天剛換 runner image，一定是它 → 回滾 image
```
