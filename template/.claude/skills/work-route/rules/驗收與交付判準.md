# 驗收與交付判準

觸發點：`SKILL.md` Phase 7 step 1（tasks 完成要驗收、開 PR、交付或回報時）。

# Rule 1 - 驗收命令接到真實被測入口；runner 依專案 techstack

- Level: `MUST`

Aixbdd 決定需求、Gherkin、DSL、設計與 tasks；SpecFormula 執行已對齊的驗收。按當前 project techstack、capability 與 SpecFormula 契約選擇已安裝 runner；只用 aixbdd 且已明確採另一 BDD runner 的專案沿用其決策，不無條件改堆疊。

對採 SpecFormula 的專案，先由 technical-research／dsl-refine／implement／bdd 等 owner 依 `rules/SpecFormula契約載入判準.md` 把必要 DSL、ISA、adapter 與驗收命令接到真實被測入口，再執行該命令。步驟未定義、缺 runner 或 acceptance_command 時，由對應 owner 修復後重驗；不拿語法 parser、空 step 或永遠成功的替身充當驗收。

## Good Example

- 這個例子是好的，因為缺 acceptance_command 時交回 owner 修復後重驗。

```text
step 未定義 → 交 implement [BDD-ALIGN] 補 isa_steps → 重跑 acceptance_command
```

## Bad Example

- 這個例子是壞的，因為拿空 step 或永遠成功的替身充當驗收。

```text
step definition 內只寫 return → 宣稱驗收通過
```

# Rule 2 - 有 UI 或 entry point 變更時交付前做沉澱檢查與 evlog map gate

- Level: `MUST`

有 UI 變更的工作交付前做沉澱檢查：本輪動到 token 來源（`app.config.ts` 的 `ui`、CSS `:root` 變數、Tailwind theme）或建立新元件慣例時，DESIGN.md 已由 `document` 更新，或 `design-review.md` 寫明「本輪無 design system 變更」；受影響畫面的每個 P0／P1 都有可核對的 polish／明確 close、重跑 critique 歸零或使用者確認的 ignore 證據。commit 0-B.1 對已採用 impeccable 的 repo 會唯讀核對；`closed: true` 或指紋不同本身不會放行。

本工作動過 entry point 時，commit 與 `gh pr ready` 之前各以整份 branch diff 再跑一次 `node .github/actions/evlog-map-gate/local.ts`；push 時 pre-push 也跑同一支。三者與 CI 同一份判定，差別只在掃的是本機的樹（未 commit 的改動也會被掃到）。

## Good Example

- 這個例子是好的，因為動到 token 來源時先更新 DESIGN.md，commit 與 gh pr ready 之前各跑一次 gate。

```text
改了 app.config.ts 的 ui → document 更新 DESIGN.md；commit 前 node .github/actions/evlog-map-gate/local.ts
```

## Bad Example

- 這個例子是壞的，因為以 closed: true 或指紋不同當成 P0／P1 已處理。

```text
design-review.md 標 closed: true，但 P1 沒有 polish 或重跑 critique 的證據
```

# Rule 3 - 四種驗收證據分別呈現，有證據才宣稱

- Level: `MUST`

分別呈現「Gherkin 可解析」「步驟已綁定／readiness 通過」「實際案例通過」「人工驗收已確認」。只有對應證據存在才能宣稱該項完成；失敗回到 owner 修復，scope 變更回需求 owner。不得為變綠自行降低已確認的驗收標準。

採 SpecFormula 的專案，dry-run 無 undefined step 不足以證明「步驟已綁定」：`isa.yml` 的指令 regex 動態註冊，`.feature` 直接寫 ISA 指令句也永遠查得到定義。這一項要同時有兩項證據：(a) truth 介面根的 `audit_feature_dsl_topology.py` 通過（`rules/SpecFormula契約載入判準.md` Rule 2）；(b) 本次觸及的每一個 `.feature` step 都是 `dsl.md` 立列、經 `dsl.yml` 的 `dsl_steps` 展開的業務句型，不是直接命中 `isa.yml` 指令的 ISA 指令句。(b) 有機械 gate 時引用它的輸出；沒有時逐條列出 step → `dsl.yml` 句型的對照當證據。任一項缺就回 dsl-refine（句型）或 implement `[BDD-ALIGN]`（轉寫）修復。

## Good Example

- 這個例子是好的，因為四項分開列，各附對應證據。

```text
Gherkin 可解析 ✅／步驟已綁定 ✅（readiness 通過＋topology audit 通過＋7 個 step 都經 dsl.yml 展開）／實際案例通過 ❌ 2 failed／人工驗收：未確認
```

## Bad Example

- 這個例子是壞的，因為把可解析說成通過，或為了變綠降低已確認的驗收標準。

```text
dry-run 無 undefined step → 回報「驗收通過」
.feature 直接寫「準備一個…, with table:」，dry-run 無 undefined → 回報「步驟已綁定」
```

# Rule 4 - 交付範圍以授權為界

- Level: `MUST`

執行已授權的交付與收尾流程；缺外部部署／付費／對外寫入授權時先完成可審查結果再詢問。使用者只要求分析、規格或 review 時，在指定成果完成處停止，不擴張成實作／部署。

## Good Example

- 這個例子是好的，因為缺對外寫入授權時先完成可審查結果再詢問。

```text
使用者只要求 review → 交付 review 結論後停止；需要部署授權 → 先備妥可審查結果再問
```

## Bad Example

- 這個例子是壞的，因為把只要分析的請求擴張成實作與部署。

```text
「幫我分析這個需求」→ 順手實作並部署 staging
```

# Rule 5 - 工作中短訊息、交接留五欄、最終回覆交代產出與剩餘

- Level: `MUST`

工作中用短訊息說明已完成的成果、當前步驟與下一個會解除的不確定性。正常接續不以五段路由報告結束回合，也不請使用者再次輸入 skill 名稱。

需要保留交接／阻塞診斷時，依 `templates/work-route交接紀錄.md` 的五欄（`需求類型`、`package 或免 package`、`下一支 skill`、`缺少的前提`、`UI checkpoint`）記錄到同 package，使用者只看影響結果的摘要。

最終回覆交代產出、驗證與實際剩餘工作。需要人類判斷時展示具體選擇與理由；沒有必要的人類決策就繼續已授權工作，不用「下一步要不要……」轉嫁協調責任。

## Good Example

- 這個例子是好的，因為正常接續用短訊息，需要交接時把五欄記進同 package。

```text
需求類型: behavior／package: W-… specs/plans/W-…/／下一支 skill: tasks（rules/.workflow/tasks）／缺少的前提: 無／UI checkpoint: 不需要（純 CLI）
```

## Bad Example

- 這個例子是壞的，因為每個回合都以五段路由報告收尾，或用「下一步要不要……」轉嫁協調責任。

```text
「spec 寫好了，下一步要不要我跑 spec-by-example？」
```

# Rule 6 - 預設持續推進到成果完成或必要的人類決策

- Level: `MUST`

預設持續推進到使用者要求的成果完成，或到必要的人類決策／不可自行解除的外部阻塞。流程 owner 的 artifact 權責、runtime 指定 executor、PM／UI gate、權限與驗收證據保持有效；統一入口不代表略過下游契約。收到新訊息先吸收修正，再沿同一工作接續。

## Good Example

- 這個例子是好的，因為吸收新訊息後沿同一工作接續，下游 gate 與權責保持有效。

```text
收到使用者修正 → 更新 spec → 沿同一 package 續跑 SKILL.md Phase 6
```

## Bad Example

- 這個例子是壞的，因為把統一入口讀成可以略過下游契約或 PM／UI gate。

```text
「使用者說一路做完」→ 跳過 PM 確認直接 implement
```

# Rule 7 - 交付給人校對或驗收的改版，MUST 附 before／after 對照

- Level: `MUST`

交付物要給人校對或驗收、且是既有內容的改版時（文件、規格書、web article、畫面），最終回覆寫出 before／after 對照的入口或截圖位置，讓對方不必自己找差異。只寫「已更新」「已改好」不算交付。

- 文件類：走 web article 平台的版本對照（上一版或指定版對當前版）。平台還沒有版本對照時，附兩個版本 render 之間的差異，或改版前後的截圖。
- 畫面類：附改版前後同一畫面、同一狀態的截圖，寫出存放位置。
- 對照的兩端標明版本：before 是對方上次看過的那一版，不是工作中途的任意 commit。

首次交付、沒有前一版可比時寫明「首版，無對照」，不必硬造對照。

## Good Example

- 這個例子是好的，因為最終回覆給出對照入口，兩端版本都標明。

```text
規格書已更新到 v3。對照：https://…/article/abc?compare=v2..v3（v2 是客戶 10/15 看過的版本）
儀表板改版前後截圖：specs/plans/W-…/evidence/before-after/dashboard-{before,after}.png
```

## Bad Example

- 這個例子是壞的，因為只說已更新，對方得自己翻兩版找差異。

```text
規格書第 4 章已依回饋更新，請再看一次。
```
