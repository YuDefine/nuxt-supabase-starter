# 工作種類與必要產物

契約全文在 `specs/truth/work-lifecycle.md` § Package（Work kind）、§ Delta、§ Close；本檔是 work-route 開 package 與改判時要照做的部分。觸發點：`SKILL.md` Phase 3 step 2（要開 package 或改判工作種類時）。

# Rule 1 - 開 package MUST 以 `--kind` 記錄判定出的工作種類

- Level: `MUST`
- `flow plan open <slug> --title '…' --kind <值>`。值域與要求集：

| 判定表的列 | `--kind` | readiness 要求集 | delta 形狀（不符回 `kind-delta-mismatch`） |
| --- | --- | --- | --- |
| 新增／修改／刪除既有行為 | `behavior` | full | 不限 |
| bug，出錯的行為沒有 scenario | `bug-uncovered` | full | 至少一列 ADD 到 `specs/truth/features/**` |
| 重構，行為不變 | `refactor` | 錨點全是 NOOP → regression；有 ADD 錨點或沒有錨點 → full | truth features、contracts、data 沒有 MODIFY／DELETE |
| bug，出錯的行為已有 scenario | `bug-covered` | regression | 沒有 MODIFY／DELETE；ADD 只落在已存在的 truth `.feature`；不改 `dsl.md`／`dsl.yml` |
| 驗收階段發現的 bug，所在功能範圍沒有 truth 覆蓋 | `acceptance-gap` | full＋範圍盤點表（Rule 6） | 至少一列 ADD 到 `specs/truth/features/**` |

- full：`spec.md`、沒有待釐清標記、plan acceptance scenario、`acceptance_command`、新鮮 `truth_baseline`、dry-run 無未定義步驟（採 SpecFormula 時 dry-run 不足以證明步驟已綁定，另見 `rules/驗收與交付判準.md` Rule 3）。regression：不要 `spec.md` 與 plan acceptance，改要至少一列迴歸錨點（NOOP，或已 applied 的 ADD），且每一個錨點 scenario 出現在 dry-run 結果裡；其餘同 full。
- 沒給 `--kind` 照 full 檢查（`work_kind: null`），不是放寬。
- `kind-delta-mismatch` 代表判錯種類，改判；**NEVER** 為了過 gate 刪 delta 或換 action。

## Good Example

- 這個例子是好的，因為付款金額算錯的行為在 `結帳.feature` 已有 scenario，照 bug-covered 開，錨點指向那支 feature。

```text
flow plan open checkout-rounding --title '結帳金額四捨五入錯' --kind bug-covered
| D1 | NOOP | specs/truth/features/api/結帳.feature -> Scenario Outline: 結帳金額 | 違反既有不變量 | proposed |
```

## Bad Example

- 這個例子是壞的，因為要新句型代表這個行為原本沒有 scenario；readiness 會回 `kind-delta-mismatch`，應改判 `bug-uncovered`。

```text
--kind bug-covered
| D1 | ADD | specs/truth/features/api/dsl.md -> 退款金額句型 | … |
```

# Rule 2 - 迴歸錨點 MUST 寫進涵蓋該行為的既有 truth 介面 feature

- Level: `MUST`
- delta 列的 unit 寫成 `specs/truth/features/<路徑>.feature -> Scenario: <標題>`（`Example:`、`Scenario Outline:` 也可）。ADD＝新寫一條，NOOP＝既有 scenario 已能重現。
- 由 dsl-refine 寫：優先在既有 Scenario Outline 加 Example 列，否則在同檔加 Scenario，用領域語言描述**現在正確**的行為。**NEVER** 另開專放迴歸的 feature 檔。
- 來源註解只寫 `# 來源：work <work-id>`，**NEVER** 寫 plan 路徑：truth 裡出現 `specs/plans/<id>`，結案時 `live-refs` 會擋。
- ADD 錨點先 commit、先跑紅，紅燈的 cucumber JSON 留在 plan `evidence/`；實作的 spec-integrity 從那個 commit 算起。

## Good Example

- 這個例子是好的，因為錨點加進既有 Scenario Outline 的 Example 列，來源註解只寫 work id。

```text
結帳.feature 的 Scenario Outline: 結帳金額 新增一列 Example（現在正確的行為）；註解「# 來源：work W-2026-10-12-checkout-rounding」
```

## Bad Example

- 這個例子是壞的，因為另開專放迴歸的 feature 檔，來源註解寫了 plan 路徑，結案時 `live-refs` 會擋。

```text
新增 specs/truth/features/api/regression.feature；註解「# 來源：specs/plans/W-…/plan.md」
```

# Rule 3 - 結案時每一個錨點 MUST 先紅後綠且判決新鮮

- Level: `MUST`
- `flow plan check-close` 對每一列 NOOP 與已 applied 的 ADD 錨點要求 plan `evidence/` 有 passed 判決，晚於 plan 最後修訂與該 truth feature 最後一次修改兩者較晚者（`truth-scenario-verdict-missing`／`-not-passed`／`-stale`）。
- 同一條 scenario 在 passed 之前要有 failed（`regression-anchor-never-red`）。`refactor` 豁免：它的錨點釘住不變的行為，按定義不會紅。
- `bug-covered`、`bug-uncovered`、`refactor`、`acceptance-gap` 至少一個錨點（`regression-anchor-missing`）。`acceptance-gap` 不逐錨點要求先紅後綠（盤點表裡本來就正確的行為不會紅），改由 Rule 6 要求原 bug 那一列與至少一支 e2e 錨點先紅後綠。
- 結案後錨點留在 truth，PR 改到它或它提到的程式時 CI 會再跑（`scripts/affected-truth-features.ts`）。

## Good Example

- 這個例子是好的，因為 bug-covered 的錨點先留紅燈判決、修好後留綠燈判決，且晚於 plan 最後修訂。

```text
evidence/ 先有該 scenario 的 failed 判決，修復後有 passed 判決（時間晚於 plan 與 feature 的最後修改）→ check-close 通過
```

## Bad Example

- 這個例子是壞的，因為只留綠燈判決，沒有先紅的紀錄（`regression-anchor-never-red`）。

```text
evidence/ 只有 passed 判決，從沒出現過 failed → bug-covered 結不了案
```

# Rule 4 - hotfix 與純邏輯 bug 不是工作種類

- Level: `MUST`
- hotfix：`flow plan open --hotfix` 允許先修，plan 帶一條「補迴歸 scenario（hotfix 先修）」Open work，沒勾結不了案。補的時候照出錯的行為原本有沒有 scenario，以 `flow plan set-kind <work-id> --to bug-covered|bug-uncovered --reason '…'` 定種類。
- 沒有 I/O 的純邏輯 bug（計算、解析、格式化、邊界值）且出錯的行為**沒有 scenario**：**不開 plan**，迴歸落 unit test，與修正同一個 commit；已有 scenario 的純邏輯 bug 照 Rule 1 開 `bug-covered`（`需求分流判準.md` Rule 2 K2 先於 K3）。
- 判錯種類時用 `set-kind` 改判（§ Decisions 自動記舊值、新值、理由），**NEVER** 以不同 `--kind` 重開同一個 slug（會被拒絕）。

## Good Example

- 這個例子是好的，因為 hotfix 先修，補迴歸 scenario 時以 set-kind 定種類。

```text
flow plan open fix-login --hotfix → 先修 → 補迴歸 scenario 時 flow plan set-kind W-… --to bug-covered --reason '既有 scenario 涵蓋'
```

## Bad Example

- 這個例子是壞的，因為判錯種類後以不同 `--kind` 重開同一個 slug，會被拒絕。

```text
flow plan open checkout-rounding --kind bug-uncovered（原本是 --kind bug-covered）→ 被拒絕
```

# Rule 5 - package 落點依 lifecycle marker 判定；缺 marker 是要先修的前提

- Level: `MUST`

已有 `plan.md` frontmatter 同時含 `work_id:` 與 `truth_baseline:` 時，沿用 `specs/plans/<work-id>/`。新工作：repo 根有 `specs/truth/work-lifecycle.md` 時 MUST 先 `flow plan open` 鑄 `W-…`，並以 `--kind` 記錄上表判定的工作種類（Rule 1，**每一次**開 package 或改判之前讀它）。manifest 宣告 `aixbdd`／`specformula` 卻沒有該檔，是要先修的前提而不是降級理由：照 `SKILL.md` Phase 3 step 2 處理 truth root，再 `flow plan open`；**NEVER** 靜默改鑄 `NNN-<slug>`。只有兩側都沒宣告、且使用者沒有要採用 lifecycle 的 consumer 才鑄 `NNN-<slug>`。不為補前提、轉 owner 或重試另開 package。

## Good Example

- 這個例子是好的，因為manifest 宣告 aixbdd 卻缺 work-lifecycle.md 時先修 truth root 再鑄 W-。

```text
manifest 宣告 aixbdd、缺 specs/truth/work-lifecycle.md → 照 clade-onboard 的 truth-root 處置判準處理 → flow plan open --kind …
```

## Bad Example

- 這個例子是壞的，因為把缺檔當降級理由，靜默改鑄舊式 package。

```text
缺 specs/truth/work-lifecycle.md → 改鑄 NNN-<slug>
```

# Rule 6 - 驗收階段發現、所在範圍沒有 truth 覆蓋的 bug MUST 開 `acceptance-gap`，框整塊功能補驗收

- Level: `MUST`
- 判斷：bug 在驗收階段發現（客戶／HR 驗收、發版驗證、staging 實走、主管抽驗、對方回「不通過」），且它所在的功能範圍在 `specs/truth/features/**` 沒有 truth 覆蓋 → **只能**開 `--kind acceptance-gap`，**NEVER** 開 `bug-covered`／`bug-uncovered`，也 **NEVER** 走 K3 免 package 只修那一行。範圍已有 truth 覆蓋的照 Rule 1 判 `bug-covered`／`bug-uncovered`。
- 範圍＝bug 所在的整個使用功能（使用者從進入到完成那件事的整條流程），不是出錯的那一個點。原 bug 的紅→綠錨點只是盤點表其中一列。
- 必要產物：plan.md 的範圍盤點表、每列的 truth scenario（Truth delta 錨點）、原 bug 的紅→綠錨點（`bug` 列）、至少一支覆蓋整條使用流程的 e2e scenario。
- 盤點表的機械格式（`flow plan readiness` 與 `check-close` 照這個格式讀；別的 skill、brief、review 規則引用這個格式時指向本 Rule）：

```markdown
## Scope inventory

| id | 行為 | 落點 | scenario／理由 |
| --- | --- | --- | --- |
| S1 | <該功能的一個行為> | existing | `specs/truth/features/<路徑>.feature` -> `Scenario: <標題>` |
| S2 | <行為> | add | `specs/truth/features/<路徑>.feature` -> `Scenario: <標題>` |
| S3 | <原 bug 出錯的行為> | bug | `specs/truth/features/<路徑>.feature` -> `Scenario: <標題>` |
| S4 | <整條使用流程> | e2e | `specs/truth/features/<路徑>.feature` -> `Scenario: <標題>` |
| S5 | <行為> | out | <不做的理由> |
```

- 落點值域只有五個：`existing`（已有 scenario，Truth delta 要有同 unit 的 NOOP 列）、`add`（本次新寫，Truth delta 要有同 unit 的 ADD 列）、`bug`（原 bug 的錨點，Truth delta 要有同 unit 的 ADD 或 NOOP 列）、`e2e`（端到端 scenario，Truth delta 要有同 unit 的 ADD 或 NOOP 列）、`out`（明列不做，第四欄寫理由）。第四欄的 scenario 寫法與 Truth delta unit 相同（Rule 2）。
- 閘門（readiness 與 check-close 都檢查；最後兩條只在 check-close）：

| code | 擋下什麼 |
| --- | --- |
| `scope-inventory-missing` | 沒有 `## Scope inventory` 或表內沒有列 |
| `scope-inventory-row-unplaced` | 落點不在值域內；`out` 沒寫理由；`existing`／`add`／`e2e` 第四欄不是 scenario 參照 |
| `scope-inventory-row-unanchored` | scenario 參照在 Truth delta 找不到對應動作（見上）的有效列 |
| `acceptance-gap-bug-missing` | 沒有任何 `bug` 列 |
| `acceptance-gap-e2e-missing` | 沒有任何 `e2e` 列 |
| `acceptance-gap-bug-never-red` | 某一列 `bug` 錨點在 plan `evidence/` 沒有先 failed、最新為 passed |
| `acceptance-gap-e2e-never-red` | 沒有一支 `e2e` 錨點在 plan `evidence/` 先有 failed、最新為 passed |

- 每一列錨點仍照 Rule 3 要求新鮮的 passed 判決。閘門只驗格式與判決，驗不了盤點有沒有漏行為、e2e 有沒有走過出錯那一步——那兩件由寫盤點的人與 review 負責。缺項就結不了案：**NEVER** 為了過閘門把該做的行為改標 `out`、把 e2e 換成單點 scenario，或改判成 `bug-covered`。

## Good Example

- 這個例子是好的，因為客戶驗收發現結帳失敗、結帳功能沒有 truth 覆蓋，框整條結帳流程盤點，原 bug 只是其中一列，另有一支 e2e 先紅後綠。

```text
flow plan open checkout-acceptance --title '驗收：結帳失敗' --kind acceptance-gap
## Scope inventory
| S1 | 付款失敗時訂單保持待付款 | bug | `specs/truth/features/api/結帳.feature` -> `Scenario: 付款失敗時訂單保持待付款` |
| S2 | 加入購物車到付款完成 | e2e | `specs/truth/features/web/結帳流程.feature` -> `Scenario: 從加入購物車到付款完成` |
| S3 | 匯出收據 PDF | out | 本次驗收未涵蓋收據，另開 work W-… |
evidence/：S1、S2 先 failed、修好後 passed → check-close 通過
```

## Bad Example

- 這個例子是壞的，因為驗收發現的 bug 所在範圍沒有 truth 覆蓋，卻只開 bug-uncovered 補一個錨點、修一個點就想結案。

```text
客戶驗收回報結帳失敗（結帳功能沒有任何 truth feature）→ flow plan open fix-checkout --kind bug-uncovered → 只補 S1 一列錨點
```
