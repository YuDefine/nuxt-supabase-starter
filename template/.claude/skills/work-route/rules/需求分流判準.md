# 需求分流判準

觸發點：`SKILL.md` Phase 1 step 2（每一次收到需求）。

# Rule 1 - 本入口持有接續責任，artifact 仍由指定 owner 產出

- Level: `MUST`

使用者描述想完成的工作即可。本 skill 持有從需求到驗收、交付的接續責任：定位同一工作、載入正確 owner 的契約、執行已授權步驟、處理可修復前提，再依結果繼續。不是只列出「下一支 skill」就結束的導航頁。

每份 artifact 仍由指定 owner 產出；呼叫 owner 是同一 agent 載入其完整契約後執行，或依 runtime routing 交給必要 executor，不要求使用者輸入另一個 slash command。先通過 owner 的前提，不由 router 冒充 owner 或跳過驗收。

## Good Example

- 這個例子是好的，因為判出 owner 後由同一 agent 載入契約執行並查驗產出，再接下一步。

```text
判定下一步是 spec-by-example → 載入其契約 → 產出 features/acceptance/** → 查驗 → 回 SKILL.md Phase 6 重新判定
```

## Bad Example

- 這個例子是壞的，因為只列出下一支 skill 就結束回合，把協調責任丟回使用者。

```text
「下一步請你執行 /specify」→ 結束回合
```

# Rule 2 - 依當前需求取處理列

- Level: `MUST`

評估：巢狀（先判 Q 表的需求入口，Q6／Q7 再判 K 表的工作類型）

評估：first-match；以上皆非 → Q*

| id | 當前需求 | 處理 |
| --- | --- | --- |
| Q1 | 只問 onboard 狀態、readiness、registry drift | 交 clade-onboard 完成查詢，不建立 package |
| Q2 | 純討論、評估方案，未要求落地 | 在對話中研究與說明，不寫 repo／flow |
| Q3 | 已簽 presale 包（`presale.json` status=signed）＋ 新 repo | 同 Q5 走 clade-onboard → project-bootstrap（intake 由 presale 包預填）；回此入口後以 `flow plan open <slug> --seed-from <presale 目錄> --milestone M1` 開第一個 package，不從會議紀錄重寫 spec |
| Q4 | 已簽 presale 包 ＋ 既有 consumer | 以 `flow plan open <slug> --seed-from <presale 目錄> --milestone <M-x>` 開 package [^Q4] |
| Q5 | 新建／採用專案 | 執行 clade-onboard 判定，依結果承接 project-bootstrap；保留其 intake、外部副作用授權與完成條件，完成後回此入口 |
| Q6 | clade 中央倉，registry role=source-of-truth | 依 work-lifecycle 處理，不跑排除 source-of-truth 的 consumer audit、不製造 consumer manifest；→ K 表 |
| Q7 | 已 onboard 專案的新工作／續跑 | 檢查其實際 manifest 與所需 capability，定位本次 package；→ K 表 |
| Q* | 以上皆非 | 交 clade-onboard 判定 repo 狀態，回此入口重判 Q 表 |

[^Q4]: 後續 Milestone 在前一個結案後才開。`contract-<M-x>.feature` NEVER 改寫或刪除，範圍變更回 presale 開修訂版。

評估：first-match；以上皆非 → K*

| id | 工作類型 | 處理 |
| --- | --- | --- |
| K1 | 使用者明說 hotfix | `flow plan open --hotfix` 先修 [^K1] |
| K2 | bug 回報，出錯的行為已有 scenario（含純邏輯）[^K2] | `--kind bug-covered`：NOOP delta 指向被違反的不變量＋迴歸錨點（先紅再修）；不發明新 truth |
| K3 | bug 回報，沒有 scenario，出錯的是沒有 I/O 的純邏輯（計算、解析、格式化、邊界值） | 免 package：迴歸落 unit test，與修正同一個 commit [^K3] |
| K4 | bug 回報，沒有 scenario（只有舊測試或沒有測試），不屬 K3 | `--kind bug-uncovered`，進下方 workflow：ADD delta 把當下正確的行為寫成 truth 與 scenario，再修 [^K4] |
| K5 | 分析發現缺陷要重構，行為不變 | `--kind refactor`，進下方 workflow：先確認（缺的以 ADD delta 補上）釘住現行行為的 scenario 且綠，再動結構 [^K4]；行為要變就改判 K8 |
| K6 | 純措辭／設定，不改行為、權限、資料或部署語意 | 依 repo 流程直接實作與驗證，免 package |
| K7 | 一次性工作（不改行為） | 遵守該次授權，不強套完整流程 |
| K8 | 新增／修改／刪除既有行為 | `--kind behavior`，進下方 workflow，完成已授權部分 |
| K* | 以上皆非 | 問使用者是否改變行為、是否為 bug，答後重判 K 表；未答前不建 package |

[^K2]: 「已有 scenario」＝`specs/truth/features/**` 涵蓋該行為的 interface feature 裡，有 `Scenario`、`Scenario Outline`，或 Outline 的 `Example` 列能重現出錯的輸入；plan 的 acceptance feature、unit／e2e 測試、舊測試都不算。判法：先找涵蓋該行為的 truth feature 再看有沒有能重現的條目，有就取 K2，找不到才往 K3／K4。純邏輯 bug 同樣先查這一步，否則已寫成 truth 的不變量會失去迴歸錨點。
[^K3]: 免 package 不在 `work_kind` 值域內。
[^K1]: hotfix package 帶一條「補迴歸 scenario（hotfix 先修）」open work，沒補完結不了案；補的時候以 `flow plan set-kind` 定為 `bug-covered` 或 `bug-uncovered`，不以一支 unit／e2e 迴歸測試結案。
[^K4]: 該區舊測試同一件工作吸收（bug-uncovered 在 implement 的 Phase 3）。

## Good Example

- 這個例子是好的，因為 bug 回報、出錯行為已有 scenario（即使是沒有 I/O 的四捨五入），取 K2（bug-covered），不發明新 truth。

```text
結帳金額四捨五入錯，truth 的 結帳.feature 已有 Scenario Outline: 結帳金額 → flow plan open … --kind bug-covered → NOOP delta 指向該不變量＋迴歸錨點，先紅再修
```

## Bad Example

- 這個例子是壞的，因為同一情境改以一支 unit／e2e 迴歸測試結案，scenario 沒有成為迴歸錨點。

```text
結帳金額算錯（有 I/O、已有 scenario）→ 免 package，補一支 unit test 就 commit
```

# Rule 3 - 只查本步前提；「繼續」沿用已確認範圍

- Level: `MUST`

所有路徑都檢查本步所需前提；不要求一次備齊未來步驟的輸出。使用者的「繼續／y」沿用已確認的範圍與決策，不重新訪談；未呈現過的 PM 驗收不因泛稱繼續而視為確認。

## Good Example

- 這個例子是好的，因為「繼續」只沿用已確認的決策，未呈現過的 PM 驗收仍要展示後確認。

```text
使用者回「y」→ 沿用已確認範圍續跑；Gherkin 尚未展示 → 先展示並問具體確認問題
```

## Bad Example

- 這個例子是壞的，因為把泛稱的「繼續」當成 PM 已確認，或要求一次備齊未來步驟的輸出。

```text
使用者回「繼續」→ 視為 Gherkin 已確認，直接進 system-analysis
```
