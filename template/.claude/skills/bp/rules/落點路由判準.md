
# Rule 1 - Q1／Q2／Q3 MUST 自己先答一遍，答不出來的才問使用者

- Level: `MUST`
- 分類負擔歸 bp，不歸使用者：使用者只講出那條實踐是什麼，落點由 bp 判。目標是讓使用者回是非題，不是回「該放哪一層」。
- 三題依序答：Q1 誰需要知道（Rule 2）→ Q2 何時需要知道（Rule 3）→ Q3 它是什麼形態（Rule 4）。每題都要能指出命中哪一列與 tie-breaker 問句的答案。
- 落點的到達機制與載入時機查 `references/落點與散播機制.md` 的 7 落點表；本檔只放判準。
- 詞彙：「落點（placement）」指資產放在 clade 哪個目錄、怎麼到達 consumer。**NEVER** 用「層」指涉落點——`registry/conventions.json` 的 `layer` 已是領域層（data／observability／auth／lifecycle／infra／framework／deploy）。

## Good Example

- 這個例子是好的，因為三題都自答，只把真正判不出的一題丟成是非題。

```md
Q1：全 consumer 都可能 propagate → 不對，propagate 只在 clade 跑 → 只有 clade（tie-breaker：consumer session 不可能執行這條）
Q2：做 publish 時才用得到 → 某支 skill 的 rules/（clade-publish）
Q3：判準
要問你的只有一題：這條要不要同時加 hook 在 propagate 前擋？（是／否）
```

## Bad Example

- 這個例子是壞的，因為它把分類工作丟回給使用者。

```md
這條要放 rules/core、skill 還是 docs？你覺得呢？
```

# Rule 2 - Q1 誰需要知道：依受眾選落點，只對一個 consumer 有效的 NEVER 進 clade

- Level: `MUST`

| 答案 | 落點 |
| --- | --- |
| 全 consumer 都該遵守 | 落點 1（`rules/core/`） |
| 只有用某個 stack 的 consumer（Supabase／CF Workers／Nuxt…） | 落點 2（`rules/modules/<group>/<variant>/`） |
| 只有 clade 自己（治理、散播機械、clade 自治區紀律） | clade 自己的 `.claude/rules/local/`（clade home 是 Claude session，這格就是字面路徑），**不散播** |
| 只有某一個 consumer，且已是穩定規約 | 該 consumer 自己的中立 local 規約 `.clade/rules/`（legacy `.claude/rules/local/` 仍可讀，per [[local-rule-override]]），**不進 clade** |
| 只有某一個 consumer，且還是單次 session 的觀察 | 該 consumer 的 `tasks/lessons.md`，**不進 clade**（成熟後再依 [[session-tasks.operations]] § 升級路徑往上走） |

- tie-breaker 問句（判不出時逐字問自己）：
  - 判不出後兩列：問「這條現在寫成 rule，下一個 session 讀到會不會覺得證據只有一次」。會 → `tasks/lessons.md`。
  - 判不出 1 還是 2：問「一個沒有這個 stack 的 consumer 讀到這條，會不會覺得莫名其妙」。會 → 2。
  - 判不出 1 還是自治區：問「consumer session 有沒有可能真的執行這條」。沒有（例如「改 propagate.ts 前先答三問」）→ 自治區。
- 最後兩列是**不收**的出口：**NEVER** 因為使用者送了 `\bp` 就一定要在 clade 找一個落點塞進去。

## Good Example

- 這個例子是好的，因為只對某個 consumer 有效的觀察被導回該 consumer 自家，沒有進 clade。

```md
\bp <consumer-id> 的 sync 腳本在週一凌晨會撞到客戶備份
Q1：只有 <consumer-id>，且證據只有這一次 → <consumer-id> `tasks/lessons.md`（不進 clade）
```

## Bad Example

- 這個例子是壞的，因為單一 consumer 的一次觀察被升成全 fleet 規約。

```md
落點：rules/core/backup-window.md（全 consumer always-load）
```

# Rule 3 - Q2 何時需要知道：依載入時機定成本，任務型判準落到某支 skill 的 rules/ 並指名觸發點

- Level: `MUST`
- 這題決定**成本**：always-load 的每一個 byte，每個 session 都要付。

| 答案 | 落點 | 成本 |
| --- | --- | --- |
| 每個 session、任何工作都可能踩到 | 落點 1／2 且**不寫** `paths:` | 最貴 |
| 編輯某類檔案時才用得到 | 落點 1／2 且寫 `paths: ['<glob>']` | 零 always-load |
| 做某任務時才用得到的**判準** | 該任務那支 skill 的 `rules/<判準>.md`＋**具名觸發點**（SOP step 的 `READ 若〈條件〉，讀取 rules/〈判準〉.md`，或 hook 在那一刻印 pointer） | 零 always-load |
| 做某任務時才用得到的**流程** | 落點 3（skill 本體的 SOP step） | 零 always-load |
| 想查的時候查得到就好 | 落點 6／7 | 零 |

- 判到「某支 skill 的 `rules/`」時，回報 **MUST** 指名是哪支 skill、哪個 phase／step 會讀它（觸發點）；講不出觸發點就不准落這一列——沒有觸發點的判準等於沒人會讀。
- **判準是 `paths:` 欄位存在與否，不是 frontmatter 存在與否**——只有 `description` 沒有 `paths:` 的 frontmatter 仍然是 always-load。官方逐字：「Rules without a `paths` field are loaded unconditionally and apply to all files.」
- 寫 `paths:` glob 時 **MUST** 用 `git ls-files '<glob>'` 實測它在目標 repo 匹配得到東西。常見錯法是照 consumer 目錄慣例寫（`scripts/x/**`），在 clade home 因為源碼在 `vendor/` 底下而零匹配。

## Good Example

- 這個例子是好的，因為任務型判準落到具體 skill 的 rules/，並寫出哪一步會讀它。

```md
落點：capabilities/core/skills/clade-publish/rules/propagate前工作樹判準.md
觸發點：clade-publish Phase 2 step 1「READ 若準備跑 propagate，先讀取 rules/propagate前工作樹判準.md」
```

## Bad Example

- 這個例子是壞的，因為任務型判準被寫成 always-load rule，且沒有觸發點。

```md
落點：rules/core/propagate-clean-tree.md（無 paths:）
```

# Rule 4 - Q3 它是什麼形態：有 variant 分歧的 MUST 進 conventions.json

- Level: `MUST`

| 形態 | 落點 |
| --- | --- |
| 判準（「什麼情況該怎麼判」） | rule（1／2／自治區），或依 Q2 落到某支 skill 的 `rules/` |
| 有順序的操作步驟 | skill（3）；沒有分支的純範本走 snippet（6） |
| 可執行的東西 | `vendor/scripts/`（5） |
| 這條規則的成因／量測／退場條件 | `docs/rule-rationale/<rule-name>.md`（7） |
| 一次具體失敗的重現與預防 | 走 `/oops`：clade `specs/truth/` 或約束它的 rule §（`docs/pitfalls/` 已退役） |
| 有「推薦做法 vs 過渡做法」的分歧 | `registry/conventions.json` |
| 要在工具事件當下強制、改寫或顯示的行為（文字規約管不住，或管住了仍被重複交代） | 執行期機制，三選一照 Rule 9 |

- 一條實踐若存在 variant（推薦／過渡／已淘汰），**MUST** 進 `registry/conventions.json`（欄位清單見 `references/落點與散播機制.md`）。這是最容易漏的一支：`bp-scan.ts --plan`（新專案該套什麼）與 `convention-conformance-audit`（誰採用了哪個 variant）都以它為唯一輸入，不在裡面的條目對這兩條管線不存在，等於登記了卻不會被套用。
- Q2／Q3 判到 `docs/` 之後還要定子目錄：以 clade `docs/README.md` 的准入 predicate 為 SoT，**NEVER** 憑目錄名字猜，也 **NEVER** 把那些 predicate 複製進本檔。

## Good Example

- 這個例子是好的，因為有推薦與過渡兩種做法的實踐同時登記進 conventions.json。

```md
連帶：registry/conventions.json 新增 `auth-session-storage`，variants：cookie（stable）／localStorage（legacy，migration_to: cookie）
```

## Bad Example

- 這個例子是壞的，因為有 variant 的實踐只寫成 rule，plan 與 conformance 都抓不到。

```md
落點：rules/modules/auth/better-auth/session.md（只寫「建議用 cookie」）
連帶：無
```

# Rule 5 - 縱向：同一落點內要瘦身時，依內容性質下推

- Level: `MUST`
- Q1–Q3 定橫向落點；既有 rule 或 SKILL 太大要瘦身時，依下表決定每段內容留在原處還是下推：

| 這段內容是 | 去哪 |
| --- | --- |
| NEVER／MUST 生效當下要防的具體開脫，或讓禁令綁得住的證據清單 | **留原處**。下推掉就等於拿掉防呆 |
| 這條規則的成因／歷史量測／退場條件 | `docs/rule-rationale/<rule-name>.md`，完全不參與 auto-load |
| 只在編輯特定檔案時才用得到的操作判準 | 新建帶 `paths:` 的 conditional rule |
| 只在做某任務時用得到的內容 | 依形態下推到該 skill：判準 → `rules/`、輸出骨架 → `templates/`、機械步驟 → `scripts/`、查表資料 → `references/`；主檔留一個具名讀取 step |

- 大檔的體積多半是真載重的操作內容，只靠 rationale 外推減不了多少；有效的是最後一列的拆分（例：`commit/SKILL.md` 把只對有 supabase migrations 的 repo 生效的整段下推，主檔留一行觸發判定）。
- `references/` 只收查表資料、指令集、外部逐字來源與授權、外派 worker 自讀的契約；**NEVER** 把含 MUST／NEVER 的判準下推進 `references/`。

## Good Example

- 這個例子是好的，因為判準與骨架各自下推到對應目錄，主檔只留讀取 step。

```md
- 「什麼情況要 rebase 而不是 merge」→ commit/rules/整合方式判準.md（Phase 3 step 2 讀）
- PR body 骨架 → commit/templates/pr-body.md＋.example.md（Phase 5 step 1 讀）
```

## Bad Example

- 這個例子是壞的，因為含 NEVER 的判準被塞進 references/。

```md
- 「NEVER 在 main 上 rebase」連同整段判準 → commit/references/notes.md
```

# Rule 6 - 不收的出口與 memory 邊界

- Level: `MUST`
- **NEVER** 把該進 memory 的東西寫進 clade 源檔：純個人偏好、純事實指針、無法歸進任何規約檔的碎片 → memory（且 MUST 先問過使用者）。
- 反過來，可以變成 rule／cookbook／snippet 的東西 **NEVER** 塞進 memory。
- 被糾正後要留下的可重複工作方法 → 走 `/skill-engineering` 做成或改進 skill；技術踩坑與流程修正 → `/oops`。

## Good Example

- 這個例子是好的，因為純個人偏好被導回 memory，沒有進 clade。

```md
\bp 我喜歡回覆用條列
判定：純個人偏好 → 不進 clade，改走 memory（先問使用者同意再寫）
```

## Bad Example

- 這個例子是壞的，因為個人偏好被寫成 fleet 規約。

```md
落點：rules/core/reply-style.md
```

# Rule 7 - 新規約 MUST 接上消費端與觸發點

- Level: `MUST`
- 新規約若沒有對應的 audit signal、gate 或具名觸發點，它只是一段沒人讀的文字；接不上消費端時要在回報裡明講「這條是純參考」。
- 新增判斷依據時照 clade 訊號誕生契約填觸發條件、消費端、觸發點三欄；觸發點只認三種：skill SOP 的 READ step、工具事件 hook 印 pointer、script／gate 失敗輸出印判準位置。

## Good Example

- 這個例子是好的，因為新規約同時說清楚誰讀、哪一刻讀。

```md
消費端：/commit 0-F 的 bp-scan.ts --changed-only
觸發點：commit gates.md § 0-F 的 READ step
```

## Bad Example

- 這個例子是壞的，因為規約只寫進 docs，沒有任何觸發點。

```md
落點：docs/conventions/propagate.md（需要時去看）
```

# Rule 8 - 反模式：看到自己在做左欄就改道

- Level: `SHOULD`

| 看到自己在做 | 問題 | 改法 |
| --- | --- | --- |
| 新開一個 registry／一支新 audit script | 機械只縮不長；`propagate-maintenance-mode` 三問先答 | 併進既有 registry／既有 audit 的新 check |
| 寫進 `rules/core/` 但內容只有某個 stack 用得到 | 全 consumer 付 always-load 成本換少數人受益 | 移到 `rules/modules/<group>/<variant>/` |
| 寫進 always-load rule，但只有做某任務時才用得到 | 每個 session 付費 | 改落某支 skill 的 `rules/`＋具名觸發點（Rule 3） |
| 寫了 rule 但沒有任何 audit／gate 消費它 | 「跑了沒人看」的純負債 | 補 signal，或明講這條是純參考 |
| 把操作細節寫進 always-load rule | 每個 session 付費，實際只有做那件事時要看 | 依 Rule 5 下推，rule 留 pointer |
| 建了 snippet 但沒有任何 rule 指過去 | 入向 orphan，沒人會讀到 | 補 pointer，或直接刪 |
| 想寫進 `CLAUDE.md`／`AGENTS.md`（全域或 repo 層），包括「加一句提示讓某支 skill 被觸發」 | 每個 session 付費，也繞過 skill 的觸發與模組化；這兩檔原則上淨空 | 交 `/skill-engineering` 落進 skill（description 觸發、`rules/`、`scripts/`）；只有 skill 機制做不到時才寫，回報 MUST 說明做不到的理由（例：notion-hub 跨客戶混淆，原想在全域 CLAUDE.md 加 Notion 觸發提示 → 改由 notion-hub description 承接，並刪掉全域既有的 Notion 段） |

## Good Example

- 這個例子是好的，因為想新開 audit script 時先併進既有 audit。

```md
原本想新建 audit-propagate-clean.ts → 改成 audit-governance-drift.ts 新增 check
```

## Bad Example

- 這個例子是壞的，因為又長出一支只檢查一件事的新 script。

```md
新建 scripts/audit-propagate-clean.ts＋registry/audits.json 新 entry
```

# Rule 9 - 執行期機制：先修既有的，護欄走 command hook，mod 只在三個門檻命中時才選

- Level: `MUST`
- 只有 Rule 4 判到「要在工具事件當下強制、改寫或顯示的行為」才進本條；能用一段判準或一個 SOP step 解決的，照 Rule 2–4 落文字規約，**NEVER** 為了「比較保險」加機制。
- 依序問，第一個命中的就是落點：

| 順序 | 問句（可觀察） | 落點 |
| --- | --- | --- |
| 1 | 既有 hook 或 rule 是否已經在管這件事？查 `capabilities/core/hooks/`、當前 runtime 專案層與使用者層設定裡已掛的 hook、`rules/` | 已在管而訊號仍出現 ＝ 機制失效 → **修那一支**（matcher 沒中、輸出沒人讀、判準過時）。**NEVER** 再疊一條新的 |
| 2 | 這個行為是不是護欄：擋下、要求先確認、或改寫工具輸入？ | command hook（落點 3 的 `capabilities/core/hooks/`）。護欄 **NEVER** 放 mod |
| 3 | 是否命中 mod 門檻（下表）任一列？ | mod（Claude Code 的 function-hooks plugin），實作交 Claude Code **內建**的 `plugin-authoring` skill（harness 隨附，不在 clade 的 skill 目錄；其他 runtime 沒有它。當下 session 的 skill 清單看不到它時，停在提案並回報缺這項能力，**NEVER** 憑印象手寫 mod） |
| 4 | 以上皆否 | command hook；印 pointer 的 hook 仍是 Rule 7 認可的觸發點 |

- 第 2 問不放 mod 的理由：mod 只在 Claude Code 載入，fleet 還有 Codex 與其他 harness，放 mod 的護欄在那些 session 不存在；command hook 走既有投影，各 runtime 都收得到。
- mod 門檻（command hook 做不到、mod 才做得到的三件事）：

| 門檻 | 判法 | 例 |
| --- | --- | --- |
| 常駐畫面 | 資訊要一直留在畫面上，而不是印進對話佔 context、被捲走 | pane、prompt 上方的 band、status line 項目、toast |
| 包住動作前後 | 同一段程式要看到工具呼叫的輸入**與**結果，或要改寫結果 | 依呼叫前記下的狀態改寫工具回傳 |
| 行程內狀態 | 要在 session 內或跨 session 記住先前發生的事，且每次 hook 重讀檔案不可行 | 累計本 session 已觸發幾次後才顯示 |

- 判到 mod 時回報 **MUST** 寫明命中哪一列門檻，並註明「僅 Claude Code 生效」；同一行為若同時需要護欄，護欄部分另落 command hook。
- mod 源檔放 clade 哪個目錄，等第一個 mod 真的要做時再走一次本檔判定；**NEVER** 先建一個沒有內容的落點。

## Good Example

- 這個例子是好的，因為先查到既有 hook，判成修機制而不是新增；另一條畫面需求才判 mod 並寫明門檻。

```md
訊號：使用者近 30 天 4 個 session 說「commit 前先給我看要帶哪些檔」
問 1：`pre-bash-git-commit-only-whitelist.sh` 已在管 commit 範圍，但只擋不顯示 → 機制失效
落點：修 capabilities/core/hooks/pre-bash-git-commit-only-whitelist.sh（擋下時印出將帶入的檔）

訊號：使用者每次回到主持 session 都問「現在有哪些題在等我」
問 1：無既有機制／問 2：不是護欄／問 3：命中「常駐畫面」
落點：mod（prompt 上方 band 顯示待拍板題數；僅 Claude Code 生效），實作交 plugin-authoring
```

## Bad Example

- 這個例子是壞的，因為沒查既有 hook 就新增，而且把護欄放進只有一個 runtime 會載入的 mod。

```md
訊號：使用者常說「別人正在改的檔先不要動」
落點：新做一個 mod，在 tool.call 攔 Edit／Write 後跳出確認
（`capabilities/core/hooks/pre-edit-claim-conflict.sh` 已存在沒被檢查；Codex session 完全沒有這道護欄）
```
