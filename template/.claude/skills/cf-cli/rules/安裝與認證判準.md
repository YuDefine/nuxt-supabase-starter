# Rule 1 - 經 mise 安裝指定版本的 cf，NEVER 全域 npm 安裝

- Level: `MUST`
- 安裝與升級一律 `mise use -g npm:cf@1.0.0-beta.5`，再以 `cf --version` 確認。
- 必須指定版本：beta 期 `mise latest npm:cf` 解析到舊的 `0.15.0`，不是本 skill 實測的版本。
- **NEVER** `npm i -g cf`。

## Good Example

- 這個例子是好的，因為經 mise 釘版本並確認。

```bash
mise use -g npm:cf@1.0.0-beta.5
cf --version
```

## Bad Example

- 這個例子是壞的，因為全域 npm 安裝又沒指定版本。

```bash
npm i -g cf
```

# Rule 2 - 認證走 token 或 profile，多帳號異動前確認身分

- Level: `MUST`
- 認證用 `CLOUDFLARE_API_TOKEN`（account 層操作另設 `CLOUDFLARE_ACCOUNT_ID`），或 `cf auth login`／`--profile`。
- 機器上有多個帳號或 profile 時，任何異動前都必須先 `cf auth whoami`，確認是目標帳號。

## Good Example

- 這個例子是好的，因為異動前先確認身分。

```bash
cf auth whoami --profile staging
cf d1 list --name app-db --profile staging
```

## Bad Example

- 這個例子是壞的，因為多帳號環境下沒確認身分就刪資源。

```bash
cf <刪除資源的指令> <resource-id>
```

# Rule 3 - 找指令先搜尋再看 help，查詢字串不帶識別資訊

- Level: `MUST`
- 第一次用某個子指令或指令失敗時：`cf cli search "<動作 + 資源類型>"` → `<指令> --help`；API 欄位用 `cf schema <指令去掉開頭 cf>`。
- 搜尋字串只寫動作與資源類型；**NEVER** 帶 domain、account／zone／resource ID、email、token。

## Good Example

- 這個例子是好的，因為搜尋字串只描述動作與資源類型。

```bash
cf cli search "purge cache zone"
cf <search 回傳的指令> --help
```

## Bad Example

- 這個例子是壞的，因為搜尋字串帶了 domain 與 zone ID。

```bash
cf cli search "purge cache example.com 023e105f4ecef8ad9ca31a8372d0c353"
```

# Rule 4 - 輸出沒有 `.result` 外層，`--dry-run` 不經 API 驗證

- Level: `MUST`
- 成功時 stdout 就是 API 回應的 `result` 本體（**沒有** `.result` 外層），API 錯誤時 exit 非 0；`jq` 路徑照此寫。
- 異動類指令必須先跑 `--dry-run`；它只在本機印出將送出的 request，不經 API 驗證。
- 其他檔（skill、snippet、runbook）的 cf 異動範例為了簡潔可能省略 `--dry-run`，**NEVER** 讀成可跳過。

## Good Example

- 這個例子是好的，因為 `jq` 直接取本體欄位，異動前先 dry run。

```bash
cf d1 list --name app-db | jq -r '.[0].uuid'
cf <異動指令> <參數…> --dry-run
```

## Bad Example

- 這個例子是壞的，因為照 REST API 習慣多寫了 `.result`，且直接實跑異動。

```bash
cf d1 list --name app-db | jq -r '.result[0].uuid'
cf <異動指令> <參數…>
```
