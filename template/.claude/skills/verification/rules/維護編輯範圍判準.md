
# Rule 1 - 只可修改被維護的 verify skill 目錄

- Level: `MUST`
- 只可修改被維護的 `<skills-root>/verify-<app>/`：`SKILL.md`、`features/` 與它自己擁有的 harness scripts。只維護 verification infrastructure，**NEVER** 在同一輪修產品 code。

## Good Example

- 這個例子是好的，因為修正只落在 target 目錄。

```text
<skills-root>/verify-<consumer-id>/features/loans.md：補上漏列的 CLI entry point
```

## Bad Example

- 這個例子是壞的，因為改到 target 以外的檔。

```text
順手修 e2e/fixtures/seed.ts 讓 drive 過
```

# Rule 2 - 每個落差判成 doc drift／harness gap／product gap 之一

- Level: `MUST`
- map 描述錯誤 → doc drift，修 map。
- app 正常但 harness 無法 drive → harness gap，修 owned harness 並 live re-prove。
- app 行為真的壞掉 → product gap，只回報；NEVER 改產品 code，NEVER 把 map 改成假裝壞行為正確。
- 任何 map 或 harness correction 都要重跑受影響 feature。產品 gap 不進本次 diff；Experience acceptance 仍由產品 owner／指定 reviewer 決定，live pass **不能**自動代表 UX accepted。
- `verified-unreachable` 必須列 attempted route 與具體 unmet prerequisite；若 map 漏了 prerequisite，那是 doc drift。

## Good Example

- 這個例子是好的，因為 product gap 只回報。

```text
loans 列表排序與 map 不符；source 顯示 sort 參數被忽略 → product gap，列入 product_gaps，不改 map
```

## Bad Example

- 這個例子是壞的，因為把 map 改成符合壞掉的行為。

```text
排序壞了 → 把 features/loans.md 的預期改成「依建立時間排序」
```
