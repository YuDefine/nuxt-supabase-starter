# 跨環境版本對齊判準（Phase P）

觸發點：[phases/parity.md](../phases/parity.md) Step P.3（讀完矩陣、要判讀與分派每一格之前）；Rule 7 另由 SKILL.md Step 0.2（目標刷新）讀（進 Phase P／M／T 前）。

# Rule 1 - 矩陣每一格依狀態處置；量不到、未宣告、沒有目標 NEVER 讀成對齊

- Level: `MUST`
- 矩陣（`audit-ci-toolchain-parity.ts --matrix`）一格的狀態取該層最嚴重的觀測值；處置依下表，**NEVER** 把後四類讀成 ✓、**NEVER** 放進「已對齊」的分母：

評估：first-match；以上皆非 → M*

| id | 狀態 | 意思 | 處置 |
| --- | --- | --- | --- |
| M1 | `aligned` | 宣告或實測等於 SoT 目標（major-lts：同 major） | 無 |
| M2 | `covered` | 版本由前一層決定（setup action 回到 repo 宣告、`pnpm/action-setup` 跟 `packageManager`） | 看它指向的那一層 |
| M3 | `drift` | 量得到且不等於目標 | Rule 2 分派 |
| M4 | `unpinned` | 有宣告但不是確切版本（range、`@latest`、`lts/*`、`node:lts`、`${{ }}`、ARG 展開、缺 `.nvmrc`） | 先宣告化（Rule 2 第 1 序位） |
| M5 | `undeclared` | runner 標籤對不到 `registry/runner-toolchain.json`，或 consumers-meta 沒有 entry | 補宣告：runner 是 clade 自己的 registry（clade worktree 補），consumer-meta 是 consumer 的檔（relay） |
| M6 | `unmeasurable` | 結構上量不到（self-host 沒有 runtime probe、runner 沒 `sshTarget`、只做靜態掃描） | 補量測面；**NEVER** 推論成「應該沒落後」 |
| M7 | `no-target` | SoT 的 target 是 null 或 measure-only | 要不要定目標是 fleet 決策，走 Step P.5 問 user |
| M8 | `n/a` | 這一層沒有這個工具 | 無 |
| M* | 其他值 | script 輸出了本表沒有的狀態 | STOP，回報原始輸出；**NEVER** 讀成對齊 |

- 回報分母 **MUST** 是「量得到的格數」，並把 `undeclared`／`unmeasurable`／`no-target` 的格數另列；**NEVER** 用 fleet 全體當分母宣告「N% 對齊」。

## Good Example

- 這個例子是好的，因為量不到的格另列，沒有混進對齊率。

```text
node：量得到 27 格（aligned 23、unpinned 2、drift 2）；另 undeclared 4、unmeasurable 7（某 consumer… self-host runtime 無 probe）
```

## Bad Example

- 這個例子是壞的，因為把 unmeasurable 當成沒問題，算出假的對齊率。

```text
node：38 格中 36 格沒有 ⚠ → fleet node 95% 對齊
```

# Rule 2 - 分派依固定序位：先宣告化，再升版；clade NEVER 執行遠端升級

- Level: `MUST`
- 每一格 `drift`／`unpinned`／`undeclared` 依序取**第一個命中**的序位，寫進 rollout plan 的「升級路徑」欄：

| 序位 | 命中條件 | 升級路徑 | 由誰做 |
| --- | --- | --- | --- |
| 1 宣告化 | 版本沒有寫在 repo：runner 裸呼叫預裝 CLI（可改 setup action 釘版）、Dockerfile `FROM` 浮動、self-hosted compose 不在 repo、`npx <cli>` 無依賴 | 把版本寫進 repo，之後隨 commit 從 dev 推到 staging／prod | relay 給該 consumer |
| 2a 已宣告落後，有上游 BC clause | repo 宣告存在、落後 target，且改動能一對一對到 release notes 的 BC | Phase F（套件）或 Phase T（pnpm／node） | 本 skill Phase F／T |
| 2b 已宣告落後，無 BC clause | 同上但找不到對應 clause（純版號對齊、CI `version:` 對 pin） | relay，brief 指 SoT 與 cookbook | relay 給該 consumer |
| 3 本機落後 | dev 列 drift | Phase M | 本機 session |
| 4 只能預裝在主機上 | docker engine、psql、runner 必備且無 setup action 的 binary | runner 主機的 owner（第 3 段由 ci-runners 承接；之前一律 `flow ask`） | 授權後的 infra owner |
| 5 無法宣告也無 owner | 以上皆否 | `flow ask` 進待拍板佇列 | user |

- clade 自己的宣告面（`registry/toolchain.json`、`registry/runner-toolchain.json`）由 clade 在 worktree 改；consumer 的檔一律 relay（per `.claude/skills/clade-home/rules/clade-role-and-todo-discipline.md` § Consumer 工作命中時 MUST relay）。
- **NEVER** 在 clade session ssh 進 runner／staging／prod 升版或改設定——遠端升級是 consumer 的 production 動作；clade 擁有的是 SoT、掃描與收斂追蹤。
- **NEVER** 跳過序位 1 直接要 consumer「上去升一下」：版本沒寫進 repo，誰升都會在下一次 deploy 或重建主機時漂回去。

## Good Example

- 這個例子是好的，因為 runner 裸呼叫的 CLI 先要求改成 setup action 釘版，版本回到 repo。

```text
某 consumer ci.yml:178 migrate job 在 fc-supabase-prod 裸呼叫 supabase（unmeasurable）
→ 序位 1 宣告化：relay 某 consumer「改用 supabase/setup-cli 並釘 SoT target」，驗收＝矩陣 runner 欄變 covered
```

## Bad Example

- 這個例子是壞的，因為 clade 主線 ssh 進 prod 主機升 binary，版本仍不在 repo。

```text
ssh fc-supabase-prod 'sudo npm i -g supabase@2.120.0'
```

# Rule 3 - 遠端探測只在有授權的 session 跑，串行、唯讀

- Level: `MUST`
- 矩陣預設不連任何遠端（runner 欄是靜態掃描、remote 欄是宣告面分類）。要量實際版本才跑：
  - runner：`node ~/offline/clade/scripts/audit-runner-toolchain-drift.ts --probe --upstream`
  - self-hosted 主機 image：`node ~/offline/clade/scripts/audit-remote-env-version-drift.ts --probe-hosts [--official-compose <path>]`
- 兩者都是跨機器 side effect：**MUST** 在 user 明確授權探測的 session 跑；腳本本身串行、一條短指令（`<bin> --version`／`cat <composeDir>/docker-compose.yml`），**NEVER** 改成平行或加任何寫入指令。`pnpm audit:manual` 批次不會觸發探測。

## Good Example

- 這個例子是好的，因為探測前先取得授權，且照腳本的串行唯讀方式跑。

```text
user：「可以探測 fc-supabase-prod」→ audit-runner-toolchain-drift.ts --probe --upstream
```

## Bad Example

- 這個例子是壞的，因為沒授權就為了量版本平行 ssh 多台 prod。

```bash
for h in prod-a prod-b; do ssh "$h" supabase --version & done
```

# Rule 4 - remote 層：audit-remote-env-version-drift 的六類與 hosts 五態分開讀

- Level: `MUST`
- 矩陣 remote 欄只對 node 判 runtime；Workers 的 `compatibility_date` 與 self-hosted stack image 由 `audit-remote-env-version-drift.ts` 直接輸出。六類（Workers／宣告面）：

| 類別 | 意思 | 動作 |
| --- | --- | --- |
| `drift` | 量得到且落後（目前唯一量得到的是 Cloudflare Workers 的 `compatibility_date`） | relay 給該 consumer |
| `invalid` | 讀到一個值但它不是有效日期 | 修那個值。**不列入「量得到」的分母** |
| `ambiguous` | 同一個檔給出多個相異日期（top-level ＋ `[env.*]` 覆寫） | 先確定哪一個是 production；audit 不替你挑 |
| `data-missing` | platform 有 probe 但這台沒有可讀的值 | 再分兩種：root 底下沒有設定檔（確認 config 位置或 platform 宣告）／有檔但缺欄位（補欄位） |
| `undeclared` | `consumers-meta.json` 根本沒有這台的 entry | **漏登記，不是不部署**——補宣告 |
| `unmeasurable` | node runtime 版本結構上量不到（self-host 沒有 runtime probe；宣告與檔案不一致也歸此） | self-hosted Supabase 主機改看 `hosts` 段：consumer 在 `.claude/consumer-meta.json` 補 `deploy.hosts[]`（`rules/core/consumer-meta.md` § 遠端主機）。補宣告不是升版，NEVER 影響 exit code |

- 第七類 `hosts`（`--probe-hosts` 才有；`deploy.hosts[]` 每台 `{ role, ssh, stack, composeDir }`，唯讀比官方 self-hosted compose 的 image tag）：

評估：first-match；以上皆非 → H*

| id | 狀態 | 意思 | 動作 |
| --- | --- | --- | --- |
| H1 | `aligned` | image tag 與官方 compose 一致 | 無 |
| H2 | `drift` | 有 image 與官方不同／缺／多 | relay 給該 consumer 升版（序位 1：compose 進 repo 優先） |
| H3 | `unreachable` | ssh 連不上（exit 255／逾時） | 修 ssh alias 或網路。**NEVER** 讀成 aligned |
| H4 | `unreadable` | 連得上但讀不到 compose（缺 `composeDir`、檔不存在、stack 無 probe） | 補 `composeDir` 或確認路徑。**NEVER** 讀成 aligned |
| H5 | `no-baseline` | 官方 compose 取不到（`gh api` 失敗） | 修 gh 認證或帶 `--official-compose <path>`。**NEVER** 讀成 aligned |
| H6 | （未探測） | 有宣告但沒帶 `--probe-hosts` | 要量就在有授權的 session 帶旗標；未探測 **NEVER** 讀成 aligned |
| H* | 其他值 | script 輸出了本表沒有的狀態 | STOP，回報原始輸出 |

- 「量得到」表的 `宣告 platform` 欄是 `none` 的列（如 starter template 帶 `wrangler.jsonc`）沒有遠端，**NEVER** 當成遠端 drift relay；宣告 `self-host` 卻有 `wrangler.jsonc` 報 `unmeasurable`，**NEVER** 拿檔案值當遠端版本。

## Good Example

- 這個例子是好的，因為 data-missing 依成因分兩種處置。

```text
某 consumer data-missing：有 wrangler.jsonc 但缺 compatibility_date → relay「補欄位」
```

## Bad Example

- 這個例子是壞的，因為把未探測的 hosts 當成 aligned。

```text
某 consumer 宣告了 deploy.hosts，這輪沒帶 --probe-hosts → 標 aligned
```

# Rule 5 - runner 層：audit-runner-toolchain-drift 的八態分開讀

- Level: `MUST`
- workflow 在 self-hosted runner 上裸呼叫預裝 CLI 時，CI 紅燈的表面症狀像 migration 或程式寫壞（2026-08-28 某 consumer：runner 的 supabase CLI 落後 44 個 minor，報 `cannot insert multiple commands into a prepared statement`）。self-hosted job 紅燈指不到原因時 **MUST** 先跑 runner audit。宣告面：runner 拓撲在 `registry/runner-toolchain.json`，工具目錄與比對基準在 `registry/toolchain.json`。

評估：first-match；以上皆非 → U*

| id | 狀態 | 動作 |
| --- | --- | --- |
| U1 | `behind` | 序位 1：改用 setup action 釘 SoT target；做不到才序位 4。**NEVER** 在 clade 主線 ssh 上去升 |
| U2 | `ahead-of-pin` | exact 工具高於 SoT target（types 格式同樣會漂移）：同 `behind` 處置，或經 Step P.5 把 SoT 往上調 |
| U3 | `probe-failed`（`failure=connect`） | 修 ssh 連線或 sshTarget |
| U4 | `probe-failed`（`failure=command`） | ssh 通了但遠端指令失敗：binary 不在 runner 上，或探測指令不對（改 SoT 的 `probeArgs`，如 go 用 `version`） |
| U5 | `probe-failed`（`failure=parse`） | 指令成功但輸出讀不出版本：看 `reason`，補 `probeArgs` |
| U6 | `undeclared-runner` | 在 `registry/runner-toolchain.json` 的 `runners[]` 補這組標籤所在的 runner |
| U7 | `unmeasurable` | 補 `sshTarget`，或在授權 session 帶 `--probe` |
| U8 | `upstream-unknown` | measure-only 工具沒有上游可比：補 SoT 的 `upstream`，或帶 `--upstream` |
| U9 | `repo-pinned` | 已回到 repo 宣告（setup action），歸 ci 層判 |
| U* | 其他值 | STOP，回報原始輸出 |

- `unmeasurable`／`probe-failed`／`upstream-unknown` **NEVER** 讀成 current。

## Good Example

- 這個例子是好的，因為 probe-failed 依 failure 分型處置。

```text
go @ runner-x probe-failed failure=command → SoT tools.go.probeArgs 改 "version"
```

## Bad Example

- 這個例子是壞的，因為把 probe-failed 當成沒落後。

```text
supabase @ fc-supabase-prod probe-failed → 沒量到落後，略過
```

# Rule 6 - rollout plan 只寫目標狀態與驗收，收斂以重跑矩陣為準

- Level: `MUST`
- rollout plan 每列只寫：工具、層、consumer、現值、目標、升級路徑（Rule 2 序位）、驗收、狀態。**NEVER** 寫 consumer 端要改哪幾行、拆實作步驟或排它的 phase——那是「替 consumer 規劃實作」反模式；relay brief 也只帶訊號＋SoT pointer＋驗收。
- 驗收一律寫成可重跑的矩陣條件（例：`--matrix --tool supabase --consumer <consumer-id>` 的 ci 欄為 aligned），**NEVER** 用「consumer 回報已完成」結案。
- 狀態只用四值：`pending`（未送達）→ `relayed`（已 relay，附 pane／label）→ `aligned`（重跑矩陣證實）／`blocked`（consumer 回報卡住，同時 `flow ask`）。每次重跑矩陣就更新狀態；`relayed` 跨過一輪 improvement-digest 仍未 `aligned` 的列 **MUST** 轉 `flow ask`，**NEVER** 讓它靜置在 relayed。

## Good Example

- 這個例子是好的，因為只寫目標與可重跑的驗收。

```text
| supabase | ci | <consumer-id> | 2.78.1 ×5 | 2.120.0 | 2b relay | --matrix --tool supabase --consumer <consumer-id>：ci aligned | relayed（<consumer-id>/version-parity-supabase） |
```

## Bad Example

- 這個例子是壞的，因為替 consumer 寫了實作步驟，驗收又只靠回報。

```text
某 consumer：改 deploy-staging.yml:142 與 deploy-production.yml:266 的 version，再跑 supabase gen types，做完回報即結案
```

# Rule 7 - fleet 目標每一輪都是共同可達最新版，NEVER 沿用上一輪的固定版號

- Level: `MUST`
- Charles 2026-10-13：「每次執行 /version-upgrade 就是取共同可達的最新版」。進 Phase P、M、T 之前 **MUST** 跑 `node ~/offline/clade/scripts/audit-ci-toolchain-parity.ts --refresh-targets`，本輪比對與升版的目標一律取「共同可達最新」欄。
- 共同可達的定義（四條全過；實作在 `scripts/lib/toolchain-registry.ts`）：
  1. 穩定版：`latest` dist-tag 以下、非 pre-release
  2. node：最新 LTS 的 major（Current 線不算）
  3. 候選版的 `engines.node` 接受 fleet node major（刷新後的）
  4. 發佈滿 `reachability.minimumReleaseAgeMinutes`（pnpm 11+ 預設 1440 分鐘；太新的版本 consumer 端 pnpm 裝不起來）
- 各列處置：

| 動作 | 意思 | 處置 |
| --- | --- | --- |
| `keep` | SoT 已是共同可達最新 | 照 SoT |
| `bump` | SoT 落後 | 本輪以新目標為準；clade worktree 帶 `--write` 寫回 SoT（supabase CI 範本副本同步）並 publish。**NEVER** 為了「這輪先不動」沿用舊目標 |
| `manual` | exact 工具沒有 `npm` 來源，算不出可達版本 | 問 user 定目標或補 `npm` 欄位 |
| `error` | 查詢失敗（網路、registry） | 回報原錯誤，本輪 **NEVER** 宣稱目標已是最新 |

- 偏離規則（釘在舊版、跳過某個壞版）是 user 的決定：寫進 SoT 該工具的 `note` 並附理由；**NEVER** 主線自行挑一個比共同可達更舊或更新的版本。
- consumer 端的 exact 工具高於 SoT（`ahead-of-pin`）仍是不一致：先刷新 SoT，刷新後仍高於共同可達（例：裝了發佈未滿一天的版本）才回頭要該層降回。

## Good Example

- 這個例子是好的，因為每輪先刷新，SoT 落後就寫回並以新目標分派。

```text
--refresh-targets：supabase 2.120.0 → 2.121.0 bump → clade worktree --write → publish → --matrix 以 2.121.0 判各層
```

## Bad Example

- 這個例子是壞的，因為沿用上一輪寫死的版號，或自己挑一個 pre-release。

```text
SoT 還寫 2.120.0 就直接拿來比；或「2.121.0-beta.3 比較新」→ 改成目標
```
