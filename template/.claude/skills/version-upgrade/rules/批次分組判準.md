# 批次分組判準

觸發點：`phases/consumer-batch.md` Step B.3（分類完、寫計畫檔之前，決定哪些 item 合成同一列、同一 commit）。

# Rule 1 - 同家族的套件合成一列、一個 commit，一起升到同一版

- Level: `MUST`

評估：first-match；以上皆非 → 各自一列

| id | 判準 | 例 | 處置 |
| --- | --- | --- | --- |
| G1 | 同一個 release 系列（monorepo 一起發版，版號相同） | `vue` 與 `@vue/compiler-sfc` 同為 3.5.44 | 合成一列 |
| G2 | 同 scope 前綴且 target 版號相同 | `@commitlint/cli` 與 `@commitlint/config-conventional` | 合成一列 |
| G3 | 一方是另一方的 peer 依賴、或 adapter／plugin 綁定主套件版本 | `@pinia/colada` 與 `@pinia/colada-nuxt` | 合成一列 |
| G4 | 使用者在 plan gate 指定 lockstep（「vue 跟 nuxt 一起動」） | — | 合成一列，或整列排除 |
| G* | 以上皆非 | — | 各自一列 |

合成的一列：`item` 欄寫家族名（例 `vue 家族`），列出所有成員與 target；派工 prompt 的 `<pkg>` 帶全部成員，一次 `pnpm add` 一起裝；commit message 寫家族名。家族內一個成員失敗＝整列失敗，**NEVER** 拆開只升成功的那幾個（拆開正是 first-pass 失敗的成因）。

## Good Example

- 這個例子是好的，因為同 release 系列合成一列，一次升。

```text
vue 3.5.30→3.5.44、@vue/compiler-sfc 3.5.30→3.5.44 → 一列「vue 家族」→ 一次 pnpm add → 一個 commit
```

## Bad Example

- 這個例子是壞的，因為家族被拆開升，first-pass 失敗、research 白跑。

```text
先升 vue → typecheck 紅（compiler-sfc 版本不符）→ 升 research
```
