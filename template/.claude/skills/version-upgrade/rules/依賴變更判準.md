# 依賴變更判準

觸發點：`phases/consumer-batch.md` Step B.1（盤點完、決定 target 前讀 Rule 1）、Step C.1（寫派工 prompt、要移除依賴或重生 lockfile 時讀 Rule 2）、Step C.6（升 action 前讀 Rule 3）。

# Rule 1 - target 版號：`@types/*` 封頂、`catalog:`／`overrides:` 同步、`npm:` alias 追目標

- Level: `MUST`

fleet 14 consumer 中 9 個用 `pnpm-workspace.yaml` 的 `catalog:`：

- `catalog:` 條目與 `overrides:` 條目 **MUST 同步改**——兩者共同釘選同一個版本，改一邊忘一邊 = lockfile 不動
- `npm:` alias 條目（如 `vite: npm:@voidzero-dev/vite-plus-core@^0.3.0`）的版號追的是 **alias 目標 package**，不是 alias 名——`pnpm outdated` 報的也是目標 package 版本
- `@types/*` 特殊封頂（MUST 在分類後立刻套用）：

  `@types/<lib>` 的 major 版號**跟著對應 runtime / lib 版本走**，不是越新越好。**MUST** 把每個 `@types/*` 套件的 target version 上限封頂為 project 當前對應版本的 major：
  - `@types/node` → ≤ project Node major（讀 `.nvmrc` / `.tool-versions` / `package.json` `engines.node` / `Dockerfile` 任一可靠來源；都查不到才問 user）
  - `@types/react` → ≤ `dependencies.react` 的 major
  - 其餘 `@types/<lib>` 同理跟 `<lib>` 自身 major

  若 `outdated` 給的 Latest 超過上限，target 改成「上限 major 內最新」（例：Node 20 環境 + `@types/node` Latest 是 22.x → target 鎖 `^20.x` 最新 minor/patch，**不**升 22）。Step B.4 寫出的計畫表 **MUST** 在這些 `@types/*` 條目後標註「(capped to Node N / react N)」讓 user 看到封頂邏輯有作用。

  **NEVER** 為了「升到最新」把 `@types/*` 推超過對應 runtime / lib — 型別會漂移：typecheck 用的是 newer types，但 runtime 跑的是舊版 API，bug 表現是「TS 說沒問題、prod 卻炸」這種最難 debug 的型別。

## Good Example

- 這個例子是好的，因為 `@types/node` 跟著 project 的 Node major 封頂，並在計畫表標出。

```text
.nvmrc = 20、outdated 報 @types/node latest 22.x → target 鎖 20.x 最新 → 計畫表標「(capped to Node 20)」
```

## Bad Example

- 這個例子是壞的，因為只改了 `catalog:`，沒同步 `overrides:`。

```text
pnpm-workspace.yaml catalog: vue ^3.5.44、overrides: vue 3.5.30 → pnpm install 後 lockfile 不動
```

# Rule 2 - 移除依賴三判準；`allowBuilds` 條目改 `false`、NEVER 刪

- Level: `MUST`

本條（批次中順手清掉未使用套件、**或**重生 lockfile 清掉殘留解析時都適用——後者同樣會讓套件離開依賴樹）：

一個套件只有下列三條**全部**成立，才算可以從依賴樹拿掉。任一條不成立就保留，並把理由寫進該條目上方的註解：

評估：all-match

| id | 判準 | 指令 | 它擋的是哪一種 |
| --- | --- | --- | --- |
| V1 | `pnpm why <pkg>` 完全無輸出 | `pnpm why <pkg>` | 仍是某個已安裝套件的 optional peer |
| V2 | vendored tgz／`file:` 來源內沒有任何 import | `for t in $(git ls-files '*.tgz'); do tar -xzOf "$t" \| grep -qE "['\"]<pkg>['\"]" && echo "$t"; done`；`file:` 目錄改 `grep -rlE "['\"]<pkg>['\"]" <dir>` | **沒宣告**卻靜態 import 它的套件——`pnpm why` 對這種零訊號 |
| V3 | consumer 的 verify-commands **全鏈**綠，含 BDD／e2e | 照 `.clade/rules/verify-commands.md`（或 `.claude/rules/verify-commands.md`）逐條跑 | 前兩條都漏掉的 runtime 解析 |

**NEVER** 用「typecheck / lint 綠」代替V3：依賴變更沒有 `.ts` diff，而 ESM 的 bare specifier 解析只在執行時發生。

V1 **有輸出**時，`pnpm-workspace.yaml` 的 `allowBuilds` 對應條目改 `false`（明說不建置），**NEVER** 刪掉——缺條目時 pnpm 以 `ERR_PNPM_IGNORED_BUILDS` **exit 1**，而 `typecheck` / `lint` / `format` 都先跑 deps-status check（內部呼叫 `pnpm install`），三個 script 在跑到本體前就一起紅，症狀與成因完全脫鉤。`false` 是決定，缺條目是沒決定，pnpm 只接受前者。改用 `ignoredBuiltDependencies:` 無效（pnpm 11.24 實測會忽略它，並往 `allowBuilds` 寫回 `set this to true or false` 佔位）。

2026-09 某 consumer 實證：09-09 移除 `better-sqlite3` 宣告（`0403915`）時它仍靠 db0 的 optional peer 被裝著，BDD 照綠；09-14 重生 lockfile 清掉那筆殘留（`ade3e10`）後套件真的消失，而 vendored `@specformula/node` 靜態 import 它——BDD 從那一筆起紅，三天後才被發現。V2 在第一步就看得到。SpecFormula consumer 可跑 `node ~/offline/clade/scripts/audit-specformula-adoption.ts --repo .` 看 `sqlite` 欄。

細節見 [[pitfall-pnpm-allowbuilds-entry-removal-reddens-unrelated-scripts]]。

## Good Example

- 這個例子是好的，因為三條全成立才移除，V3跑到 BDD。

```text
pnpm why foo 無輸出 → vendored tgz 無 import → verify-commands 全鏈（含 BDD）綠 → 移除
```

## Bad Example

- 這個例子是壞的，因為以 typecheck 綠代替V3，並刪掉 `allowBuilds` 條目。

```text
pnpm why better-sqlite3 有輸出 → 仍刪 allowBuilds.better-sqlite3 → typecheck/lint/format 一起紅
```

# Rule 3 - GitHub Actions 由本 skill 升、不靠 Dependabot；升 action 一律 `pnpm update --include-github-actions`

- Level: `MUST`

Dependabot 唯一的更新途徑是**開 PR**。不走 PR 流程的 consumer（本 fleet 絕大多數）會讓那些 PR 無限累積：沒人 review、沒人合、還把 major 版跳號（`upload-artifact` v4→v7 這種）混在裡面當成例行 bump。

改由本 skill 接手後：升級走既有的 worktree + per-item commit + changelog 分類，major 跳號會被 `rules/changelog分類判準.md` Rule 1 標成 `adaptation` 並在計畫表攤開給 user 拍板，而不是靜靜躺在一個沒人看的 PR 裡。

**Consumer 端配套**：接手的 consumer **MUST** 刪掉 `.github/dependabot.yml`（留著會繼續開 PR）並關掉既有的 dependabot PR。`.github/dependabot.yml` 存在 = 本 skill 的 actions 盤點沒被採用。

升 action 一律一支一次：

```bash
pnpm update --include-github-actions <owner/repo> [--latest]
```

- 不帶 `--latest` 只升到同 major 內最新；major 跳號（計畫表標 `adaptation`）才帶 `--latest`
- pnpm 會把 tag-ref 改成 SHA＋tag 註解（`@<sha> # v7.0.0`）；這是預期結果，**NEVER** 手動改回 tag-ref
- **NEVER** 帶 `--lockfile-only`：對 action 是 exit 0 零改動（2026-10-20 前置實測①），看起來成功、什麼都沒升
- pnpm < 11.16 的 consumer 用 `corepack pnpm@<SoT pnpm target> --pm-on-fail=ignore update …`（與 `inventory.py` 同一條路）

## Good Example

- 這個例子是好的，因為一支 action 一次、major 跳號才帶 `--latest`。

```text
pnpm update --include-github-actions actions/checkout --latest → ci.yml、e2e.yml 兩處改成 @<sha> # v7.x
```

## Bad Example

- 這個例子是壞的，因為帶了 `--lockfile-only`，exit 0 卻零改動。

```text
pnpm update --include-github-actions --lockfile-only → 「全部升好了」
```
