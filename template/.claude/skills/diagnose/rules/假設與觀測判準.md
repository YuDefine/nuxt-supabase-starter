
# Rule 1 - 測任何一個之前先列 3–5 個排序過的可證偽假設

- Level: `MUST`
- 先產出 **3–5 個**依可能性排序的假設，再開始驗證其中任何一個。只產生一個假設會錨定在第一個看似合理的念頭上。
- 每個假設 **MUST** 可證偽，寫出它的預測，格式：

  > 若 <X> 是原因，則 <改 Y> 會讓 bug 消失／<改 Z> 會讓它更糟。

- 說不出預測的假設只是感覺（vibe）：丟掉，或改寫到說得出預測為止。
- 清單給使用者看，是因為使用者常有能立刻重排的領域知識（「#3 那塊上週剛部署過」），或知道哪些假設早就排除過；這是便宜又省時的檢查點。

## Good Example

- 這個例子是好的，因為四個假設都有排序，且各自寫出可觀察的預測。

```text
1. 若 discount 查無資料時回 undefined 是原因，則 fixture 換成有效折扣碼會轉綠；把折扣碼改成不存在的值仍紅。
2. 若 supabase .maybeSingle() 改 .single() 的升級是原因，則 pin 回舊版 supabase-js 會轉綠。
3. 若 RLS 擋掉 discounts 讀取是原因，則改用 service role client 會轉綠。
4. 若 order.items 為空陣列時才觸發，則 fixture 加一個 item 會轉綠。
```

## Bad Example

- 這個例子是壞的，因為只有一個假設，也沒有預測。

```text
應該是 discount 那邊的 null 處理有問題，我去看一下。
```

# Rule 2 - 每個觀測對應一個預測，一次只改一個變數

- Level: `MUST`
- 每一個 probe（加 log、下斷點、改設定）都必須對應到 Phase 3 某個假設的某個預測；說不出它在驗哪個預測的 probe 不要加。
- **一次只改一個變數**，改完重跑迴圈再改下一個；同時改兩個就無法判斷是哪個造成結果。
- 觀測工具偏好序：
  1. **Debugger／REPL 檢查**：環境支援時優先，一個斷點勝過十行 log（例：`node --inspect` 或在 `vp test` 下 `debugger`）。
  2. **針對性 log**：放在能區分不同假設的邊界上。
  3. **NEVER**「全部都 log 再 grep」。

## Good Example

- 這個例子是好的，因為 probe 指名驗哪個預測，且只動一個變數。

```text
驗假設 1 的預測「折扣碼不存在時仍紅」：只把 fixture 的 code 從 SAVE10 改成 NOPE，其餘不動 → 重跑仍紅，符合預測。
```

## Bad Example

- 這個例子是壞的，因為它一次改多處、到處加 log，結果無法歸因。

```text
同時升級 supabase-js、改用 service role、在每個函式開頭 console.log 參數，再跑一次看看。
```

# Rule 3 - 所有除錯 log MUST 帶唯一前綴 tag

- Level: `MUST`
- 每一行除錯 log 都加上同一個唯一前綴，例如 `[DEBUG-a4f2]`（每次除錯 session 換一個隨機後綴）。
- 收尾時用一次 `grep` 找出全部並移除；沒有 tag 的 log 會留下來，有 tag 的 log 會被清掉。

## Good Example

- 這個例子是好的，因為 tag 一致，收尾一行 grep 就能清乾淨。

```text
console.log('[DEBUG-a4f2] discount row', row)
收尾：grep -rn 'DEBUG-a4f2' server/ app/ test/  → 0 筆
```

## Bad Example

- 這個例子是壞的，因為 log 沒有 tag，收尾時無從確認是否清完。

```text
console.log('row', row)
console.log('here')
```

# Rule 4 - 效能退化走量測與二分，不靠 log

- Level: `MUST`
- 效能退化時 log 通常是錯的工具。先建立 baseline 量測（timing harness、`performance.now()`、profiler、query plan 例如 `EXPLAIN ANALYZE`），再二分（commit、資料量、設定）。
- 先量測，後修正；**NEVER** 憑感覺挑一個「看起來慢」的地方先優化。

## Good Example

- 這個例子是好的，因為先有可重複的數字，再用二分縮範圍。

```text
baseline：curl -w '%{time_total}' /api/orders?page=1 → 上週 tag 0.8s、HEAD 6.1s
git bisect run ./scripts/perf-check.sh（> 2s 判 bad）→ 指向 a1b2c3「orders 加 include items」
EXPLAIN ANALYZE 顯示 order_items 走 Seq Scan
```

## Bad Example

- 這個例子是壞的，因為沒有量測就加 log 猜位置。

```text
在每個 query 前後加 console.time，看哪個比較久，應該是 items 那段。
```
