
# Rule 1 - 回饋迴圈依建構順序挑第一個做得出來的

- Level: `MUST`
- 一條會在這個 bug 上變紅的 pass/fail 訊號，是找到原因的前提：二分、假設驗證、觀測都只是在消耗它；沒有它，讀再多 code 也只是猜。在這一步投入不成比例的力氣，積極、有創意、不輕易放棄。
- 大致依下列順序，選第一個在此 bug 上做得出來的；排在後面的只在前面的做不出來時才用：
  1. **失敗測試**：在任何能碰到 bug 的 seam——unit、integration、e2e（例：`pnpm exec vp test test/order-sync.test.ts`）。
  2. **curl／HTTP script**：打正在跑的 dev server（例：`pnpm dev` 起 Nuxt 後 `curl` 對應 API route）。
  3. **CLI 呼叫**：餵 fixture 輸入，把 stdout 跟已知正確的 snapshot 做 diff。
  4. **Headless browser script**（Playwright）：驅動 UI，對 DOM、console 或 network 下斷言。
  5. **重播擷取的 trace**：把真實的 network request／payload／event log 存到磁碟，單獨餵進那條 code path。
  6. **一次性 harness**：起系統的最小子集（一個 service、mock 掉依賴），用一次函式呼叫走到 bug 的 code path。
  7. **Property／fuzz 迴圈**：bug 是「有時候輸出錯」時，跑 1000 組隨機輸入找出失敗型態。
  8. **二分 harness**：bug 出現在兩個已知狀態之間（commit、資料集、版本），把「開在狀態 X、檢查、重來」自動化，讓 `git bisect run` 能跑。
  9. **差分迴圈**：同一份輸入分別跑舊版與新版（或兩組設定），diff 輸出。
  10. **HITL 腳本**：最後手段。必須由人點擊時，用 skill 的 `templates/hitl-loop.sh` 驅動**人**，讓迴圈仍然有結構：腳本由使用者在自己的終端機執行（agent 的 Bash 沒有使用者的終端機，`read` 會讀到 EOF），擷取的 `KEY=VALUE` 輸出回到 agent 手上。
- 建對回饋迴圈，這個 bug 就修好九成。

## Good Example

- 這個例子是好的，因為它先試排序前面的方式，做不出來才往下，並說明原因。

```text
500 只在帶折扣碼的訂單出現。
1. 失敗測試：server/api/orders.post.ts 沒有既有測試 seam 可直接打 → 先試 2。
2. curl：pnpm dev 起來後 curl -X POST /api/orders -d @fixture/discount-order.json → 回 500，訊息與使用者一致。採用。
```

## Bad Example

- 這個例子是壞的，因為它跳過可自動化的方式直接請人點，等於沒有迴圈。

```text
請你打開瀏覽器下一張帶折扣碼的訂單，看看是不是還會 500，我再根據你的回覆推測原因。
```

# Rule 2 - 有了迴圈之後 MUST 收緊：更快、訊號更尖、更穩定

- Level: `MUST`
- 把迴圈當產品看待。有了一條之後，逐一問三題並動手改：
  - **能更快嗎？** 快取 setup、跳過無關的初始化、縮小測試範圍（只跑單檔、單一 `it`）。
  - **訊號能更尖嗎？** 斷言使用者描述的那個症狀，而不是「沒有 crash」。
  - **能更穩定嗎？** 固定時間、固定 RNG seed、隔離檔案系統、凍結 network。
- 30 秒且時好時壞的迴圈只比沒有好一點；2 秒且穩定的迴圈才算 tight。

## Good Example

- 這個例子是好的，因為三題都有對應的具體改動。

```text
更快：從 `vp test` 全套（90s）改成 `vp test test/order-sync.test.ts -t "applies discount"`（2s）
更尖：斷言從 expect(res.ok).toBe(false) 改成 expect(res.body.message).toContain("reading 'id'")
更穩：vi.useFakeTimers() 固定 2026-10-01，移除對真實 Supabase 的呼叫
```

## Bad Example

- 這個例子是壞的，因為它停在第一版迴圈，斷言也只是「有錯」。

```text
跑 pnpm test，整套大概 90 秒，有紅就代表 bug 還在。
```

# Rule 3 - 非決定性 bug 的目標是提高重現率，不是乾淨重現

- Level: `MUST`
- 時好時壞的 bug，不追求一次就乾淨重現，而是把**重現率**拉高：把觸發點迴圈跑 100 次、平行跑、加壓力、縮窄時序窗、插入 sleep。
- 50% 的 flake 可以除錯，1% 不行；持續拉高到可以除錯為止，並把拉到的重現率記下來，後面每次重跑都對照它。

## Good Example

- 這個例子是好的，因為它把 1/10 的 CI flake 拉成可量測的高重現率。

```text
for i in $(seq 100); do pnpm exec vp test test/order-sync.test.ts --silent || echo FAIL; done | grep -c FAIL  → 3/100
加 --pool=threads --maxWorkers=8，並在 syncOrder 的 await 之間插 setTimeout(0) → 61/100。以此為基準。
```

## Bad Example

- 這個例子是壞的，因為它跑一次綠就判定沒問題。

```text
本機跑了一次是綠的，應該是 CI 環境的問題，先不管。
```

# Rule 4 - 真的建不出迴圈時 MUST 停下，列出試過的並要三樣東西之一

- Level: `MUST`
- 明說建不出來，列出試過哪些方式與各自卡在哪裡。
- 向使用者要下列其中之一：(a) 能重現的環境的存取權；(b) 遮蔽過的擷取 artifact（HAR、log dump、core dump、帶時間戳的螢幕錄影）；(c) 允許加入暫時性的 production instrumentation。
- **NEVER** 在沒有迴圈的情況下進 Phase 2。

## Good Example

- 這個例子是好的，因為它列出嘗試與卡點，再要具體的東西。

```text
建不出迴圈：
- curl 本機 dev server：200，無法重現（本機沒有 production 的 RLS policy）
- Playwright 對 staging：staging 無此筆資料
請提供其一：(a) staging 匯入一筆同型資料的權限 (b) production 該次請求的 log（遮蔽 token）(c) 允許在 orders handler 加一行 [DEBUG-7c1e] log 部署一天
```

## Bad Example

- 這個例子是壞的，因為建不出迴圈就直接讀 code 猜。

```text
本機重現不了，不過看 code 應該是 RLS 的問題，我先改 policy 試試。
```

# Rule 5 - Phase 1 完成條件：一條已實跑過、tight 且 red-capable 的命令

- Level: `MUST`
- Phase 1 只有在能指名**一條命令**（腳本路徑、測試呼叫、curl），且**已經至少實跑過一次**（貼出遮蔽後的 invocation 與輸出）時才算完成。該命令必須同時滿足四格：
  - [ ] **Red-capable**：它走到真正的 bug code path，並斷言**使用者描述的那個症狀**，所以會在這個 bug 上變紅、修好後轉綠。「跑得完沒報錯」不算，它必須抓得到這個特定的 bug。
  - [ ] **Deterministic**：每次跑判決相同（時好時壞的 bug：依 Rule 3 固定且夠高的重現率）。
  - [ ] **Fast**：秒級，不是分鐘級。
  - [ ] **Agent-runnable**：agent 可以無人看管地跑；需要人時只能經 `templates/hitl-loop.sh`，由使用者執行、agent 解析輸出。
- 發現自己在這條命令存在之前就在讀 code 建理論時，**停下**：直接跳到假設正是本 skill 要防的失敗。沒有 red-capable 命令，就沒有 Phase 2。

## Good Example

- 這個例子是好的，因為它指名一條命令、貼出實跑輸出，四格逐一對應。

```text
命令：pnpm exec vp test test/orders.discount.test.ts
輸出：FAIL  applies discount code > TypeError: Cannot read properties of undefined (reading 'id')  (1.8s)
- Red-capable：打 server/api/orders.post.ts，斷言訊息含 reading 'id'，與使用者回報一致
- Deterministic：連跑 5 次 5 次紅
- Fast：1.8s
- Agent-runnable：無需登入，fixture 在 test/fixtures
```

## Bad Example

- 這個例子是壞的，因為命令沒跑過、斷言也不是使用者的症狀，就開始談原因。

```text
迴圈可以用 pnpm test，應該會紅。看了 orders.post.ts 之後我認為是 discount 為 null 時沒有防呆，接下來驗證這個假設。
```
