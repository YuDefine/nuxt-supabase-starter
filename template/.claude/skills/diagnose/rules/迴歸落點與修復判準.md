
# Rule 1 - 迴歸測試只寫在正確的 seam；沒有正確 seam 本身就是發現

- Level: `MUST`
- 迴歸測試**在修正之前**寫，但只寫在**正確的 seam** 上。
- 正確的 seam：測試在那裡重演的是**真正的 bug 型態**，跟它在呼叫端發生時一樣。
- 只有太淺的 seam 時（bug 需要多個呼叫端，測試卻只有單一呼叫端；unit test 重演不了觸發 bug 的那條呼叫鏈），在那裡寫的迴歸測試只會給出假信心，不要寫。
- **沒有正確的 seam，這件事本身就是發現**：記下來，說明是程式架構讓這個 bug 鎖不住，並在 Phase 6 回報裡明列，交給後續處理。
- 落點類型（scenario、integration、unit）不由本 skill 自判：宣告 aixbdd 的 consumer 照 work-route skill `rules/需求分流判準.md` Rule 2 的 K2–K4（bug 回報三列），以及它指向的 `clade-spec-workflow` skill `rules/legacy-tests.md`（受測單元沒有 I/O 才落 unit test；帶 `clade-legacy-test` marker 的舊測試照該檔吸收）。未宣告 aixbdd 的 repo 照該 repo 既有的測試慣例。

## Good Example

- 這個例子是好的，因為它判斷 seam 是否重演真實型態，並在沒有 seam 時把它當發現回報。

```text
bug 只在兩個 webhook 同時更新同一張訂單時出現。
syncOrder() 的 unit test 只有單一呼叫端，重演不了競態 → 不是正確 seam。
integration 層沒有能並發觸發兩個 webhook 的 harness → 沒有正確 seam。
發現：order 更新沒有經過單一入口，競態無法在測試中鎖住；列入回報。
```

## Bad Example

- 這個例子是壞的，因為它在太淺的 seam 寫了一個綠燈測試就宣稱鎖住迴歸。

```text
在 syncOrder() 加一個 unit test，餵一次更新，斷言結果正確 → 綠。迴歸已鎖住。
```

# Rule 2 - 有正確 seam 時依五步修復，強制製造的紅燈先 diff pristine

- Level: `MUST`
- 有正確 seam 時，依序：
  1. 把 Phase 2 縮小過的最小重現，寫成該 seam 上的失敗測試。
  2. 看它紅。如果紅燈是你**修改 code 或 fixture 強制製造的**，先對未改動的乾淨副本做 `diff`（例：`git diff --stat`、`diff fixture.json fixture.pristine.json`），證明那個修改真的落地了，才相信這個紅燈。
  3. 套用修正。
  4. 看它綠。
  5. 對**未縮小的原始情境**重跑 Phase 1 的迴圈。
- 跳過第 2 步的 diff，可能是修改沒寫進檔、寫錯檔或被快取蓋掉，紅燈其實來自別處，後面的綠燈也就不能證明修好。

## Good Example

- 這個例子是好的，因為強制製造的紅燈先用 diff 證明修改落地，最後回到原始情境重跑。

```text
1. 把最小重現寫成 test/orders.discount.test.ts > "unknown discount code"
2. 共用的 test/fixtures/discount.json 帶有效折扣碼，紅不起來 → 複製成本測試專用的 test/fixtures/discount-unknown.json 並把 code 改成 NOPE（共用檔不動）→ diff test/fixtures/discount.json test/fixtures/discount-unknown.json 只差該行，確認落地 → 紅
3. 套用修正：orders.post.ts 對查無折扣碼回 400
4. 綠
5. 重跑 Phase 1：curl -X POST /api/orders -d @fixture/discount-order.json → 201
```

## Bad Example

- 這個例子是壞的，因為沒確認強制修改是否落地，也沒回到原始情境。

```text
改了 fixture 讓它變紅，跑測試是紅的；修好之後跑這個測試是綠的，完成。
```

# Rule 3 - 宣告完成前收尾清單五格 MUST 全部有證據

- Level: `MUST`
- 宣告完成前逐項勾選，每項附上證據（命令與輸出、檔案路徑、grep 結果）：
  - [ ] 原始重現不再重現（重跑 Phase 1 迴圈）。
  - [ ] 迴歸測試通過（或已記錄沒有正確 seam）。
  - [ ] 所有 `[DEBUG-...]` 觀測已移除（`grep` 該前綴為 0 筆）。
  - [ ] 一次性原型已刪除（或移到明確標示的 debug 位置）。
  - [ ] 成立的那個假設寫進 commit／PR 訊息，讓下一個除錯的人學到。

## Good Example

- 這個例子是好的，因為每格都有可檢查的證據。

```text
- 原始重現：curl -X POST /api/orders -d @fixture/discount-order.json → 201
- 迴歸：vp test test/orders.discount.test.ts → 3 passed
- grep -rn 'DEBUG-a4f2' . → 0
- scratch/repro-discount.ts 已刪除
- commit body：「根因：查無折扣碼時 .single() 丟錯被吞成 undefined（假設 1 成立）」
```

## Bad Example

- 這個例子是壞的，因為它只說修好了，清單沒有任何證據。

```text
已修好，測試都過了，debug log 應該都清掉了。
```
