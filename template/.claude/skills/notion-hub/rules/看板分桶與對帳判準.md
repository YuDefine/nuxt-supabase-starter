# Rule 1 - 預設只撈本專案的票，依 `stageOf` 逐張分桶

- Level: `MUST`
- board 是 hub 共用：filter `所屬專案` = `project.rowId`；使用者明說才看全 hub。**NEVER** 不加 filter 就把別專案的票算進來。
- 看板意圖**整個不改任何欄位**。
- 分桶：

| 桶 | predicate | 該做什麼 |
| --- | --- | --- |
| 🆕 新進未處理 | backlog 且 `Work ID` 空 | `優先級` P0 或 bug 類型的做輕量初判（root cause 方向一行、疑似檔、`estimate-hours`），不改欄位 |
| 🚧 進行中 | 進行中 | **每張** MUST 讀 `Work ID`（`<consumerId>/<workId>`），照 Rule 2 標 `⚑` |
| ⏳ 待客戶驗收 | 驗收中 | 列出 |
| ❓ 等拍板 | needs-customer／needs-engineer | 列出 |
| ⚠️ stale | 進行中／驗收中且 `提報日期` 距今 > 14 天 | 列出 |
| ✅ 已收斂 | 完成／封存 | 只報數量 |

- 報告模式另撈 `交付項目`（filter `專案`）列 `逾期`；hub 沒有交付項目（resolve 的 `hub.delivery` 為 null）時，改列 board 上承諾日期欄（`hub.fields.board.dueDate`；fc 是 `預估完成日`）已過、狀態未完成的票。
- 有 `⚑` → 回報結尾的首要建議是對應意圖（認領、對帳驗收或補跑 release）。

## Good Example

- 這個例子是好的，因為只撈本專案、逐桶列出並把 `⚑` 轉成下一步建議。

```text
fc／ERP：🆕 2（#85 P0 bug：疑似 server/api/orders.get.ts 分頁）🚧 3（1 張 ⚑ 疑似已修好未發版）⏳ 1 ✅ 14
→ 首要建議：#77 補跑 release
```

## Bad Example

- 這個例子是壞的，因為沒有 filter，還順手改了欄位。

```text
撈全 board 42 張 → 把 stale 的 3 張改成封存
```

# Rule 2 - 進行中的票 MUST 讀 `Work ID` 對帳，沒有 `Work ID` 才用 git 模糊對帳

- Level: `MUST`
- `Work ID` 前綴不是本 repo → `⚑ 屬別 repo`。
- 前綴是本 repo → `notion-sync.ts status --work <id>`；spine 已 done／accepted 但票仍進行中 → `⚑ 疑似已修好未發版`。
- `Work ID` 空 → git 模糊對帳（`references/ntn-cookbook.md` § 模糊對帳）：拿得到 tag 且在 main → 補跑 `release` 的候選（版本＝該 tag；代表 `/commit` Step 6b 當時漏跑）；只在 `session/*` branch → worktree-only，維持 in-progress；拿不到 tag → 維持 in-progress。
- 模糊命中 ≠ 真解：回填前 **MUST** 逐張給使用者看證據（commit、tag、`git show --stat`）。
- 版本欄（`hub.fields.board.fixVersion`）填 git tag（`vX.Y.Z`），由 `notion-sync.ts release --tag` 寫；`git describe --tags --abbrev=0` 只在 `/commit` 打完 tag 之後才是本次版本。

## Good Example

- 這個例子是好的，因為模糊命中後先給證據再回填。

```text
#77 無 Work ID；git log --grep 出貨單 → 3f2a1c0，git tag --contains → v1.41.2（在 main）
→ ⚑ 疑似已修好未發版；證據給使用者確認後才 release --tag v1.41.2
```

## Bad Example

- 這個例子是壞的，因為 grep 命中就直接當真解回填。

```text
git log --grep 出貨單 命中 → notion-sync.ts release --tag v1.41.2（未給使用者看）
```
