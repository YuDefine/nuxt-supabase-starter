# Rule 1 - 讀票與定位 root cause 後才三向分流

- Level: `MUST`
- 先讀票（raw＋客戶 comment）、以 codebase-memory 定位 root cause 與修法草案，再依下表分流：

| 判定 | predicate | 處置 |
| --- | --- | --- |
| 可直接做 | 需求清楚、修法草案成立 | 使用者同意後 `flow open <slug> --origin notion:<page-id>`，緊接 `notion-sync.ts open --work <id> --ticket <page-id> --title "<客戶看得懂的一句話>"`（票 → 進行中＋`Work ID`；建交付項目列——客戶提的 bug 與功能都建，D3），然後交給 work-route |
| 要客戶先拍板 | 有只有非技術決策者能拍板、會決定 schema／API／UI 範圍的問題 | 走問客戶（決策題 ticket） |
| 前提不成立／重複／已修 | 讀票或對帳後判定 | 回報使用者，由客戶側處理；封存類 **NEVER** 自動碰 |

## Good Example

- 這個例子是好的，因為先評估再開工，`open` 帶了 `--title`。

```text
#85「出貨單展開很慢」→ root cause：useOrderItems 逐列查詢 → 可直接做
→ flow open order-expand-n1 --origin notion:<page-id> → notion-sync.ts open --work <id> --ticket <page-id> --title "出貨單展開明細時載入太慢" → work-route
```

## Bad Example

- 這個例子是壞的，因為沒評估就開工，需求其實要客戶拍板。

```text
#85 → 直接 flow open，猜客戶要的是分頁
```

# Rule 2 - coordinator 派來的票：派出即同意，先評估再分流，需求不清 NEVER 跑 `notion-sync open`

- Level: `MUST`
- brief 帶 ticket page id（coordinator skill 巡檢）時，派出就是使用者的同意，**NEVER** 再問要不要接。
- worktree 已帶 `--origin notion:<page-id>` 開好，跳過 `flow open`。順序固定：**先**照 Rule 1 評估，**再**分流：
  - 可直接做 → `notion-sync.ts open --work <id> --ticket <page-id> --title "<客戶看得懂的一句話>"`，**MUST** 帶 `--title`（省略時交付項目 Item 會是 worktree slug 如 `notion-fc-85`，客戶看得到），一路做到 `/commit` release（票 → 驗收中）。
  - 需求不清 → **不跑** `notion-sync open`（它會寫 `Work ID`、把票推到進行中）：`flow ask` 把題目送進使用者的 `\my` 佇列，同時照問客戶的做法在票上留補充說明並設 needs-customer——使用者與客戶兩邊都知道卡在哪，**NEVER** 猜需求先做。

## Good Example

- 這個例子是好的，因為需求不清時兩邊都通知，且沒有推進票。

```text
coordinator 派 #91（worktree 已 --origin notion:<id>）→ 評估：不知道要顯示含稅或未稅
→ flow ask「#91 金額要含稅還是未稅？」＋票上留言並設需使用者確認；不跑 notion-sync open
```

## Bad Example

- 這個例子是壞的，因為省略 `--title`，客戶在時程頁看到 worktree slug。

```text
notion-sync.ts open --work W-2026-10-04-notion-fc-91 --ticket <id>
```

# Rule 3 - 非 `file` 建票的工作開工前 MUST 跑一次 `notion-sync.ts open`

- Level: `MUST`
- `follow` 依設計永不建交付項目列；`flow open` 或認領客戶票開的工作漏跑 `open`，這個 work item 不會出現在客戶時程頁（掛載點全表見 [[notion-work-coupling]]）。
- `file` 建的票已在 script 內完成，不需再跑。

## Good Example

- 這個例子是好的，因為認領後立刻補上交付項目列。

```text
flow open … --origin notion:<id> → notion-sync.ts open --work <id> --ticket <id> --title "…"
```

## Bad Example

- 這個例子是壞的，因為以為 follow 會自動建列。

```text
flow open … --origin notion:<id> → 直接開工（客戶時程頁看不到這件）
```
