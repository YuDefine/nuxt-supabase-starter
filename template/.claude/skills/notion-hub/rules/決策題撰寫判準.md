# Rule 1 - 只有非技術決策者能拍板、且會決定 schema／API／UI 範圍的問題才開決策題 ticket

- Level: `MUST`
- 寫 code 前有 ≥1 個這種問題時開決策題 ticket；純技術決策自己決；1–2 句的小確認在 chat 問使用者。
- 既有客戶票只需要問一句 → 不開新票：在該票留 comment（口語、給選項情境），並把 `狀態` 設成 `hub.ticketStatus['needs-customer']`（`references/ntn-cookbook.md` § 寫入）。
- 動筆前一次萃取齊：需求標題（口語化，使用者確認）、N 個拍板題（決策維度／選項／影響）、code pointer（`search_graph`／`trace_path`）。不確定的一次問齊，**NEVER** 邊寫邊問。
- 已有 work item 時建票後由 `notion-sync.ts open --work <id> --ticket <page>` 綁 `Work ID`；沒有就等客戶回覆後走認領。

## Good Example

- 這個例子是好的，因為三題都會改變資料表與畫面範圍，只有客戶答得了。

```text
出貨單展開欄位：要顯示哪些欄位、能不能在展開處直接改數量、歷史紀錄保留多久 → 開決策題 ticket（3 題）
```

## Bad Example

- 這個例子是壞的，因為索引要怎麼建是技術決策，不該問客戶。

```text
決策題：「出貨單查詢要用複合索引還是 materialized view？」
```

# Rule 2 - 客戶問題用客戶的話、每題一個維度並給情境化的 `to_do` 選項

- Level: `MUST`
- 標題＝客戶用自己的話說的需求。
- 題數 3–6；每題只有一個決策維度；每題口語化並給範例。
- 每題給選項，每個選項給情境；選項 **MUST** 是 `to_do` 勾選框（不是 `bulleted_list_item`，否則 checkbox 渲染不出來）。
- 選項前先用 `- **{詞}**：{日常語言解釋＋範例}` 解釋會出現的詞。
- **不用任何技術術語**：RPC／schema／DTO／API／table／foreign key／migration 全部禁。
- **NEVER** 讓客戶選技術路徑（「A. CREATE TABLE / B. ALTER TABLE」）；**NEVER** 多題擠成一段散文。

## Good Example

- 這個例子是好的，因為選項是情境、可勾選，且沒有術語。

```md
## 1. 展開出貨單時，想看到哪些資訊？
- **展開**：在出貨單列表點一下該筆，下方直接出現明細，不用另開頁面
- [ ] A. 只看品名與數量（畫面最清爽）
- [ ] B. 品名、數量、單價、小計（方便當場核對金額）
```

## Bad Example

- 這個例子是壞的，因為是技術選項、又是一般條列。

```md
## 1. 明細資料來源
- A. join order_items table
- B. 新增 order_item_view
```

# Rule 3 - 4 段版面順序與標題層級不可改，接手 prompt 必含 6 段

- Level: `MUST`
- 版面固定 4 段：`# 已提交待驗收參考` → `# 開發前想跟您確認 N 件事`（`## N.` 編號題）→ `# 🤖 Claude 接手 Prompt（給開發者用，客戶可忽略）` → `## 開發者備忘`（含 HANDOFF cross-link、N 題答案影響的範圍）。骨架見 `templates/客戶決策題ticket.md`。

| 段落 | 客戶讀法 | 開發者讀法 |
| --- | --- | --- |
| `# 已提交待驗收參考` | 「之前做完的長這樣」 | 驗收時補截圖的固定 anchor |
| `# 開發前想跟您確認 N 件事` | 「我只要打勾就好」 | 拍板紀錄 |
| `# 🤖 Claude 接手 Prompt` | 「不關我事」 | 唯一接手入口 |
| `## 開發者備忘` | 通常不看 | HANDOFF cross-link、決策影響範圍 |

- 接手 prompt 6 段順序固定、標題用全形【】：開頭一句（repo／模組、需求、HANDOFF entry）→【第一步 — 先檢查客戶有沒有回 Notion】→【N 題對應的架構決策】→【分流】→【{workflow 階段}必填區塊】→【既有 code pointer，不必再 grep】，結尾【plan 完】交給 work-route。
- prompt 規約：self-contained（新 session 只看它就能接手）；code pointer 用 repo-relative 完整路徑；每題對應的架構決策一定寫；【第一步】的讀取指令 MUST 帶 `has_more` 翻頁（漏頁會把客戶已勾誤判成沒勾）；【分流】MUST 含「客戶沒回 → 別重發提醒，回報『Notion 還沒打勾』並結束」，否則新 session 會自作主張 ping 客戶。
- 接手 prompt 的 `notion-sync` 步驟只寫到綁 work item 為止——之後的生命週期由 flow 事件自動推進。
- 建頁拿到 page id 後 **MUST** 回填進【第一步】。

## Good Example

- 這個例子是好的，因為分流有「沒回不重發」，且第一步帶翻頁。

```text
【分流】
- 客戶都回了 → flow open … → notion-sync.ts open --work <id> --ticket <page-id> → 交給 work-route
- 客戶還沒回 → 別重發提醒，直接告訴我「Notion 還沒打勾」並結束
```

## Bad Example

- 這個例子是壞的，因為沒寫沒回時怎麼辦，接手者會去催客戶。

```text
【分流】客戶回了就開工
```

# Rule 4 - 客戶沒回就回報「還沒回」並結束，NEVER 建議 N 天後 ping 客戶

- Level: `MUST`
- 建票完成的回報：ticket URL、N 題、HANDOFF entry 位置、接手方式。
- 客戶沒回 → 回報「還沒回」並結束；**NEVER** 主動建議「N 天後 ping 客戶」或排程提醒。

## Good Example

- 這個例子是好的，因為只回報現況。

```text
#93 Notion 還沒打勾（3 題皆未勾）。
```

## Bad Example

- 這個例子是壞的，因為用模板天數填出一個沒有訊號的 follow-up。

```text
客戶還沒回，建議 3 天後再 ping 一次。
```
