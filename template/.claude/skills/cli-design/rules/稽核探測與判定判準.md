# Rule 1 - 探測只執行不會改變任何狀態的呼叫

- Level: `MUST`
- `probe_cli.py` 預設只跑 `--help`（另以 `NO_COLOR=1` 重跑一次）。跑之前先從原始碼確認 `--help` 會在任何 handler 執行前被攔截（commander、yargs、cobra、clap、argparse、click 內建攔截；手寫解析器要看到 handler 前的判斷）。看不出來就不跑這支腳本，判準項全部改從原始碼與文件取證。
- 其餘 root 探測要逐項加進 `--allow`，加之前從原始碼確認它落到的分支只會印 help 或錯誤後結束：
  - `short_help`（`-h`）、`help_subcommand`（`help`）、`version`（`--version`）：解析器不認得時會被當成什麼。
  - `unknown_command`、`unknown_flag`：不帶子命令時的預設動作是什麼、看不懂的位置參數與旗標會不會被略過（例如 `strict: false` 的 `parseArgs`）。

  探測用的是本機真實的憑證與環境：會略過看不懂旗標、且預設動作會同步、部署或寫入的 CLI，`--version` 與未知旗標都會觸發那個動作。確認不了的項目不加進 `--allow`，對應判準改從原始碼取證；輸出的 `probes_not_run` 會列出沒跑的項目。
- 測 C5 的「最接近建議」用 `--typo <名稱>`：拼錯的名稱和 `unknown_command` 走同一條分支，所以帶之前要先做上一項 `unknown_command` 的原始碼確認，確認不了就不帶。自己挑一個唯讀子命令（例如 `status`、`auth`）的近似拼法，且不能是任何真實子命令的前綴（有些解析器接受縮寫）。對象會自動更正並直接執行時（例如 git 設了 `help.autocorrect`，或原始碼看得出模糊匹配後就執行），不帶 `--typo`。
- 遞迴探測子命令（`--depth` ≥ 1）只在已確認 `--help` 會被攔截時才開。子命令清單優先用 `--commands a,b,c` 給從原始碼讀到的清單；只有清單太長時才依賴腳本從 help 文字解析，並先看一次 `root_subcommands` 有沒有混進不是命令的字。
- 唯讀命令（`list`、`get`）只在兩個條件同時成立時才實跑：
  - 使用者明確同意。
  - 已確認目標環境不是 production，或使用者已授權對 production 唯讀。
- `--dry-run` 只在文件或原始碼證實該命令的 dry-run 不會送出請求時才實跑。
- NEVER 實跑會建立、修改、刪除、部署或寄送的命令。即使帶了 `--dry-run`，只要無法證實該命令支援 dry-run，就不跑。
- 手動補跑的呼叫照腳本同樣的條件：暫存 cwd、stdin 接 `/dev/null`、設逾時。

## Good Example

- 這個例子是好的，因為它先從原始碼確認預設動作與 help 都會短路，才開始探測與遞迴，而且沒有實跑任何會寫入的命令。

````md
- 讀 `vendor/scripts/flow/flow.ts`：`help` 宣告了 `short: 'h'`，`if (args.version === true)` 與 `if (args.help || positionals.length === 0)` 都在 dispatch 前印出後結束 → `--help` 會被攔截、可遞迴，`short_help`、`version` 安全；不帶命令的未知旗標由 `if (!args.help && positionals.length === 0)` 那段 `fail` 擋下 → `unknown_flag` 安全
- 看不懂的命令走 ``fail(`unknown command …`)``，`help` 是已知命令、只印 USAGE → `unknown_command`、`help_subcommand` 安全
- `uv run …/probe_cli.py --allow short_help,help_subcommand,version,unknown_command,unknown_flag --typo sattus --depth 1 -- node vendor/scripts/flow/flow.ts`
- `flow open`、`flow close` 只讀 help，不實跑
````

## Bad Example

- 這個例子是壞的，因為它為了測退出碼直接實跑刪除命令，沒確認預設動作就跑未知旗標，又在沒確認 help 會短路的情況下開遞迴。

````md
- `mycli db delete test-db` 看看沒帶 --force 會回什麼
- `syncer` 不帶引數時會同步，沒查就帶 `--allow unknown_flag,version`（未知旗標被略過 → 真的同步了一次）
- 直接 `--depth 2` 掃全部子命令
````

# Rule 2 - 判定只有四種值，每格都要對得到證據

- Level: `MUST`
- 判定值：
  - `PASS`：證據顯示完全符合。
  - `PARTIAL`：只有部分命令符合，或有條件符合；要列出不符合的命令。
  - `FAIL`：證據顯示不符合。
  - `N/A`：適用條件不成立；理由要對應判準檔 Rule 1 的規模、使用者或「僅當…」條件。
- 每格判定都要附至少一筆證據，形式三擇一：
  - probe JSON 的欄位路徑與值，例如 `probes.unknown_command.exit_code = 1`。
  - 原始碼位置 `file:line`。
  - 實際執行的命令與輸出片段。
- 拿不到證據的項目不判定，列進報告的「未驗項」並寫明原因（例如「需要憑證才能觀察」「無原始碼」）。NEVER 用推測補成 `PASS`。
- 零命中不是證據：「help 沒提到 `--json`」只證明 help 沒寫，要再查原始碼或實跑一次唯讀命令，才能判 `FAIL`。
- `probe_cli.py` 的 `leaf_names`、`flags_seen` 是從 help 文字擷取的原始清單；A2、A3 的同義詞判定由判準檔決定，判之前回頭讀對應的 help 原文確認。

## Good Example

- 這個例子是好的，因為每格判定都能回溯到一筆具體證據，推不出來的項目誠實列為未驗。

````md
| C5 | FAIL | `probes.unknown_command`：exit_code=1、stderr 無候選建議 |
| E3 | 未驗 | create 要寫入遠端，未獲授權實跑；原始碼 `src/db.ts:88` 未處理 409 |
````

## Bad Example

- 這個例子是壞的，因為它用印象判定，也把沒看到當成看過。

````md
| C5 | PASS | 應該有做 |
| B2 | FAIL | help 沒寫 --json |
````

# Rule 3 - 嚴重度沿用判準檔的預設值，調整要寫理由

- Level: `MUST`
- 每個 `FAIL`／`PARTIAL` 的嚴重度先沿用判準檔該 ID 標注的 `P0`／`P1`／`P2`。
- 只有在對象的實際使用情境改變了影響時，才可以上調或下調，並在報告寫明理由。例如使用者已明說只給人互動用，D2 才能從 P0 下調。
- 報告的發現依 P0 → P1 → P2 排序；同級內依受影響的命令數由多到少排。

## Good Example

- 這個例子是好的，因為嚴重度調整附上了可核對的理由。

````md
- D2 FAIL，P0 → P1：使用者確認只在本機互動使用，CI 不呼叫這支 CLI
````

## Bad Example

- 這個例子是壞的，因為它沒有理由就把 P0 下調成 P2。

````md
- C6 FAIL（P2，影響不大）
````

# Rule 4 - 修法要寫到能直接動工的粒度

- Level: `SHOULD`
- 每個 `FAIL`／`PARTIAL` 的修法要寫到命令、旗標或檔案層級，並附上改完後的行為範例。
- 涉及改名或移除的修法，走判準檔 H4 的棄用路徑，不建議直接做 breaking change。
- 同一個根因造成的多項 FAIL（例如解析器不支援 `--help`，同時導致 F1、F2、C5 失敗）合併成一筆修法，並列出它解掉的全部 ID。

## Good Example

- 這個例子是好的，因為修法指到檔案與行為，也標出一次修好的多個 ID。

````md
- 修法（解 F1、C5）：`src/cli.ts` 改用 `parseArgs({ strict: true })` 並在 dispatch 前攔 `--help`；
  未知命令回 exit 2 並以 Levenshtein 列出最接近的兩個子命令。
  改後：`mycli db gt` → stderr `Did you mean: get?`、exit 2
````

## Bad Example

- 這個例子是壞的，因為修法只是一句口號，接手的人不知道要改哪裡。

````md
- 修法：改善錯誤處理
````

# Rule 5 - 結果全綠或第一次探測新型 CLI 時，先用已知樣本校準

- Level: `SHOULD`
- 探測結果出現「全部 `PASS`」，或對象使用沒見過的解析器時，先對一支已知行為的 CLI（例如 `gh`）跑同一個 probe，確認 probe 對已知樣本會命中（例如 `gh atuh` 會被測到 exit 非 0 且附建議）。
- 校準沒命中，表示 probe 或判讀有問題，要先修正，再回頭判定原對象。

## Good Example

- 這個例子是好的，因為它先用已知樣本證明探測有效，才採信全綠結果。

````md
- 對象全 PASS → 對 `gh` 跑 `probe_cli.py --allow unknown_command --typo atuh -- gh`：`typo_command` exit_code=1、suggestion_detected=true → probe 有效
````

## Bad Example

- 這個例子是壞的，因為全綠時沒有校準，探測可能根本沒有在測。

````md
- 全部 PASS，結案。
````
