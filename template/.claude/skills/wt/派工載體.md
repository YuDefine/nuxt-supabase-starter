# 派工載體

`wt` Phase 2 第 3 步依選定載體讀對應一節。載體、model 與 effort 一律照 Phase 2 第 1 步在 routing table（`rules/core/agent-routing.routing-table.md`）選定的那一列；本檔只寫各載體的指令、參數與等待方式，**不**另列 model／effort 對照表。判不進任何一列的任務由主線自己在該樹內做，NEVER 自挑一個 model 派出去。

不論哪個載體，派工前都要：

- 已依 `templates/worker-brief.md` 寫好 worker brief，第一行是 `routing-row: <列名>`。
- 父 session 的 cwd 不動；worker 的工作目錄只透過 brief 的「工作目錄」與載體的 cwd 參數指定。
- 派工的同一則訊息內排好等待機制（見各節與 § 等待機制共通），NEVER 先結束回合再補。

## in-process subagent

適用：routing table 該列的載體寫 in-process（例：Sonnet 四列的 `sonnet-implementer`、decision／planning 列的 `Plan`），且本 turn 收得回成果。以下 `Agent`、`TaskStop`、`ScheduleWakeup` 是 Claude Code 的原生名稱；其他 runtime 換成各自的等價操作。

`Agent` 參數：

| 參數 | 值 |
| --- | --- |
| `name` | `wt-<slug>`，之後可 `SendMessage({to: name})` 續接 |
| `subagent_type` | routing table 該列指名的 in-process 載體；Sonnet 四列只准 `sonnet-implementer` |
| `model` | 照該列；`sonnet-implementer` 的 frontmatter 已釘 model 與 effort，省略 `model`。該列要求顯式 model 時照寫，NEVER 省略成繼承主線 |
| `isolation` | 省略。worktree 本身就是隔離；Agent tool 內建的 worktree isolation 是給父 repo 用的 |
| `prompt` | 整份 worker brief 原文 |

等待：

- 同一則訊息記下 owner（agent name 或 id）與 deadline（取值依 `[[agent-routing.keepalive-wake]]` § deadline 怎麼取，NEVER 憑感覺填「+4h」），並排一條 inert keepalive。這條路徑沒有可供 `TaskOutput` 查詢的 harness task id，**逐字**填 `task=none`：

  ```text
  ASYNC_KEEPALIVE_CONTROL task=none owner=<owner> deadline=<ISO>. Status-only. Never query TaskOutput or infer task status; wait for the native completion notification instead. Before deadline, if no notification has arrived, re-arm this exact message. At or after deadline, stop this wakeup and enqueue ASYNC_DEADLINE_INTERVENTION task=none owner=<owner> cause=deadline. Never replay the dispatched instruction.
  ```

- deadline 到達：依 owner 的原生控制面 `TaskStop(<owner>)`，等 terminal notification；確認 terminal 前保留 ownership，NEVER 收割、重派或釋放相關 lock。
- 收到完成通知：`ScheduleWakeup({stop: true})`，進 Phase 3。
- Agent tool 回傳只說明成果怎麼送達，不代表主線在等待期間可以閒置。

## Herdr child

適用：routing table 該列的載體寫 Herdr（Claude Code 原生 `cc`／`cc2` child），或工作是 handoff 級、要跑很久、本 turn 收不回。transport 規約在 `rules/core/session-tasks.operations.md` § Herdr session transport；完整旗標、錯誤碼與跨機放置在 `vendor/snippets/herdr-session-handoff/README.md`。第一次用本載體或遇到不熟的錯誤碼時，先讀該 README。

worker brief 寫成檔案（例：`/tmp/wt-<slug>-brief.md`），再以 coordinated create-only dispatch 派出：

```bash
node ~/offline/clade/vendor/scripts/herdr-session-handoff.ts \
  --cwd <worktree-absolute-path> \
  --label '<consumer>/<slug>' \
  --prompt-file /tmp/wt-<slug>-brief.md \
  --launcher <cc|cc2|cc3> \
  --model <該列 model slug> --effort <該列 effort> \
  --route routing-table --tier-basis table-row --table-row <該列列名> \
  --coordinate
```

| 參數 | 說明 |
| --- | --- |
| `--cwd` | worktree 絕對路徑。已註冊的 git worktree 沿用其主 repo 的 workspace trust，不必另帶 `--trusted-workspace` |
| `--label` | 必填，命名這個任務（`<consumer>/<slug>`，48 字元內，不以 `-` 或空白開頭）；NEVER 只寫 repo 名 |
| `--prompt-file` | worker brief 檔案的絕對路徑 |
| `--launcher` | 省略時繼承當前 live 的 `cc`／`cc2` 身分；當前 runtime 不是 `cc`／`cc2`（例：Codex 主線）時顯式帶 `cc`（池入口，admission 依額度挑帳號）。`pi` 不能 create，Pi 列走 § Pi dispatcher |
| `--model`／`--effort` | 照該列逐字。Claude child 的 effort 只到 `high`（Opus 只到 `medium`），`max` 在建 pane 前就被拒；NEVER 把 model 寫進 brief 讓 child 自選 |
| `--route`／`--tier-basis`／`--table-row` | 三者皆必填且無預設。`table-row` 只接 Claude-native 列，helper 會把該列要求的 model／effort 與 `--model`／`--effort` 逐字比對，不符即拒 |
| `--coordinate` | 本 session 持有這筆 dispatch 並在前景收割。本 session 自己是被派出的 child（`CLADE_DISPATCH_ID` 非空）時再派 worker 會被拒 `nested_dispatch_refused`，改由主線派 |

等待與收割：

- `--coordinate` 在前景跑一段有界的等待；child 在時限內回報就直接收割並回收 pane。
- 回傳 `coordination_pending`：child 仍在跑、尚無 outcome。保留 pane 與 durable record，立即以同一 session 續接：

  ```bash
  node ~/offline/clade/vendor/scripts/herdr-session-handoff.ts --coordinate-resume <dispatch_id>
  ```

- 收割依據是 correlated business outcome（`success`／`blocked`／`failed`／`unknown`），NEVER 把 pane lifecycle 的 `idle`／`done`、prompt 已送出或 `status: dispatched` 當成完成。
- 收割到 `blocked`：讀它帶的 decision，依 `rules/成果驗收判準.md` 處置。
- 收據的 `model_verification` 是 `mismatch` 時屬 `transport_error`，pane 保留作證據；是 `unverified` 時 NEVER 宣稱已核實 model。
- 派工生命週期責任（啟動提示、空白輸入框、阻塞、交接）照 `rules/core/session-tasks.operations.md` § 派工生命週期責任。

## Pi dispatcher

適用：routing table 該列的執行者是 Pi（例：`mechanical-fanout`、`read-heavy-scan`、`web-search`、`notion-ops` 等 Gemini／Grok 列，以及 `delegate-sub` 首跳）。Sonnet 四列、decision／planning 列、`dotclaude-authoring`、UI 列與 `code-review-opus` 都是 native Claude，NEVER 走本節。Pi 背景派工在 Claude Code 以 `Bash run_in_background=true` 執行，worktree 是 dispatcher 的工作目錄。

### Brief 派工（實作類 Pi 列）

worker brief 寫到 `/tmp/wt-pi-<slug>-prompt.md`；寫 code／改檔的 Pi brief MUST 已依樣板的 `{{PI_INLINE_DIRECTIVES}}` 逐字貼入 `agent-routing.pi-watch-protocol` § Plan-first 與 § Commit Authorization 兩段（Pi 不讀指標），然後：

```bash
node ~/offline/clade/vendor/scripts/pi-dispatch.ts \
  --brief /tmp/wt-pi-<slug>-prompt.md \
  --cwd <worktree-absolute-path> \
  --label wt-<slug> \
  --model <該列 model> --effort <該列 effort> \
  --route <routing-table|claude-delegate-sub> \
  --tier-basis <table-row|delegate-sub> \
  [--table-row <該列列名>]
```

### Template 派工（調查類 Pi 列）

調查任務產出結構化 JSON 證據，通常不需要 commit。依調查型態選 `vendor/snippets/pi-offload/templates/` 下的 template：

- 除錯（錯誤、bug、crash、非預期行為、timeout、leak、exception、500）：屬 `non-ui-implementation`，native Claude 載體，不走 Pi；`debug-evidence.template.md` 只當 brief 素材。
- 指令收集、驗證矩陣：
  - 派工前能完整寫出指令清單（沒有任何指令的目標依賴前一個指令的輸出）→ 主線自己跑完指令、把每份輸出導到 `/tmp/`，再派 `fanout-analyze.template.md` 並帶 `--var evidence=...`。
  - 寫不出完整清單 → `fanout-collect.template.md`。
- 長文件、跨 repo、release notes、架構掃描 → `read-heavy-scan.template.md`。

`--var` 參數：

| 變數 | 內容 |
| --- | --- |
| `task` | 任務原文＋主線補的上下文（檔案路徑；除錯時的假設清單） |
| `acceptance` | 主線寫定的驗收標準，NEVER 留給 Pi 決定 |
| `git_baseline` | `git -C <worktree-path> status --porcelain \| head -20` 的輸出 |
| `allowed_paths` | 通常唯讀；調查需要寫入（例：重現腳本）時只列具體 `/tmp/` 路徑 |

```bash
node ~/offline/clade/vendor/scripts/pi-dispatch.ts \
  --template ~/offline/clade/vendor/snippets/pi-offload/templates/<template>.template.md \
  --var "task=<task>" \
  --var "acceptance=<acceptance>" \
  --var "git_baseline=<baseline>" \
  --var "allowed_paths=<paths>" \
  --label wt-investigate-<slug> \
  --model <該列 model> --effort <該列 effort> \
  --workspace-access <readonly|mutation> \
  --route routing-table \
  --tier-basis table-row \
  --table-row <該列列名> \
  --cwd <worktree-absolute-path>
```

### 旗標交叉檢核

- **`--route` 必填**（缺了 exit 1）：記錄你依循哪條政策。照 routing table 某列派工就是 `routing-table`。NEVER 在拿不準時退回 `manual`——它是政策指標的分母，填錯會讀成假陰性，而不是缺資料。
- **`--tier-basis` 必填**（缺了 exit 1）：記錄那條政策對檔位的結論，dispatcher 會拿這一對與 `--model` 交叉檢核。照列派工時 basis 是 `table-row`；自己判斷降到 gemini 是 `five-conjunct`，只有五個條件全成立才成立，否則 dispatcher 以自相矛盾拒絕不符的 model。
- **basis 是 `table-row` 時 `--table-row <row>` 必填**（缺了 exit 1）：列名是 routing table 每列開頭〔`backticks`〕裡的 slug，dispatcher 會比對該列指名的 model 與 `--model`。NEVER 省略——少了它，`table-row` 會變成唯一沒有 model 約束的 basis，是「看起來合規卻無視該列」最便宜的寫法。講不出列名代表你沒查表，改用別的 basis，不要猜列名。
- **effort 跟著 model 走**（`pi-routing-policy.ts` 的 `TIER_EFFORT`，不按任務複雜度分級）：`grok-xai` 一律 `xhigh`，`gemini` 一律 `high`，其他值 dispatcher exit 1。
- 一次只判一個角色：同一次 dispatch 摻了收集與 gate 兩種輸出時，先拆成兩次 dispatch 再各自查表，NEVER 挑一個折衷檔位。

### 派工回報區塊

`Bash run_in_background` 回傳後立刻印出：

```text
🚀 Pi dispatched [<coding|analyze>]
  worktree: <worktree-absolute-path>
  model:    <model-slug chosen>
  effort:   <effort level chosen>
  prompt:   <brief 路徑，或 template: <template-filename>.template.md>
  bash job: <job-id>
```

### Watch Protocol

notification-only，加一條 1500s safety net：

- `Bash(run_in_background=true)` 回傳 `<task-id>` 後，立即記錄 owner／deadline（deadline 取值依 `[[agent-routing.keepalive-wake]]` § deadline 怎麼取；`--budget N` 的實際 kill 落在 `(N+5)` 分，預設 `--budget 20`）並排 1500s canonical inert control wakeup：

  ```text
  ASYNC_KEEPALIVE_CONTROL task=<task-id> owner=wt-pi:<slug> deadline=<ISO>. Status-only. Call TaskOutput(block=false) for this task. If terminal, stop this wakeup and enqueue ASYNC_LIFECYCLE_HANDOFF task=<task-id> owner=wt-pi:<slug> cause=terminal. If running before deadline, re-arm this exact message. If running at deadline, or status remains unknown after the bounded retry, stop this wakeup and enqueue ASYNC_DEADLINE_INTERVENTION task=<task-id> owner=wt-pi:<slug> cause=<deadline|unknown>. Never replay the dispatched instruction.
  ```

- `<task-notification status=completed>`：claim task id → 讀 stdout → 進 Phase 3。
- `<task-notification status=failed>`：claim task id → 讀 stderr／stdout → 回報失敗，保留 worktree。
- control wakeup 只准 adapter 的狀態查詢（Claude：`TaskOutput(block=false)`）、重排同一條 inert prompt、停止 wakeup、排 lifecycle handoff／deadline intervention；NEVER 讀 BashOutput tail 或執行原任務。
- deadline 到達且 task 仍 running：停止 control wakeup → adapter 的取消操作（Claude：`TaskStop(<task-id>)`）→ 等 terminal；terminal 前 NEVER 收割、重派或釋放 ownership。

### 結束碼與產出

| exit | 意義 | 讀哪裡 |
| --- | --- | --- |
| 0 | Pi 跑完且回報 JSON 可解析 | stdout JSON 的 `result`；調查類把重點 findings 寫進該樹 `WORKTREE-BRIEF.md` 的 `# Findings` 節，讓接續 session 不必重跑 |
| 1 | 用法或 render 錯誤（旗標錯、未解析的 `{{placeholder}}`） | 修指令，NEVER 重試 |
| 2 | 業務失敗（`result.status === 'fail'`；`read-heavy-scan` 的 `raw` 字串複驗不中也算） | 讀 `result` JSON；品質失敗的升級不在 Pi，照 routing table 改派 native 載體 |
| 3 | 機械失敗（pi 不在、spawn 錯、timeout、最後訊息無可解析 JSON） | 回報 JSON 的 `lastMessagePath`、`/tmp/pi-<label>-stdout.log`、`/tmp/pi-<label>-stderr.log` |
| 4 | 配額擋下（派工前 gate 或執行中 usage limit） | 照回報的 `next_step` 降級，MUST 帶 `--retry-of` |

## 等待機制共通

- 每一種 async 派工都在派出的**同一則訊息**排 keepalive；模板與 deadline 取值的正本在 `[[agent-routing.keepalive-wake]]` § 派出當下的模板與 deadline，主線靜默上限在 `[[agent-routing]]` § 主線靜默上限。
- 只有 background process launcher（Pi 的 `Bash run_in_background`）有可查的 harness task id，填真實 `<task-id>`；in-process subagent 逐字填 `task=none`，NEVER 虛構 id、NEVER 把原 `wt` 輸入或 brief 放進 wakeup prompt。
- keepalive 只承載控制面，完成時停止；Herdr child 以 `--coordinate`／`--coordinate-resume` 收割，不另排第二條 keepalive。
- deadline 是「超過就判定卡死」的閾值，不是期望完成時間；一律往晚的方向取。兩層派工（worker 會再自行派 Pi）時取子層可能的最大 budget 當上界，取不出就在 brief 要求 worker 回報它選的 budget，收到後改排一次。
- 收到 terminal 通知前保留 ownership；任何載體都 NEVER 把「worker 說做完了」直接當驗收，一律進 Phase 3 核對。
