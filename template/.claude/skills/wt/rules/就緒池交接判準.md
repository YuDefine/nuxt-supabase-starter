# Rule 1 - 只有驗收通過且允許落地的來源才能登記就緒

- Level: `MUST`
- 登記就緒前，主線 **MUST** 已完成：
  1. 收割 worker 的 terminal outcome。
  2. 依 `rules/成果驗收判準.md` 驗過 scope 與必要驗收。
  3. 確認寫入權已交接（worker 回報 writer-release，該樹無活寫入者、claim 或 lock）。
- 驗收通過的成果先做 scoped checkpoint（`batch checkpoint`，只保存，不跑完整 AI 審查），再用 `wt-helper batch ready` 登記：來源 HEAD、work id、證據，以及落地授權。
- 只有「已明確就緒且允許落地」的 worktree 進池。**NEVER** 從「`git status` 乾淨」「worker 說 done」「draft PR 已開」推定已驗收或已就緒。
- 命令、參數與證據格式只照 commit skill 的 `batch.md`；本檔不複寫命令。

## Good Example

- 這個例子是好的，因為三項前提都有證據才登記，並把授權一起寫進 receipt。

```md
A（auth-refresh）：terminal ✓、驗收 ✓（成果驗收判準 Rule 1 四項）、writer-release ✓
→ batch checkpoint → batch ready（HEAD 3f2a91c、work id W-2026-10-01-auth、evidence sidecar、落地授權：呼叫端已授權自動落地）
```

## Bad Example

- 這個例子是壞的，因為它用乾淨的工作樹推定已就緒。

```md
B 的 worktree `git status` 乾淨 → 應該做完了 → batch ready。
```

# Rule 2 - 收尾 gate 與 bookkeeping 在來源樹完成，skill-owned worktree 也走同一個池

- Level: `MUST`
- 驗收 gate 與 carrier bookkeeping 在**持有該工作實作的 worktree** 執行，完成後連同成果一起 checkpoint，再進就緒池。**NEVER** 在看不到實作的 main 跑驗收 gate，也 **NEVER** 在落地前刪除來源。人工檢查、spec sync、sidecar 與 evidence 義務都保留，不因走批次而省略。
- skill-owned worktree 同樣在完成點登記就緒並評估批次條件，包括：
  - 呼叫端交來的單一 ad-hoc 任務（舊稱 Form 1）——完成時**本輪**就登記已驗證的 checkpoint 並評估觸發；**NEVER** 只因為沒有 archive 事件就把已完成的樹擱著（TD-863）。
  - `/version-upgrade` 等其他 skill 自己開的 worktree。
- 已授權的自動落地由主線執行。使用者明示要保留的 worktree 不納入自動回收。
- worker 不因批次契約取得 push `main`／publish／刪除來源的權限；worker 只 push 自己的 session branch、開自己的 draft PR（見 `rules/worker契約.md`）。

## Good Example

- 這個例子是好的，因為單一 ad-hoc 任務完成後當輪就進池評估。

```md
ad-hoc 任務 fix-typo 驗收通過 → 本輪 batch checkpoint → batch ready → batch status --trigger auto --workflow pr-merge-based
```

## Bad Example

- 這個例子是壞的，因為它把完成的樹擱置等「之後一起處理」。

```md
fix-typo 做完了，沒有 archive 事件，先放著，下次有別的 change 再一起 commit。
```

# Rule 3 - 每個評估時點都跑 auto 觸發檢查，而且必須帶 `--workflow`

- Level: `MUST`
- 以下每個時點都跑 `wt-helper batch status --trigger auto --workflow <已解析的 workflow_model>`：
  - 有來源登記就緒時
  - 收割一個 worker 結果時
  - 停止開發時
  - session 接手時
- **NEVER** 省略 `--workflow` 讓 CLI 預設成 PR 制；`workflow_model` 要先從該 repo 的設定解析出來再帶入。
- 自動觸發門檻：
  - `pr-merge-based`：1 個 distinct work id（一個可獨立接受的目的對應一個 PR）。
  - `trunk-based`：4 個 distinct work id。
  - 同一任務的多棵 worktree 不重複計數。
- 未達門檻 → 繼續開發，不佔 commit lock。
- ready backlog 達 3 件時，優先交付，不再開新工作。

## Good Example

- 這個例子是好的，因為它先解析 workflow 再帶入，並依門檻決定續做或觸發。

```md
repo workflow_model = trunk-based；就緒 2 個 work id
→ `batch status --trigger auto --workflow trunk-based` → 未達 4 → 繼續開發。
```

## Bad Example

- 這個例子是壞的，因為省略 `--workflow`，trunk-based 的 repo 會被當成 PR 制、1 件就觸發。

```md
`wt-helper batch status --trigger auto`
```

# Rule 4 - 手動、依賴、清空、停止四種情況可以提前結批

- Level: `MUST`
- 除了 auto 門檻，下列觸發可提前結批：
  - **`manual`**：使用者要求 `/commit` 或 merge back。**無最低件數**。使用者說的「merge back」一律走 manual batch，不走 legacy `merge-back`。
  - **`dependency`**：下游工作必須等這批先落地。
  - **`drained`**：所有已授權的開發都已完成或受阻。
  - **`stop`**：使用者結束本輪。
- 單純的 session handoff **不是**觸發條件：保留佇列，交給接手的 session 評估。

## Good Example

- 這個例子是好的，因為它辨識出 dependency 觸發，提前結批讓下游能開工。

```md
就緒 1 件（trunk-based，未達 4），但任務 C 需要 A 的 API 先進 main → `--trigger dependency` 結批。
```

## Bad Example

- 這個例子是壞的，因為它把 handoff 當成結批理由，或要求使用者湊滿件數才處理 manual 請求。

```md
- 要交接了 → 先把就緒的全部落地。
- 使用者說 merge back → 「目前只有 1 件，未達 4 件門檻，先不處理」。
```

# Rule 5 - 觸發後由主線自己進 `/commit`，NEVER 要使用者代打

- Level: `MUST`
- 命中觸發條件後，主線自己呼叫 `/commit`，在隔離整合區合併：
  - `trunk-based`：固定收同 repo 當下**所有**已就緒且允許落地的成員。
  - `pr-merge-based`：預設只收**一個** work id；緊密相依需要合批時必須顯式 `--group-work-ids`。
- **NEVER** 要使用者代打已命中條件的 `/commit`，也 **NEVER** 要使用者開 main 或輸入任何指令。使用者唯一的後續動作是真正的人工檢查決定（GUI 的 OK／Issue／Skip）；決定之後由 coordinator 標記完成並自己呼叫 `/commit`。
- 若某個 workflow 步驟需要另開乾淨 session，使用 [[session-tasks.operations]] § Herdr session transport 派出並回報 dispatch receipt。

## Good Example

- 這個例子是好的，因為命中條件後主線直接接手，人工檢查以外不打擾使用者。

```md
batch status 回報 auto 觸發（pr-merge-based，1 個 work id）→ 主線呼叫 /commit。
人工檢查需使用者在 GUI 點 OK → 收到 OK 後主線標完成並續跑 /commit。
```

## Bad Example

- 這個例子是壞的，因為它把已命中的落地動作推回給使用者。

```md
已達觸發條件，請你在 main 打 `/commit` 完成落地。
```

# Rule 6 - 整批跑完整品質流程，批次開始後的新成員進下一批

- Level: `MUST`
- 整批跑完整 simplify、review、checks 與適用的人工 gate，依功能建立多筆正式 commit。
- 批次開始後才就緒的成員進**下一批**，不中途插入。未就緒的任務不阻擋手動提交。
- 批次整合衝突在隔離整合 worktree 內解決，再以 `batch resume` 續跑；來源保持不動。
- 測試訊號在來源 worktree 以 `test:affected` 取得；**NEVER** 為了跑測試把 draft PR 提早 `gh pr ready`。
- Integration 模式：切片由 coordinator 以 `integration-merge.ts --pr <n>` 落地到 `integration/<work-id>`；`test:affected` 由 coordinator 在 integration 轉 ready 前跑一次。
- review 後 coordinator 的 push 僅限把正式 HEAD 送上**既有** PR 的 head；ready、merge 與 push `main` 只由具名 coordinator 執行。

## Good Example

- 這個例子是好的，因為新成員被排到下一批，衝突在整合區解。

```md
批次（A、B）進行中，C 剛就緒 → C 進下一批。
A、B 整合衝突 → 在整合 worktree 解完 → batch resume。
```

## Bad Example

- 這個例子是壞的，因為它中途塞進新成員，並為了測試訊號提早轉 ready。

```md
批次跑到一半把 C 也合進來；為了看 test-lane 先把 draft PR `gh pr ready`。
```

# Rule 7 - 正式品質流程未通過、成果未落地 main，來源就保留

- Level: `MUST`
- 正式落地 main 之後，由 commit skill 呼叫 batch cleanup：逐來源驗證已落地、HEAD 未變、無 WIP／活寫入者／保留契約，才移除 worktree 與 branch；隔離整合區最後回收。PR 制要等 PR 合入 main。清理可以獨立重試。
- 安全邊界——下列都**不是**可刪來源的證據：
  - `absorbed into main`：舊 merge-back 可能只寫了 index，要有正式 commit 與落地證據才可清理。
  - 「checkpoint 已 commit」「draft PR 已開」「squash exit 0」：正在拿這些當刪除理由時，改查正式落地紀錄。draft 不是 ready，也不會啟動完整品質鏈。
  - 「兩條改的檔完全不重疊」：共享 index 仍有競態，同 repo 只有一批持有整合權。
- 衝突或 gate 失敗 → 保留來源。main 或 source 前移、審後又修改，都會使舊證據失效，需重新驗收；**NEVER** 用 force-discard 解決。
- 回收的完整判準見 `rules/worktree保留與回收判準.md`。

## Good Example

- 這個例子是好的，因為它以正式落地紀錄為準，而不是中間狀態。

```md
PR #742 已 squash 進 main（main 上可見正式 commit）→ batch cleanup 驗 HEAD 未變、無 WIP → 移除來源。
```

## Bad Example

- 這個例子是壞的，因為它把中間狀態當成落地，提早刪除來源。

```md
draft PR 已開、checkpoint 已 commit → 清掉 worktree 釋放空間。
```

# Rule 8 - 批次指令只讀 commit skill 的 `batch.md`，本檔不保存命令

- Level: `MUST`
- 進入就緒登記、觸發評估、批次落地或清理流程時，**MUST** 讀 commit skill 的 `batch.md`：命令、證據格式、衝突續跑與落地順序都以它為唯一正本。
- 本檔只決定「何時可以交接、何時要觸發、何時必須保留」；**NEVER** 在本 skill 內抄寫或改寫 `batch.md` 的命令細節，避免兩份正本漂移。
- 沒有就緒 worktree、也沒有待續跑批次時，普通 `/commit` 照常處理當前工作區。

## Good Example

- 這個例子是好的，因為判準與命令各有唯一來源。

```md
本檔判定 A 可登記就緒 → 讀 commit skill `batch.md` 取得 `batch ready` 的參數格式 → 執行。
```

## Bad Example

- 這個例子是壞的，因為它在 skill 內另存一份命令，日後 `batch.md` 更新時會分岔。

```md
（在本檔貼上 batch ready／status／resume／cleanup 的完整參數表）
```
