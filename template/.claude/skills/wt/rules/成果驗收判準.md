# Rule 1 - 完成回報是待驗證的主張，四項都核實才算通過

- Level: `MUST`
- worker 回報「done」只是主張。通過驗收前 **MUST** 逐項核實：
  1. **terminal outcome**：worker 已真正結束（收到完成通知，或載體回報 terminal 狀態），不是中途回報。
  2. **checkpoint scope**：`git -C <worktree> log --oneline main..HEAD` 有預期的 commit，且異動路徑落在 brief 的 scope 內（Rule 4）。
  3. **驗收證據**：brief 驗收標準要求的測試、截圖、evidence sidecar 確實存在，且是本次 revision 的（Rule 2）。
  4. **writer release**：worker 已明說停止寫入此來源；該樹沒有仍在寫的 process、claim 或 lock。
- 任一項缺證據或歸屬不明：來源留在就緒池外並保留（見 `rules/worktree保留與回收判準.md`），在回報中寫明缺哪一項與下一步，**NEVER** 用「`git status` 乾淨」推定已驗收。
- 編碼任務應有 commit；`main..HEAD` 為空且回報是 done → 視為失敗處理（Rule 7）。調查任務通常沒有 commit，改以 Rule 6 驗收。

## Good Example

- 這個例子是好的，因為它逐項核對，發現證據缺漏就不放行。

```md
A（auth-refresh）：完成通知 ✓；main..HEAD 2 commits、4 檔全在 scope ✓；
brief 要求的 test/auth 輸出 ✓；evidence sidecar 缺本 phase 的 receipt ✗；writer-release ✓
→ 不進就緒池，退回同一 worker 補 artifact-tick。
```

## Bad Example

- 這個例子是壞的，因為它只看 worker 一句話與 git 狀態就放行。

```md
worker 說 done、樹內 `git status` 乾淨 → 直接 `batch ready`。
```

# Rule 2 - 驗收先驗實作樹，NEVER 掃 main 或先合回 main 才收證據

- Level: `MUST`
- 驗收 **MUST** 在 change 所在的實作 worktree 執行（`cd <worktree> && <驗收指令>` 一行式，parent cwd 不動），驗完才進批次落地流程。
- **NEVER** 在 cwd 的 main 跑驗收 gate——main 看不到這棵樹的實作，掃出來的「通過」或「失敗」都與這次工作無關。
- **NEVER** 為了收證據先合回 main。合回是落地，不是驗收手段。
- 這條**沒有任何機械 gate 在執行**，執行者就是讀到這條規則的你。對應 pitfall：[[pitfall-pre-archive-gate-scans-main-not-change-worktree]]。
- 若主線尚未看到本次 revision 的必要證據，卻出現「合回、收尾、完成、已解決」等落地話術，**MUST** 停下，切回 worktree 內的 dev-server／驗收路徑。

## Good Example

- 這個例子是好的，因為驗收指令在實作樹內執行。

```bash
cd ~/offline/clade-wt/auth-refresh && pnpm test test/auth
```

## Bad Example

- 這個例子是壞的，因為它在 main 跑 gate，或先合回再驗。

```md
在 main 跑 `pnpm test test/auth`（main 沒有新 API，測試結果不代表本次工作）
或：先 merge-back 到 main 再跑測試收證據。
```

# Rule 3 - commit 必須存在且 header 過得了 commitlint

- Level: `MUST`
- 編碼任務跑 `git -C <worktree> log --oneline main..HEAD`：
  - 為空 → 依 Rule 7 失敗處理。
  - 每個 header 須符合 `<emoji> <type>(<scope>): <subject>`，emoji 與 type 一對一（`✨ feat`、`🐛 fix`、`🧹 chore`、`🔨 refactor`、`🧪 test`、`🎨 style`、`📝 docs`、`📦 build`、`👷 ci`、`⏪ revert`、`🚀 deploy`、`🎉 init`）；repo 要求 subject 含中文時也要符合。不合格的 header 會讓後續批次在 hook 卡住，退回同一 worker 修正。
- **NEVER** 把 commit 存在本身當成驗收通過；它只證明「有東西被提交」，不證明範圍與行為正確。

## Good Example

- 這個例子是好的，因為它同時檢查 commit 存在與格式，並把格式問題退回原 worker。

```md
main..HEAD：`🧹 feat: add refresh` → emoji 與 type 配錯（代表該樹的 commit-msg hook 沒生效）→ 退回同一 worker 修正 header 並回報 hook 為何沒擋，不在主線代改。
```

## Bad Example

- 這個例子是壞的，因為它看到有 commit 就算驗收通過。

```md
main..HEAD 有 2 個 commit → 驗收通過。
```

# Rule 4 - scope discipline：異動路徑必須落在 brief 宣告的範圍內

- Level: `MUST`
- 跑 `git -C <worktree> diff main..HEAD --name-only`，逐條比對 brief 的 Scope 段。
- 出現 scope 外路徑時依性質處置：
  - 屬於 Git baseline（fork 時帶進的 main 狀態）卻被提交 → worker 違反契約，退回同一 worker 拆出該 commit。
  - 屬於完成任務確實需要、但 brief 沒授權的擴大 → 不放行；回報呼叫端，由它決定拆成另一個任務或回 `/specify` 做授權的 scope 修訂（依 [[scope-discipline]]）。
  - 屬於無關的順手修改 → 退回同一 worker 移除。
- **NEVER** 主線自行在樹內刪改 worker 的超範圍變更再放行——那會讓證據與回報對不上。

## Good Example

- 這個例子是好的，因為它把超範圍路徑分類後各自處置。

```md
diff 多出 shared/types/user.ts（任務需要但未授權）與 README.md（順手改）
→ README 退回 worker 移除；user.ts 回報呼叫端決定是否擴 scope。
```

## Bad Example

- 這個例子是壞的，因為它看到超範圍卻以「改得不多」放行。

```md
多改了 3 個 scope 外的檔，看起來沒問題 → 放行。
```

# Rule 5 - view-layer drift 雙檢：非 UI view 列的成果不得碰 view 層

- Level: `MUST`
- 派工列不是 `ui-view-implementation` 的任務，驗收時 **MUST** 跑：

```bash
git -C <worktree-path> diff main..HEAD --name-only \
  -- '*.vue' '*.tsx' '*.jsx' '*.css' '*.scss' \
     'app/pages/**' 'app/components/**' 'app/layouts/**' \
     'pages/**' 'components/**' 'layouts/**' 'views/**'
```

- 有任何命中 → 透過當前 runtime 的使用者提問介面給三個選項，不自行決定：
  1. reset 並以修正後的 brief 重派
  2. 接受非 view 部分，view 部分依 routing table 另派 UI view 列（或由符合該列 model 要求的主線自己做）
  3. 放棄這次成果（來源依 `rules/worktree保留與回收判準.md` 處置）
- 這是 worker 自我檢查（`rules/worker契約.md` Rule 3）之外的第二道檢查，**NEVER** 因 worker 回報「已自檢」而跳過。

## Good Example

- 這個例子是好的，因為命中後交給使用者選，而不是主線默默接受。

```md
non-ui-implementation 的成果命中 app/components/LoginForm.vue
→ 向使用者提問：[1] reset＋重派 / [2] 接受 API 部分、view 另派 ui-view-implementation / [3] 放棄
```

## Bad Example

- 這個例子是壞的，因為它省略第二道檢查，view 變更跟著非 UI 成果進了就緒池。

```md
worker 回報已自檢 view-layer → 不重跑 diff，直接進就緒池。
```

# Rule 6 - 調查任務依載體的回報判讀，結論寫進 brief 的 Findings

- Level: `MUST`
- 調查型任務通常沒有 commit，驗收看載體的回報：
  - **除錯（debug）走 native Claude 載體**（`non-ui-implementation` 列，見 `派工載體.md` § Pi dispatcher），以 worker 的完成回報驗收：根因、重現步驟與證據是否回答了主線事先寫好的 acceptance，關鍵發現同樣寫進 `# Findings`。
- **調查類 Pi 列**（`read-heavy-scan` 等純讀分析）以 dispatcher 的 stdout JSON 與 exit code 驗收：
  - **exit 0**：讀 JSON 的 `result` 欄位（依模板而定的結構化證據），對照主線事先寫好的 acceptance 判斷是否回答了問題；把關鍵發現寫進 `WORKTREE-BRIEF.md` 的 `# Findings` 段，讓接續的 session 不必重跑。
  - **exit 2**（business fail）：調查有跑完但沒達到 acceptance；讀 `result` JSON 看缺什麼，決定補 brief 重派或交回呼叫端。
  - **exit 3**（mechanical failure）：Pi 自身壞掉；查 `/tmp/pi-<label>-stderr.log`，修正後重派，不要把它當成「調查結論是否定」。
  - **exit 4**（quota）：照回報的 `next_step` 降級重派，**MUST** 帶 `--retry-of`（見 `派工載體.md` 的 exit code 表）。
- acceptance 必須是主線派工前寫好的，**NEVER** 事後讓 Pi 的輸出自己定義什麼算通過。

## Good Example

- 這個例子是好的，因為它區分了機械失敗與業務失敗。

```md
wt-investigate-cache exit 3 → 讀 /tmp/pi-wt-investigate-cache-stderr.log：模板變數缺 git_baseline → 補上重派。
```

## Bad Example

- 這個例子是壞的，因為它把 Pi 自身崩潰誤讀成調查結論。

```md
exit 3 → 回報「調查結果：沒有找到 cache 問題」。
```

# Rule 7 - 不合格時依失敗型態選擇重派、換載體或保留，NEVER 草率丟棄

- Level: `MUST`
- 所有失敗路徑的共同前提：**保留 worktree 與 branch**，回報路徑與錯誤尾段（stdout／stderr 最後幾行），在 brief 寫明失敗原因。
- 依失敗型態選下一步：
  - **Claude worker 失敗**（回報 fail，或沒有 commit 就結束）→ 在同一棵樹重派：新的派工明確傳入 worktree 路徑，以接續模式從 brief 的下一個未勾項目繼續。
  - **Pi 編碼任務失敗**（非 0 exit 或失敗通知）→ 三選一：
    - **調整 brief 後重試**：修正 scope、路徑或指示，寫新的 brief 檔，重派進**同一棵樹**（樹已存在，不再跑 `wt-helper add`）。
    - **換載體**：依 routing table 該列允許的載體改派（例如改走 Claude 原生／Herdr 載體），以接續模式從 WORKTREE-BRIEF 接手。**NEVER** 為了換載體自挑 routing table 沒列的 model。
    - **丟棄**：只在呼叫端或使用者確認這份成果不要時，依 `rules/worktree保留與回收判準.md` 處置；`cleanup --force --force-discard-unland` 會永久丟失 commit。
  - **批次整合衝突** → 在隔離整合 worktree 內解，再 `wt-helper batch resume` 續跑；來源保持不動（細節屬 commit skill 的 `batch.md`）。
  - **既有樹在 rebase／merge main 後 `sync-rules` 報 `local or modified file conflict`** → 在該樹跑 `wt-helper reconcile <slug>` 後重跑原同步指令（指令見 `wt-helper指令.md`）；受保護的本地修改仍會擋下，不強制覆寫。
- 同一任務連續失敗兩次以上時，先檢查 brief 本身是否有問題（scope 錯、驗收標準不可達），再決定是否繼續重派。

## Good Example

- 這個例子是好的，因為它保留來源、修 brief 後重派進同一棵樹。

```md
Pi exit 1：brief 漏列 test/fixtures/ 為允許路徑 → 寫新 brief 檔補上 → 重派進 ~/offline/clade-wt/auth-refresh（不重跑 add）。
```

## Bad Example

- 這個例子是壞的，因為它一失敗就丟棄重開，或為了換載體挑了 routing table 沒列的 model。

```md
Pi 失敗 → `cleanup auth-refresh --force --force-discard-unland` → 重新開樹，改派一個比較便宜的 model 試試。
```
