# Rule 1 - 先查 worktree 是否已存在，再決定新建、接續或停下

- Level: `MUST`
- 對每個任務檢查 `<consumer>-wt/<slug>/` 是否已存在且帶 `WORKTREE-BRIEF.md`：
  - 存在、brief `status` 不是 `done`／`failed`、且沒有仍活著的寫入者（`claim-helper` 的 claim 或執行中的 Herdr pane）→ 走接續，跳到 Phase 1 第 6 步。
  - 有活著的寫入者、brief 已結案，或路徑存在卻沒有 brief → 不建、不接，停下回報呼叫端。
  - 路徑不存在 → 新建，續走 Phase 1 第 3 步。

## Good Example

- 這個例子是好的，因為它確認沒有活著的寫入者才接續。

```md
`~/offline/clade-wt/auth-refresh/` 存在、brief `status: in_progress`、`claim-helper` 無 claim、沒有執行中的 pane
→ 接續，跳到第 6 步。
```

## Bad Example

- 這個例子是壞的，因為路徑存在卻沒有 brief 時仍自行接手。

```md
`~/offline/clade-wt/auth-refresh/` 存在但沒有 `WORKTREE-BRIEF.md` →「應該是上次留下的」→ 直接在裡面派工。
```

# Rule 2 - 接續時不重寫 brief，只更新 `last_updated`；新指示追加到 Progress

- Level: `MUST`
- 新建時在每棵樹根目錄寫出 `WORKTREE-BRIEF.md`，Context 的 backing service 列照 `add` 輸出的狀態行填。
- 接續時不重寫，只更新既有 brief 的 `last_updated`。
- 呼叫端這次的指示與原 Task 不同時，把新指示加註日期追加到 Progress，不改 Task 原文。

## Good Example

- 這個例子是好的，因為原 Task 保持原文，新指示帶日期進 Progress。

```md
last_updated: 2026-10-07
## Progress
- 2026-10-07 呼叫端追加：refresh token 逾時改為 30 分鐘（原 Task 未列）。
```

## Bad Example

- 這個例子是壞的，因為接續時整份重寫，原 Task 被新指示蓋掉。

```md
接續既有樹 → 依 template 重新產生 `WORKTREE-BRIEF.md`，Task 段改寫成這次的指示。
```
